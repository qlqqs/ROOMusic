# 播放器管理界面设计规范

本规范适用于媒体库浏览、发行版本详情、播放队列和底部播放器等工作流。

## 视觉与信息层级

- 界面定位为私有音乐库的工作台，优先支持管理、扫描、检索和连续播放，不使用营销式首屏或装饰性大卡片。
- 视觉语言以 `frontend/DESIGN.md` 为唯一设计锚（2026-09-04 起：暖纸底 + 墨色文字 + 朱红 accent 的唱片店月刊方向，取代此前的深色 + 青绿方案）；蜜蜡色表示警告或需要关注的状态；颜色必须同时满足文字与控件的对比度要求。
- 页面区块使用 CSS grid/flex 组织；封面、卡片、详情内页与胶囊控件圆角不超过 `22px`，数据行与输入框等高密度控件保持 `6–10px` 小圆角；避免卡片嵌套卡片和大面积单一色相渐变。
- 信息密度以 Release/Medium/Track 的扫描效率为准：标题、艺术家、年份、曲目数量和状态应有稳定的视觉层级，长文本使用截断并提供可访问的完整名称。

## 布局与响应式

- 桌面端采用“刊头 + 栏目行 + 页面切换”的报刊式布局（见 `frontend/DESIGN.md` 布局节，2026-09-05 起取代三栏工作台与单页锚点）：首页（头条 + 唱片架 + 节目单横向节目带）、专辑库、编辑部为三个独立页面，经 hash 路由切换；主内容拥有弹性宽度，任一区块不得挤压核心数据的可读性。
- 移动端在窄于 `768px` 时区块改为上下堆叠，当前 CSS 使用 `max-width:768px`；栏目导航与节目带允许自身横向滚动，但不得依赖横向滚动来完成核心操作。
- 固定底部播放器必须为页面内容预留底部空间，不能遮挡最后一条发行版本或表单控件；控件尺寸保持稳定，避免播放状态变化造成布局抖动。
- 交互控件在桌面和触屏均提供足够的点击区域，文字和图标不得溢出父容器。

## 播放器交互

- 播放器至少展示当前曲目、艺术家、播放/暂停、上一首、下一首和队列入口；按钮使用语义化 `button` 与 `aria-label`。
- 播放队列是本地 UI 状态，服务端媒体库仍是数据权威；切换发行版本时应明确更新当前项和队列摘要。
- 无音频服务时允许使用本地演示播放状态，但不得伪造已完成的服务端播放或下载能力；状态应能被键盘操作并提供可见焦点。
- 加载、空、错误和无权限状态必须在对应区域内可恢复，不能只依赖颜色或控制台日志传达状态。

## 组件与可访问性

- 当前没有组件或 icon 库，使用原生 React + CSS 和语义符号；熟悉的图标操作必须提供 aria 名称，陌生符号提供可见 tooltip 或等价辅助文本。
- 使用语义标题层级、列表和导航 landmark；搜索输入必须有 label，结果项和队列项应支持键盘聚焦。
- 角色判断只用于导航和禁用态，不能替代后端权限校验；所有管理操作继续通过 REST API 获取最终结果。

## 禁止事项

- 不在组件内直接调用 `fetch` 或解析原始 JSON；遵循“页面 -> feature hook -> API decoder -> HTTP transport”数据流。
- 不把任意主机文件路径、Bearer token 或生产环境凭据放入播放器 UI 状态。
- 不以新增独立生产前端服务为前提；生产资产由 Go 应用同源提供，Vite 仅用于开发迭代。

## 验收清单

- [ ] 桌面头版区块流与 `375px` 移动端上下堆叠均无重叠或遮挡；详情内页翻开/合拢不残留焦点或遮挡。
- [ ] 播放器固定定位不遮挡页面末尾内容，播放状态变化不改变控件尺寸。
- [ ] 搜索、队列、管理操作具备加载、空、错误和恢复路径。
- [ ] 键盘可完成核心播放与导航操作，焦点可见且名称完整。
