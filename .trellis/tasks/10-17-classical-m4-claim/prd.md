# M4 认领

> 状态：2026-10-17 创建，同日完成需求讨论（K1–K5），用户批准最终规划摘要（含 K6–K9）；实施中。
> 技术设计见 [design.md](design.md)，执行计划见 [implement.md](implement.md)。

## 目标与用户价值

扫描在“证明不了是同一个版本”时会新建发行。管理员之前在旧发行上做的修改（字段修正、归入的专辑、默认版本、问题核对）会留在旧发行上，
而旧发行从此不可见：这些修改看不到效果，也无法再改动或撤销。认领让管理员把这些修改接到扫描新建的发行上，不必凭记忆重做一遍。

这是 Core 1 阶段 M4 的第三项（[路线图](../../../docs/architecture/core-1-roadmap.md) M4 行的 ③“认领：旧发行的修正与归组迁给新发行”），
对应父任务需求 R6。用户 2026-10-17 说“继续 M4 的下一个规划”，按路线顺序立项。

## 背景（已核对的事实）

**什么时候扫描会新建发行**（[ADR 0002](../../../docs/architecture/adr/0002-metadata-overlays.md) 第四节第 134 行，阶段 I 已实施）

- 发行按曲目成员关系沿用：一个候选里已沿用的曲目**严格过半**属于同一个既有发行时，才沿用它的 ID
  （`backend/internal/catalog/identity_plan.go:365` 的 `allocateReleases`，`:383` 的 `overlap*2>tt.total`）；否则写入时新建发行与一个新组
  （`backend/internal/catalog/persist.go:138` 的 `persistRelease`，`:142` 新建组）。
- 由此产生新发行的常见情形，都有集成测试：
  - 新增的文件不少于原有的，例如 2 首加 3 首、1 首加 1 首（`backend/internal/library/release_membership_integration_test.go:296`、`:328`）。
    原有曲目仍是原来的曲目 ID，只是改挂到新发行下。
  - 整张原地换成另一份音频（重新抓轨）：同一路径但指纹不同，就得到新曲目；旧曲目失去来源身份并标为缺失
    （`backend/internal/library/identity_rebinding_integration_test.go:492`；`backend/internal/catalog/persist_track.go:96` 的 `vacateSourceIdentity`）。
  - 跨扫描目录（跨 root）移动：曲目一律是新身份，旧曲目标为缺失（`identity_rebinding_integration_test.go:464`）。ADR 0002 第 133 行要求：
    “若要转移修正，必须有单独审阅的绑定映射、双方 revision、影响预览和逆操作”。
  - 多个文件音频完全相同时不重绑定（`identity_rebinding_integration_test.go:319`）。
- 拆分时，重叠更多的一方沿用原 ID，另一方是新发行（`release_membership_integration_test.go:242`）。这时旧发行仍然可见，不属于本项处理的“旧发行消失”。

**旧发行之后的状态**

- 发行行与它的修正、核对、归组从不删除。外键都是 `ON DELETE CASCADE`，只是保险（`backend/migrations/0017_governed_operations.sql`、`0019_release_issue_reviews.sql`）。
- 旧发行没有 present 曲目就不可见（`backend/internal/catalog/read.go:32` 的 `releaseVisiblePredicate`）：列表、详情、搜索、按组读取都看不到它。
  它如果是组里唯一的版本，原来的专辑地址返回 404（`backend/internal/catalog/groups.go:17`）。
- 旧发行上的受治理写入与撤销全部被拒绝：修正、归组、核对和它们的撤销都先经过 `lockVisibleRelease`，发行不可见就返回 `404 not_found`
  （`backend/internal/catalog/corrections.go:367`；调用处 `corrections.go:388`、`group_change.go:96`、`issue_review.go:182`、`revert.go:56`、`revert.go:162`、
  `issue_review.go:260`）。“归入其他专辑”的目标组也必须有可见版本（`group_change.go:123`）。所以这些修改现在是冻结的，管理员拿它们没有办法。
- 操作记录里这些记录还在，专辑列写“标题（已不可见）”，不能撤销（`frontend/src/features/governance/components/operation-list.tsx:28`；
  `backend/internal/catalog/revert.go:269` 的可撤销条件含 `info.Visible`）。

**旧发行上可能留着的人工状态**（都以发行或组为目标，走[受治理操作合同](../../spec/backend/governance-contracts.md)的 `operations.Run`）

| 状态 | 存放位置 | 与新发行的关系 |
| --- | --- | --- |
| 字段修正（八个字段的 set / null） | `release_corrections`（每个字段至多一行） | 新发行按扫描值显示，没有修正（M3 的 G8，`governance-contracts.md` 第 7 节） |
| 归入的专辑 | `releases.group_id` | 新发行自己一个新组；旧组如果没有别的可见版本，就从列表消失 |
| 默认版本 | `release_groups.default_release_id` 指向旧发行 | 旧发行不可见时静默失效，组改按“年份最早”（[默认版本合同](../../spec/backend/default-version-contracts.md)） |
| 问题核对（来源类型、介质类型、归组冲突、缺失曲目） | `release_issue_reviews`，依据是扫描结论 | 新发行没有核对，问题重新出现（[核对合同](../../spec/backend/issue-review-contracts.md)第 7 节：“迁移属于认领”） |

**推荐能用的线索**

扫描结束后暂存行就被删除（`backend/internal/catalog/staging.go:138` 的 `ClearStagedObservations`），扫描不记录“旧发行变成了哪个新发行”。下面这些线索仍在库里：

- 旧发行的扫描目录与相对目录不变：扫描只更新被沿用的发行（`persist.go:138`）。
- 原地替换时，旧曲目标为缺失，相对路径保留（`vacateSourceIdentity` 只清来源身份，`persist.go:241` 的 `MarkMissingSources` 只改状态）；新曲目就在同样的路径上。
- 旧发行的归组依据 `release_grouping_evidence.source_refs` 是它最后一次被扫描时的来源路径，最多 100 条（`persist.go:124`）；发行不再被沿用之后，这一行不再被重写。
  成员增加时，原有曲目整体改挂到新发行，旧发行名下一首曲目都不剩，只有这一行还记得原来的文件。
- 扫描从不把新发行放进已有的组（每个新发行新建一个组），所以一个版本和别的版本同在一张专辑里，只可能是人工归组的结果。

**设计与决策约束**

- ADR 0002 第四节：无法证明成员关系连续时新建发行，“原有修正留待人工认领，不静默重挂到新目标”；不按标题相似度搬移修正；
  合并、拆分时“不能把 Release 修正复制给全部拆分结果，或按最后写入覆盖合并双方修正”（第 136 行）。
- ADR 0002 第十节第 6、7 项与 ADR 0003 第十节第 7 项：认领（“修正迁移”）是 M4 的结构操作，须逐类批准；回退方式是关闭写入路由、保留数据。
- [DESIGN-acceptance.md](../../../frontend/DESIGN-acceptance.md) 第 116 行写着“认领、合并拆分仍另议”；原型里没有认领的界面。

## 裁决

| 编号 | 问题 | 结论 | 来源 |
| --- | --- | --- | --- |
| K1 | 认领做到什么程度 | **列出、推荐并迁移**：列出已不可见、但留有人工修改的旧版本；系统按同一目录和文件路径推荐对应的新版本，也能手动搜索任意可见版本（包括别的目录）；确认前预览要迁移的修改和冲突；迁移一次写一条操作记录，可以撤销；需要一次迁移 | 用户 2026-10-17 选择（推荐项） |
| K2 | 迁移哪些人工修改 | **四类整体迁移**，新版本接替旧版本：① 字段修正搬到新版本；② 旧版本和别的版本同在一张专辑里时，新版本归入那张专辑；③ 旧版本是那张专辑的默认版本时，新版本接任；④ 核对照搬，依据（同样的文件与候选值）相同就继续有效，否则按问题处理的规则重新提醒。迁完后旧版本上不留人工修改，从待认领列表里消失 | 用户 2026-10-17 选择（推荐项） |
| K3 | 新版本已有人工修改时以谁为准 | **以新版本已有的为准**：认领只补上新版本还没有的修改；两边改过同一个字段、核对过同一类问题，或新版本已经在另一张多版本专辑里时，保留新版本的；旧版本的这些修改不迁移（迁完后旧版本上也不再保留），预览里列出旧值，撤销认领可以恢复 | 用户 2026-10-17 选择（推荐项） |
| K4 | 入口 | **单独页面，详情也提示**：导航“资料库”下加“待认领”（只有管理员，不显示数量）；两栏，左边列旧版本（标题、原来的专辑、最后所在的目录、留着哪些修改），右边是推荐的新版本与理由、搜索其他版本、预览与确认；专辑详情里当前版本是某个旧版本的推荐对象时，管理员看到“可能接替了已不可见的《…》”，点进去就是认领 | 用户 2026-10-17 选择（推荐项） |
| K5 | 没有新版本可接替的旧版本 | **本项不做放弃**：一直留在“待认领”里，列表按最后一次出现的时间倒序，这类会沉到后面；文件回来后自动消失；只有认领一种写操作，以后觉得吵再单独加“放弃” | 用户 2026-10-17 选择（推荐项） |
| K6 | 推荐依据与手动搜索 | 推荐只看两条：旧版本最后的文件路径（名下曲目的路径与归组依据的来源路径）与新版本的 present 曲目相同（同一 root），或两者是同一个目录；最多 5 个，写明理由与命中的文件数；不用音频指纹，不按标题相似度。手动搜索沿用“归入其他专辑”的专辑搜索，先选专辑再选版本，可以选到别的目录、别的 root 的版本 | 本规划提出，用户 2026-10-17 随最终摘要批准 |
| K7 | 迁移的细则 | 旧版本认领后离开原来的专辑（移进一个不可见的独立组），四类全部被跳过时也照样认领（表示新版本已经接替）；默认版本只在新版本进入那张专辑时接任，否则那张专辑改回自动选择（显示不变）；缺失曲目的核对不迁移（它针对旧版本自己的曲目）；迁过去的核对保留原核对人与时间 | 同上，用户 2026-10-17 随最终摘要批准 |
| K8 | 防止认领一个没看到的状态 | 预览带令牌；提交时状态与预览不同（页面打开之后又扫描或修改过）就拒绝（`409 claim_changed`）并重新读取；两个版本的版本号都要核对 | 同上，用户 2026-10-17 随最终摘要批准 |
| K9 | 撤销 | 撤销一次认领恢复两个版本与相关专辑的全部前态（修正、核对与原核对人、专辑、默认版本）；之后任一方又被修改过就拒绝；新版本之后变得不可见也可以撤销；专辑详情的“修改记录”同时列出以这个版本为来源或目标的认领 | 同上，用户 2026-10-17 随最终摘要批准 |

K1 里的“别的目录”也包括别的扫描目录（root）。管理员逐个确认、核对两边的版本号、先预览、可撤销，正是 ADR 0002 第 133 行对跨 root 转移修正提出的条件。

## 需求

- **R1 待认领列表（K1、K4、K5）**：管理员的“待认领”页列出已不可见、但留有人工修改（修正、多版本专辑里的位置、默认版本、核对）的旧版本，
  写明原来的专辑、最后所在的目录、最后一次被看到的时间与留着哪些修改；按最后一次被看到的时间倒序、分页；选中的版本与页码写进地址。
- **R2 推荐与搜索（K1、K6）**：详情写明旧版本留着的修改明细，推荐对应的新版本并写明理由；也能搜索任意可见版本作为目标。
- **R3 预览（K1、K3、K7）**：选中目标后逐项列出会迁移的修改、因为新版本已有而保留的修改及原因、改回自动选择的专辑、不迁移的缺失曲目核对，
  以及迁过去的核对在新版本上是否仍有效。
- **R4 认领（K2、K3、K7、K8）**：确认后一次完成四类迁移：修正与核对补到新版本、新版本归入旧版本的专辑并接任默认版本（按 K3、K7 的规则）；
  旧版本上不再留有人工修改并离开待认领列表；预览之后状态变了就拒绝并重新读取。
- **R5 受治理写入与撤销（K1、K9）**：认领走共同写入流程：只有管理员，带幂等键与两个版本的预期版本号，每次成功写一条操作记录；
  可以撤销（只针对新版本最近一次修改），撤销恢复全部前态，撤销本身不能再撤销；操作记录页与“修改记录”能看到并撤销这类记录。
- **R6 专辑详情的提示（K4）**：管理员打开的版本是某个旧版本的推荐对象时，操作区提示“可能接替了已不可见的《…》”，点进去就是认领并预选当前版本。
- **R7 不影响既有行为**：扫描不读写认领涉及的人工状态；认领之后重扫，迁过去的修改保持；没有任何认领时，所有既有接口与页面的输出逐项不变；
  普通成员看不到任何认领入口，只看到修改生效后的结果。

## 规划决策记录

- 路线：人工选择（route a，用户批准最终规划摘要）。选择者：用户（qlqq）。
- 2026-10-17：用户说“继续 M4 的下一个规划”，按路线顺序立项认领；K1–K5 依次选择推荐项。K6–K9 是规划细节，在最终摘要里一并请用户批准。
- 2026-10-17：用户回复“批准”，最终规划摘要（含 K6–K9、已接受的限制与十步计划）原样生效，进入实施。理由：产品裁决都由用户逐条做出，K6–K9 与取舍随摘要一并确认。

## 已接受的限制（2026-10-17 随最终摘要确认）

- 推荐只看文件路径与目录：目录与文件名都改了（含跨 root 移动）的版本推荐不出来，需要手动搜索；归组依据的路径最多 100 条，超出部分不参与推荐。
- 认领之后，被移走的修正与核对的原记录不能再单独撤销（旧版本的版本号已变）；要恢复就撤销这次认领。
- 同一张专辑的几个版本先后被替换，而前一个的新版本没有进入这张专辑（它已在别的多版本专辑里）时，后面的旧版本看不出原来的专辑关系，需要认领后手动归组。
- 没有新版本可接替的旧版本会一直留在列表里（K5）。

## 范围外
