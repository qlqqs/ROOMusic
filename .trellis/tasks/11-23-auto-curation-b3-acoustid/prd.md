# 自动整理 B3：AcoustID 与声学指纹

父任务：`.trellis/tasks/11-22-auto-curation-sources`（R4、R6，U8；父任务 implement.md 的“B3 AcoustID 与声学指纹”）。
前置 C（`b96d8ea3`）与 E1（`740c2b5a`）已合入。设计见 `design.md`，执行计划见 `implement.md`，规划时的核实记录见 `research/verification.md`。

## 目标

没有条码、编号、ISRC，标签又差（标题与艺人是占位、不是原文）的单曲与专辑，也能靠音频本身对上 MusicBrainz。
声学指纹只在本机算，只把指纹与时长发给 AcoustID；没有指纹工具、没填密钥时这个源显示为未启用，其余功能完全不受影响。

## 已核实的事实（详见 research/verification.md）

- 镜像与开发环境固定的静态 ffmpeg（mwader/static-ffmpeg 7.1.1）没有 chromaprint 复用器。
- Alpine 3.23 的 `chromaprint` 包带 `fpcalc` 1.6.0，但依赖动态的整套 FFmpeg 库：65 个包、约 100 MiB；现在的生产镜像是 251 MB。
- chromaprint 上游在 GitHub 发布了官方的静态 `fpcalc`（1.6.2，2026-10-15，linux-x86_64 与 linux-arm64，压缩包约 2.4 MB、解开约 5.4 MB），可按 sha256 固定。
  它能从标准输入读原始 PCM（`-format s16le -rate -channels`）。用我们的 ffmpeg 解码成 11025 Hz 单声道再交给它，与它自己读文件相比位差 0.05%，60 秒音频约 30 ms。
- chromaprint 是 LGPL 2.1。项目没有许可证文件，把它的代码移植进 Go 二进制会把 LGPL 代码静态链接进来；以单独的程序随镜像分发与现有 ffmpeg 的处境相同。
- AcoustID：`https://api.acoustid.org/v2/lookup`，GET 与 POST 都可，POST 可以 gzip；“不超过每秒 3 次”；仅限非商业免费，商业用途另签；
  每个应用注册自己的 `client` 密钥（不内置共用密钥，与 U8 一致）。
- 标签里的 AcoustID 编号已经解析落库（`track_identifiers.kind='acoustid'`）；曲目有内容指纹（`tracks.content_fingerprint`）与来源的大小、修改时间。
- C 的匹配：信息不足（标题与艺人都是占位、没有任何标识）时直接 `no_match` + `insufficient_evidence`，不查询。这正是 B3 要补的那部分。
- C 的 `needsWork` 在规则版本变化时重新处理**所有**状态（包括已对上的，以及封面、歌词）；MusicBrainz 每秒 1 次，几千张专辑的曲库重做一轮要数小时。

## 需求

| 编号 | 需求 |
| --- | --- |
| B3-R1 | 部署：生产镜像带固定版本的官方静态 `fpcalc`（按架构核对 sha256）；`ROOMUSIC_FPCALC_PATH` 可配置；启动自检，不通过时只让 AcoustID 不可用；开发与测试用同一个文件（照 `scripts/ffmpeg-pinned.sh` 的做法） |
| B3-R2 | 指纹计算：照音频分析的取源方式（允许的根、大小与修改时间核对、CUE 区间、DSD）解码前 120 秒，算出指纹；结果按曲目缓存，只在音频内容（或 CUE 区间、算法版本）变化后重算 |
| B3-R3 | AcoustID 适配器：指纹识别能力、全实例每秒至多 3 次、按请求内容缓存、失败分类（限流与服务不可用退避重试；密钥无效单独识别） |
| B3-R4 | 密钥设置：管理员分别填写、更换、清除 AcoustID 的应用密钥与用户密钥（design 8.9）；密钥加密保存，只显示末四位；服务端发现某一把无效时在界面上说明 |
| B3-R5 | 源的状态：AcoustID 默认开，但没有指纹工具、没填密钥、密钥无效时不生效，分别给出原因 |
| B3-R6 | 匹配：声学指纹接在光盘目录与搜索之间（专辑与单曲两种方式），判定规则与相反证据用测试固定；信息不足的发行在指纹可用时不再直接放弃 |
| B3-R7 | 重新处理：AcoustID 变得可用时（升级后、填入密钥后），只重新处理“走到了指纹这一步却因为它不可用而跳过”的发行；已对上的、封面与歌词不重做 |
| B3-R8 | 界面：外部源一组里 AcoustID 一行的密钥填写与状态；能力名“声学指纹”；打开总开关的确认框写明 AcoustID 收到什么 |
| B3-R9 | 文档：ADR 0005 补“声学指纹可以发给 AcoustID”；ADR 0006、外部源合同、自动整理合同、部署合同、前端规范与路线图随之更新 |

## 验收标准

- [ ] AC1 生产镜像里 `/usr/local/bin/fpcalc -version` 输出 1.6.2；镜像比改动前增大不超过 10 MB；`scripts/check-production-compose.sh` 通过，容器启动后健康。
- [ ] AC2 `fpcalc` 不存在或自检失败时：应用正常启动，AcoustID 的 `inactive_reason` 为 `fingerprint_unavailable`，其余源、匹配、封面、歌词的行为与改动前相同（受控服务的集成测试）。
- [ ] AC3 同一曲目在音频内容不变时第二次取指纹不再启动解码进程；内容指纹、CUE 区间或算法版本变化后重算（集成测试，真实 ffmpeg 与 fpcalc）。CUE 虚拟轨只取自己的区间。
- [ ] AC4 适配器向 AcoustID 发出的只有 `client`、`user`、`duration`、`fingerprint`、`meta`、`format`，请求体 gzip；两次请求的间隔 ≥ 334 ms；限流与 503 退避后成功或记为稍后再试；应用密钥（码 4、17）或用户密钥（码 6）无效时只标那一把、这个源的状态变为 `key_invalid`，换了密钥后恢复（受控服务）。
- [ ] AC5 密钥接口（`/sources/{id}/keys/{name}`）：填写后列表里只返回末四位与状态；只填一把或清除任一把后 `key_missing`；非管理员 403；没有密钥概念的源 400；未声明的密钥名 404；数据库里只有密文。
- [ ] AC6 判定：标签全是占位的整张专辑，有结果的抽样曲目（抽样 ≥ 2 首时至少 2 首）的指纹交集恰好指向一个曲目数与碟数相符的外部发行、曲目数一致、时长在容差内、配对的录音都在各自的指纹结果里时对上（`method="acoustid"`）；
  任何一条相反证据（含新增的 `acoustid_mismatch`）或多个候选都通过时拿不准并建待定项；单曲同理（时长筛选后恰好一个录音，经 MusicBrainz 读回正式数据，标题不是占位时还要相等）。信息不足的发行指纹没命中时仍是 `no_match` + `insufficient_evidence`、不建待定项。规则表测试覆盖每条通过与不通过的路径。
- [ ] AC7 重新处理：升级后，AcoustID 没有密钥时不重做任何发行；填入密钥后，只有之前“没对上或拿不准且走到了指纹这一步”的发行（旧状态按 `method` 与 `conflicts` 推断，见 design 8.4）被重做一次，在前面各步就拿不准的、已对上的发行，以及封面与歌词的状态不变（集成测试计数）；暂停或扫描开始时不会把状态写成“指纹不可用”。
- [ ] AC8 界面：AcoustID 一行能填写、更换、清除密钥，状态与不生效原因的文案正确；确认框里列出 AcoustID 收到的内容；Vitest 与 Playwright 冒烟通过，新样本由解码器往返无损。
- [ ] AC9 现有接口样本除外部源列表（多一项 AcoustID）外逐项不变。

## 范围外

- 指纹提交（向 AcoustID 贡献指纹）：需要每个用户自己的用户密钥，与“后台只读”无关。
- 按标签里的 AcoustID 编号查询（`lookup?trackid=`）：带这种标签的文件几乎都同时带 MusicBrainz 录音 ID，第 1 步已经能对上；以后需要时再加。
- 后台为全部曲目预先算指纹：只在匹配走到指纹这一步时按需计算（见“代为决定的事项”第 3 条）。
- 拿不准之后的模型判断：子任务 D。

## 主代理代为决定的事项

用户 2026-11-22 授权能自己定的自己定。以下与父任务原计划不同或原计划没写的，逐条记理由：

1. **用上游官方的静态 `fpcalc`，不用 Alpine 的包。** 父任务 U8 授权“在生产镜像里增加 Chromaprint”，形式没定。Alpine 的包会让镜像大约 40%（约 100 MiB），而且是第二份 FFmpeg；
   官方静态构建只多约 5 MB，开发机也能直接运行（与固定的 ffmpeg 一样取一次、缓存在用户目录），按 sha256 固定后来源与可重复性都不差。
2. **不移植 chromaprint 到 Go。** 位精确的移植可行，但会把 LGPL 代码静态链接进项目的二进制，项目没有许可证，合规上说不清；单独的程序与现有 ffmpeg 的处境相同。
3. **按需计算、按曲目缓存，不另起后台任务。** 父任务写的是“照音频分析的形状”。指纹只在前五步都没命中时才需要，大多数带标识的专辑永远用不到；
   按需算一首不到一秒，缓存保证音频不变就不重算。另起一个全库扫描的工作者既费 CPU，又要再加一套进度与让路逻辑。取源方式仍照音频分析。
4. **不加规则版本，改为记“指纹这一步是否被跳过”。** 父任务写“规则版本加一”，但 C 的规则版本一变就重做全部状态（含已对上的、封面、歌词），而加入指纹不会改变任何已对上的结论。
   按“走到了这一步却因为不可用而跳过”精确地重开，同一个机制也覆盖了“以后才填密钥”的情况；规则版本加一做不到后者。
5. **AcoustID 默认开**（与其余三个源一致），没填密钥时显示 `key_missing`；用户只需要填密钥，不必再去开一个开关。
   这与 ADR 0006 第 8 节源表的“默认关”不同，按 U8 的原话“在管理员填入应用密钥后启用”改，ADR 追加决策记录。
6. **保存密钥时不去 AcoustID 验证。** 总开关关着时承诺不向外部发任何请求；密钥是否有效在第一次真正使用时知道，界面显示 `key_invalid`。
7. **指纹结果的分数门槛 0.9**，低于它的结果不参与判定；专辑抽样与 ISRC 相同（至多 4 首：首、三分之一、三分之二、末），至少一半抽到的曲目算出了指纹才走这一步，
   抽样 ≥ 2 首时至少 2 首有结果才可能对上；暂时性原因导致算不出的，发行记“稍后再试”。
8. **标题与艺人都对不上时仍算相反证据**（与条码、编号、ISRC 相同）：音频相同而标签完全不同，多半是翻译、音译或合辑，交给模型。宁可多交给模型。
9. **指纹缓存放在数据库**（ADR 0006 写的是数据目录、不进备份）：只为走到指纹这一步的曲目按需计算，量小；外键随曲目删除，有效性判断与音频分析一致。ADR 追加决策记录。
10. **密钥用行内输入**（照管家的模型密钥），不另开对话框；AcoustID 一行不提供“撤销来自它的改动”，因为经它对上的对应记在 MusicBrainz 名下。

11. **AcoustID 要两把密钥**（实施中发现，design 8.9）：上游 2026-11-19 公告 2027-01-01 起查询必须带用户密钥。管理员填应用密钥与用户密钥，两把都填了才可用；
   仓库仍不内置密钥。若以后项目以自己的名义注册 AcoustID 应用，可改为内置应用密钥、只让管理员填用户密钥（上游推荐的形态），需要维护者注册，留给用户决定。

## 规划结论的确认方式

路线：子代理审阅（用户 2026-11-22 的常设授权）。审阅者：规划子代理（Plan，opus，2026-11-23）。
结论：必须改 10 项（摘要不得加字段、旧状态重开条件过宽、信息不足会生成空待定项、可用性判断要分错误码、请求基础要加 POST、唯一的密钥存储与依赖规则、包的划分、管道要可定位、与 ADR 0006 的两处差异、集成测试命名），改完后可以实施。主代理全部采纳，建议改 10 项也全部采纳；修订写在 design.md 第八节，与前文冲突时以它为准。
