# UPnP/DLNA 设备发现与单设备串流（U3）

父任务 `11-24-m8-devices-artists-plugins`，决定 W6（首批只做 UPnP/DLNA 渲染器）。调研：`research/repo.md`（仓库现状）、`research/protocol.md`（协议与生态）。
技术设计见 `design.md`，执行顺序见 `implement.md`。

## 目标

ROOMusic 能找到局域网里的 UPnP/DLNA 渲染器（功放、串流器、音箱、电视、Kodi、手机上的渲染器应用），
把它当作一台播放设备：在设备列表里选中它，队列就由服务端渲染后推给它播放；播放、暂停、跳转、下一首、音量都在 ROOMusic 里控制。

用户价值：不用把手机或电脑接到音响上，服务端直接把无损流送到家里的音响设备；音效处理（采样率转换、均衡、卷积）照样生效。

## 现状

- 服务端播放区已是“服务端渲染、输出端拉流并回报进度”的结构（`zones`、`playback/render`）；跨曲目在一条连续长流里完成（无缝、交叉渐变）。
- 输出端目前只有浏览器；设备 `kind` 允许 `browser`、`native`。
- 流只认 Cookie、只能取一次、HEAD 405、不支持 Range；没有免 Cookie 的流地址。
- 出站请求没有“只允许局域网地址”的策略。
- 生产 Compose 是 bridge 网络，收不到 SSDP 组播；开发后端在宿主机运行，可以直接发现。
- 播放区只属于本人；没有“局域网共享设备”的概念。

## 需求

- R1 开关：管理员在设置里打开“局域网设备”（默认关）。关闭时不发 SSDP、不连任何设备，行为与现在相同。
- R2 发现：打开后定期 SSDP 搜索 MediaRenderer 并监听公告；设备上线、下线、改名能反映出来。管理员也可以手动输入设备地址（IP 或描述文件网址）添加。
- R3 共享与占用：发现到的设备对所有成员可见。一台设备同一时刻只为一个播放区播放；别人正在用时，可以确认后接管，原播放区暂停。
- R4 播放：选中设备后，播放区的连续长流推给设备（`SetAVTransportURI` + `Play`）；暂停、继续、跳转、下一首、换队列、改音效设置都按现有播放区命令生效。
  格式变化或跳转时重新推送新流。设备上的播放进度回到播放区（进度条、播放记录、事件）。
- R5 设备端操作：在设备自带的遥控或面板上暂停、继续、停止，播放区能看到并跟着变化；设备端跳转、上下首不支持（文档写明）。
- R6 格式：设备支持 FLAC 时用 FLAC，否则 WAV；采样率与位深上限默认 48 kHz / 24 位，可在设备菜单里改为 44.1、48、96、192 kHz。DSD 一律转 PCM。
- R7 音量：设备有音量控制时，ROOMusic 的音量滑块控制设备音量；没有时显示为固定音量。
- R8 流地址：设备通过不带 Cookie 的一次性令牌地址拉流，令牌只在这条流有效期间可用；HEAD 请求和断线重连可用（重连从当前位置续流）。
  服务端给设备的地址取自新配置 `ROOMUSIC_LAN_URL`；没设时用发现该设备的本机网卡地址加监听端口。
- R9 安全：只连 SSDP 响应来源地址上的描述文件与控制地址（主机必须一致），或管理员手动添加的地址；只允许局域网私有地址，拒绝回环与公网；
  令牌地址的错误请求限速。成员被停用或会话全部吊销时，他占用的设备停止播放。
- R10 部署：默认 Compose 不变（bridge 下可手动添加设备，需设 `ROOMUSIC_LAN_URL`）；提供 host 网络的 Compose 覆盖文件，用它时可以自动发现。部署文档写明两种做法。
- R11 前端：设备列表里 UPnP 设备有自己的图标与“局域网设备”标注；占用中显示占用者并可接管；设备菜单里有采样率上限；设置里有开关与手动添加。
- R12 开发与测试：一个假渲染器程序（SSDP 公告、AVTransport/RenderingControl/ConnectionManager、按实时拉流并计时），开发时没有真实设备也能走通。

## 验收

- A1 开关关闭：不发 SSDP、不开新端口，既有接口样本与测试结论不变。
- A2 假渲染器：打开开关后 10 秒内出现在所有成员的设备列表里；停掉后按 max-age 或 byebye 下线。
- A3 播放：选中假渲染器播放一张专辑，跨曲目连续；进度条前进；播放记录按现有规则计次；暂停、继续、跳转、下一首生效；音效设置生效（流的采样率与设置一致）。
- A4 设备端暂停与停止反映到播放区；设备离线时播放区按“输出离线”处理（暂停）。
- A5 占用：成员 A 播放中，成员 B 看到“占用中”；B 接管后 A 的播放区暂停、B 开始播放。
- A6 令牌：无令牌或过期令牌 404；HEAD 不消耗流；重连续流；令牌只对应一个播放区的一条流。
- A7 SSRF：LOCATION 指向与响应来源不同的主机、回环、公网地址时不请求；控制地址跨主机时拒绝。
- A8 成员停用后其占用的设备停止。
- A9 部署：`compose.prod.yaml` 与 host 覆盖文件通过 Compose 配置检查；文档给出 `ROOMUSIC_LAN_URL` 的写法。
- A10 前端：设备列表、占用与接管、采样率上限、设置开关与手动添加在 390 与 1440 两种宽度下正确。
- A11 真实设备试用：由 qlqq 在家里的设备上试一次（不阻塞合入，结果记入任务）。

## 不做

- Chromecast、AirPlay、Sonos 专用协议、Snapcast。
- 多设备同步播放、设备分组。
- GENA 事件订阅（用轮询）；`SetNextAVTransportURI`（连续流不需要）。
- IPv6 发现。
- 设备端跳转、上下首映射回播放区。
- DSD 原生或 DoP 输出。
- 作为 UPnP 媒体服务器（被别的控制点浏览曲库）。

## 规划决定

路线：人工选择，qlqq 于 2026-11-24 预先授权“规划完直接实现”（父任务 W1）；W6 由 qlqq 选定，其余默认值由主代理取定，交付时列出。

| 编号 | 决定 | 理由 |
| --- | --- | --- |
| K1 | 默认部署不变；自动发现靠 host 网络覆盖文件，bridge 下手动添加 | 改动现有实例的网络模式会影响端口发布与数据库地址，不应默认发生 |
| K2 | 管理员开关，默认关 | 打开后会在局域网发组播、连设备 |
| K3 | 设备对所有成员共享，一次只服务一个播放区，可确认后接管 | 家里的音响是共用的；接管比排队更符合实际用法 |
| K4 | 连续长流，不用 `SetNextAVTransportURI` | 现有渲染已在一条流里完成跨曲目；多数设备的“下一首”不可靠 |
| K5 | 状态靠轮询（播放时每秒），不做 GENA | 播放位置本来就只能轮询；事件订阅在不少设备上有格式问题，还需要设备能反连回调地址 |
| K6 | 默认 48 kHz / 24 位，可调 | GetProtocolInfo 判断不了采样率；48k 是多数设备都能接受的上限 |
| K7 | 只连 SSDP 响应来源主机上的地址 | LOCATION 不可信，防止被用来访问内网其他服务 |
| K8 | 用 huin/goupnp（BSD-2）做 SSDP 与 SOAP | 维护中，含 AVTransport1 等生成代码；自己写只省一个依赖 |
| K9 | 新配置 `ROOMUSIC_LAN_URL`，不复用 `ROOMUSIC_PUBLIC_URL` | 生产禁止后者；局域网地址与外部反代地址本来就不同 |
