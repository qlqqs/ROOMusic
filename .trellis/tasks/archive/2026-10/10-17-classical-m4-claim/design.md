# M4 认领：技术设计

需求与裁决见 [prd.md](prd.md)，执行计划见 [implement.md](implement.md)。本文写的是实现方式，需求以 PRD 为准。

## 1. 边界与能力归属

- **catalog** 拥有全部业务规则：待认领的判定、推荐、预览、认领的执行器与它的撤销和展示（`operations.Kind`）。要迁移的四类人工状态都在 catalog 的表里：
  `release_corrections`、`releases.group_id`、`release_groups.default_release_id`、`release_issue_reviews`。
- **operations** 增加一种操作类型 `release_claim`，`Run` 与 `RevertExecutor` 不改；记录列表增加一个筛选条件 `Sources`（第 7 节）。
  目标类型仍是 `release`，目标是**新版本**；旧版本的 ID 与状态写在记录的前后状态里。
- **扫描不变**：扫描照旧只写扫描列与证据，不读写修正、核对、组行与操作记录，这个结构保证不变。认领只在管理员提交时发生，没有自动认领。
- **governance 前端**新增“待认领”页与认领流程；专辑详情里的提示与“查看问题”放在同一个管理员操作区（app 组合）。

## 2. 待认领的判定

**旧版本（待认领）**：发行行存在、**不可见**（`releaseVisiblePredicate` 为假：没有 present 曲目），并且至少留有下列一项**人工状态**：

1. 有 `release_corrections` 行；
2. 所在的组里有**别的发行**（不论可见与否）。扫描从不把新发行放进已有的组，所以组里有别的发行只可能来自人工归组；
3. 是某个组的 `default_release_id`（失效中的默认版本也算）；
4. 有 `release_issue_reviews` 行（过期的也算）。

第 2 项看“有别的发行”，不看“有别的可见发行”。这样同一张专辑的两个版本都被整张替换之后，先认领一个，另一个仍能认领回这张专辑。

**新版本（认领目标）**：任意**可见**的发行，不是旧版本自己。

认领成功后，旧版本的四类状态都已移走或清除（第 5 节），它不再满足判定，从列表消失。文件回来、旧版本又可见时，它也不再待认领（K5）。
判定写成一个 SQL 谓词常量 `releaseClaimablePredicate`（`claims.go`），列表、详情、预览与执行器共用，与 `issues.go` 的做法相同。

## 3. 推荐（只读，规则固定）
推荐只决定排序与提示，不自动执行。依据是**文件路径与目录**；规则（路径集合、两个理由码、排序、上限 5 个、索引与边界）在[认领合同](../../../../spec/backend/claim-contracts.md)第 4 节，这里只记决策与取舍：

- 旧版本的路径集合除了名下曲目的路径，还要包括归组依据 `source_refs`（最多 100 条）：新增文件使原有曲目整体改挂走之后，旧版本名下一首曲目都不剩，只有这一行还记得它最后的文件清单。
- 比较的是候选的 present 曲目，旧曲目是否还持有来源身份取决于情形，不影响结果。`same_directory` 没有可用的索引（`releases_source_directory` 已在迁移 0010 删除），只在打开详情时算一次，规模变大再加索引。
- 没有候选时只提供手动搜索（K1），复用“归入其他专辑”的专辑搜索：先选专辑，多个版本时再选其中一个，别的目录、别的 root 都能选到。
- 专辑详情的提示（K4）用同一组条件反过来查：先列出待认领的旧版本（很少），再逐个检查当前版本，不从当前版本出发反查整个库。
- **真实扫描核对过的事实**（`TestPostgreSQLClaimCluesSurviveARealRescan`，合成 FLAC）：原地替换（旧曲目留在原路径、标为缺失并失去来源身份）、新增文件 2 首加 3 首（旧发行名下一首不剩）、
  目录不变而文件名与内容都换了（只命中 `same_directory`）。**单纯改名不新建发行**（扫描按内容指纹重绑定），不属于认领。
- 音频指纹不在依据里。跨 root 移动、目录与文件名都改了的情形推荐不出来，只能手动搜索（PRD“已接受的限制”）。

## 4. 数据模型（迁移 0020）

只放宽操作类型约束，不新增表：

```sql
ALTER TABLE operations DROP CONSTRAINT operations_type_ck;
ALTER TABLE operations ADD CONSTRAINT operations_type_ck
    CHECK (operation_type IN ('release_correction', 'release_group_change', 'release_group_default',
                              'release_issue_review', 'release_claim', 'revert'));
CREATE INDEX operations_claim_source_index ON operations ((after_state #>> '{source,release_id}'), created_at DESC, id DESC)
    WHERE (after_state #>> '{source,release_id}') IS NOT NULL;
```

- 不建“认领关系”表。认领之后旧版本上什么都不剩，前后状态完整记在操作记录里，撤销以它为依据；待认领列表由谓词实时算出。
- 部分表达式索引用于“修改记录”与操作记录页同时找到**来源**是某个版本的认领记录与它们的撤销记录（第 7 节）。其他类型的状态里没有 `source` 键，不进这个索引。
- 不写 down 迁移。按 ADR 0002 第十节第 7 项，回退是关闭写入路由、保留数据。

## 5. 认领的写入
`POST /api/v1/releases/{id}/claim`，`{id}` 是**新版本**；请求体 `{expected_revision, source_release_id, source_revision, preview}`。检查顺序、指纹、执行器的步骤与响应见[认领合同](../../../../spec/backend/claim-contracts.md)第 6 节，这里记决策：

- **加锁顺序**：先对旧版本核对行引用的操作记录加 `FOR KEY SHARE`，再按 UUID 升序锁两个发行行，最后按 UUID 升序锁涉及的组行。核对行带着原 `operation_id` 迁到新版本，提交时的外键检查会加同一种锁，
  而撤销那条更早的记录会先 `FOR UPDATE` 锁它、再锁发行行；不先加这把锁就会死锁（核对合同第 5 节）。扫描只更新发行行、从不锁组行，所以不会形成环形等待。
- **`not_claimable` 先于版本号核对**：已经认领过的旧版本不论带什么版本号都是 `not_claimable`。
- **四类全部被跳过时也照样执行**：旧版本的修改被清走、留在记录里，表示新版本已经接替了它，旧版本因此离开待认领列表，撤销可以恢复。没有 `no_changes`：能走到这里的旧版本一定留有人工状态。
- **专辑**：旧版本所在的组有别的发行时，新版本已在那个组 → 不用做；新版本所在的专辑没有别的**可见**版本（单版本专辑）→ 新版本归入那个组（它原来的组变空，按现状保留）；
  有别的可见版本（多版本专辑）→ 跳过（K3）。**旧版本只要组里有别的发行就移进一个新建的空组**，这样它才离开待认领列表；不可见的空组不出现在任何地方，撤销时回到原组。
- **默认版本**：对每个以旧版本为默认版本的组（通常就是原来的专辑）：新版本在其中就接任，否则改回自动选择；旧版本不可见，原来的设定本来就失效，改回自动选择不改变页面上的显示。
- **核对**：依据与原 `operation_id` 原样复制（核对人与时间不变），有效性仍在读取时判断（K2 第 ④ 点）；字段修正则写本次操作的 ID。**缺失曲目的核对不迁移**：它的依据是旧版本自己的曲目 ID 与最后一次看到的时间。
- 记录的 `expected_revision` 与 `result_revision` 是**新版本**的（`Outcome` 只有一对版本号，撤销规则以目标为准）；旧版本与各组的版本号写在前后状态里，撤销时一并核对。
- 响应的 `group_id`/`previous_group_id` 是新版本认领之后与之前所在的组（“打开这张专辑”用前者），`moved`/`skipped` 是 `{corrections, album, reviews}`，默认版本单列 `defaults: {moved: [组 ID], reset: [组 ID]}`。

## 6. 预览
`GET /api/v1/releases/{id}/claim-preview?source=<旧版本 ID>`（只有管理员，不加锁）。每一项的类别、去向、跳过的原因与核对的三种效果（`valid`/`stale`/`no_issue`）见[认领合同](../../../../spec/backend/claim-contracts.md)第 5 节，这里记决策：

- 预览与执行器共用纯函数 `buildClaimPlan`，按同一份状态快照得出每一项的去向，所以“预览写的就是执行的”是结构保证。
- **核对的效果是三态**：最初只有 `valid` 布尔，“新版本现在没有这类问题”会被写成“会重新提醒”，而根本没有问题可提醒，所以拆成 `valid` / `stale` / `no_issue`。
- **令牌只含来源与目标的 ID 加每一项的去向**（类别、字段或问题、专辑、去向、原因），不含标题和展示字段，也不含 `effect`。两个发行的修正与核对只能被受治理写入改变，每次改变都让版本号加一，版本号另行核对，所以不必进令牌；
  令牌要拦住的是不改变这两个版本号的变化：扫描改变了成员关系，以及别人改了以来源为默认版本的专辑（只让专辑的版本号加一）。令牌绑定具体的一对版本，拿别的版本对的令牌来提交得到 `claim_changed`。
- 预览只读、不加锁。页面打开到提交之间状态变了，由令牌和版本号拦下。

## 7. 撤销与操作记录
`ClaimOperations()` 实现 `operations.Kind`，由 `app` 注册。完整规则见[认领合同](../../../../spec/backend/claim-contracts.md)第 7 节，这里记决策：

- **撤销前态而不是反向操作**：先对前态引用的更早记录加 `FOR KEY SHARE`，再按第 5 节的顺序锁两个发行行和前态里的各组；新版本的版本号、旧版本的版本号、各组的版本号任一与记录不等就是 `revert_conflict`，不做部分撤销。
  认领时新建的空组不在前态里，不锁、不核对，撤销之后留着无害。
- **撤销不要求新版本可见**：认领之后新版本又被整张替换、变得不可见时，撤销仍能把人工状态还给旧版本。这与其他类型（目标不可见就 404）不同，因为这种撤销的目的就是把修改还给另一个版本。
- **Describe 的来源标题取记录里的名字**：认领记录用认领之前的有效标题（用户认领时认得的那个名字），撤销记录用恢复之后的；`visible` 才取现在的状态。认领会把旧版本的修正清走，
  现在的有效标题已是扫描值，若取现在的，操作记录里的名字就和用户认领时看到的不一样（真实服务用例发现）。
- `moved` / `skipped` 由记录的前后状态推导，不另存；专辑只给数量（页面说“接任了 N 张专辑的默认版本”），不为每条记录再查专辑。**撤销记录只带 `kind` 与 `source`。**
- **按来源筛选**：`operations.ListParams.Sources` 按 `after_state #>> '{source,release_id}'` 匹配，走迁移 0020 的部分索引，与 `Targets` 取并集，所以“修改记录”同时列出以某个版本为来源的认领。
- **与其他记录的关系**：认领之后，被移走的修正与核对的原记录目标仍是旧版本，旧版本的版本号已变，所以它们不能再单独撤销（`revert_conflict`），与“只撤销最近一次修改”一致。

## 8. 读取接口（只有管理员）
三个读接口（待认领列表、一个旧版本的详情、专辑详情用的提示）的响应与检查顺序见[认领合同](../../../../spec/backend/claim-contracts.md)第 8 节，这里记决策：

- 列表按最后一次被看到的时间倒序（K5）：名下曲目 `observed_at` 的最大值；名下没有曲目时取归组依据的 `observed_at`，都没有时取发行的创建时间。没有接替者的会沉到后面。
- 标题用有效值：有修正时就是修正后的名字，这正是管理员认得出的名字。`album.title` 是**不含旧版本自己**的成员里按代表版本规则排第一的有效标题（它自己的名字已显示在行的标题里），可见成员优先。
- `root_name` 取扫描目录路径的末段（`library_roots` 没有 `name` 列，与扫描目录列表一致），不返回绝对路径；`directory` 经 `SafeRelativeSourceRef`，不安全的是空串。
- 同一张专辑里的几个旧版本各自一项：先认领一个，另一个仍能认领回这张专辑。推荐只在详情里算，列表不算。
- `claim-hints` 命中条件与推荐相同，但不受推荐 5 个的上限限制，最多 3 个。

## 9. 前端（governance）

- 路由 `/claims`（`AdminGate`）。导航“资料库”里，在“元数据问题”之后加“待认领”，不显示数量。地址参数是 `page` 和 `release`（选中的旧版本，UUID）。
- **两栏与顺序导航**：沿用问题页的结构与 `useContainerWide`。容器宽于 900px 时两栏（列表 380px，详情最宽 860px）；更窄时先列表后详情，详情里有“返回列表”。
- **列表行**：是链接（选中写进地址，当前项带 `aria-current`，与问题列表相同）。写旧版本标题；原来的专辑（和别的版本同在一张专辑里时写“原来在《…》的专辑里”）；
  `root_name / directory`；最后一次看到的时间；留着的修改（如“修正 3 项 · 专辑 · 默认版本 · 核对 1 项”）。链接只改 `release`，页码保留。
- **详情**：
  - 留着的修改分节列出：字段修正（字段、你改成了什么、扫描值）、所在的专辑（同专辑的别的版本，可见的是链接、不可见的写“（已不可见）”；是哪张专辑的默认版本）、
    问题核对（问题、核对人、核对时间；核对人已不存在时写“（用户已不存在）”）。没有的节不出现。
  - “可能接替它的版本”是带封面的列表：标题（链接，打开它的专辑页看看）、艺人、年份、版本说明和理由的文字（如“同样的文件（12 个）”“同一目录”）。
    选择它（单选）、预览与认领在第 6 步加入。
  - 下面是“搜索其他版本”：先按标题、艺人或曲目名搜专辑（与“归入其他专辑”同一个搜索），再在专辑里选版本；结果也是单选列表。
  - 选中版本后显示**预览**（第 6 节的逐项列表：会迁移的、保留新版本的及原因、改回自动选择的专辑），按钮是“认领到《…》”。
  - 不弹二次确认：预览就是确认，结果也可以撤销。成功后就近提示“已把《旧》上的修改认领到《新》：修正 …；专辑；默认版本；核对 …”，带“撤销”和“打开这张专辑”；
    新版本已有而保留的另起一句，默认版本改回自动选择的另起一句，什么都没迁（新版本已有的都保留了）时说明新版本已经接替了旧版本。提示放在详情上方，
    不限定在某个版本的详情里（认领之后旧版本的详情就变成“不需要认领”的说明了）。
- **专辑详情的提示**（K4）：`claim-hints` 不为空时，管理员操作区在按钮行与结果提示之间显示低调的一行“可能接替了已不可见的《…》”加链接“查看并认领”，
  链接到 `/claims?release=<旧版本>&target=<当前版本>`：旧版本选中，当前版本已预选，预览直接出现。线索读取失败不重试、不提示，页面照常。
  选中的新版本（`target`）写进地址，用替换历史项的方式更新；换旧版本时清掉它；没有选中旧版本时它没有意义，解析时丢弃。
- **命令**：`useReleaseCommands` 增加第七种意图 `claim`：`release` 是新版本，另带 `source`、两个版本号和预览令牌。
  遇到 `claim_changed` 或 `revision_conflict` 后重新读取详情与预览；结果不确定时用同一个键重试。撤销沿用 `revert`，`subject` 增加 `"claim"`；
  从记录撤销认领之后页面跟着新版本回到认领之前所在的组，与撤销归组相同：用记录改动摘要里的 `previous_group_id`（认领记录的摘要带它，撤销记录不带）。
  认领只在待认领页发起，那里不跟随版本的移动，成功提示里的“撤销”也就不需要带它。
- **操作记录**：类型名是“认领”。改动行写“从《旧标题》（已不可见）认领：修正 3 项、专辑、默认版本、核对 1 项”；跳过的项另起一行：“保留这个版本已有的：标题”。
  不能撤销的原因（`notRevertibleReason`）对认领单独判断：认领不要求可见，所以不写“专辑已不可见”，只写“之后又有修改”（任一方又被修改过）。
- **可访问性**：
  - 列表是带名称的链接列表（选中写进地址）；推荐的版本在选择时是带名称的单选组。
  - 预览是带标题的列表，“会迁移”与“保留”用文字区分，不只靠颜色。
  - 提交后焦点落在结果提示上。这是问题处理留下的教训：按钮被替换后，焦点不能掉到 `body`。

## 10. 与扫描、其他操作的关系

- 扫描不读写认领涉及的四类人工状态。所以认领之后重扫：修正按视图继续生效，归组与默认版本保持，核对在依据相同时仍有效。这是结构保证，由真实重扫用例守住。
- 旧版本文件回来（又可见）时，它身上已经没有人工状态，自己是一张单独的专辑。它与新版本是两个可见版本，各自显示扫描值与各自的修改。撤销认领可以把修改还给它。
- 认领后的新版本可以照常修正、归组、核对、设为默认版本。做过这些新修改之后，认领就不能再撤销（`revert_conflict`）。

## 11. 错误码（新增）

| 条件 | 响应 |
| --- | --- |
| 旧版本现在可见，或已不再留有人工修改 | `409 not_claimable` |
| 预览令牌与现在的不同（页面打开之后有扫描或修改） | `409 claim_changed` |
| 新版本与旧版本相同 | `400 invalid_input` |

其余错误码与受治理操作合同第 8 节相同：401、403、400、`404 not_found`、`409 revision_conflict`、`idempotency_conflict`、撤销的各种 409、`503`、`500`。

## 12. 迁移、兼容与回退

- 迁移 0020 只放宽约束、建一个部分表达式索引，不改写数据。没有认领记录时，所有既有接口与页面的输出逐项不变（接口样本门禁）。
- 回退：关闭认领的写入路由与页面入口。已做的认领保留：数据都在既有的表里，记录照常可读。

## 13. 取舍

- **不建认领关系表，推荐用现有线索**：扫描不能写治理表；成员增加时，旧版本名下的曲目已经改挂走了，只有归组依据的路径还记得它最后的文件清单。
  代价是最多 100 条，CUE 等情形下路径可能对不上（推荐少一些，有手动搜索兜底）。
- **目标是新版本，一次认领一条记录**：与“只撤销最近一次修改”的规则对齐。旧版本与各组的版本号写进状态一并核对，不做部分撤销。
- **专辑关系看“组里有别的发行”**：会多列出一些成员全都不可见的组，好处是同组的多个旧版本可以逐个认领回同一张专辑。
- **认领后旧版本移进新建的空组**：只有这样它才会离开待认领列表；不可见的空组不出现在任何地方，撤销时回到原组。
- **不做放弃（K5）**：没有接替者的旧版本留在列表里，按最后一次看到的时间沉到后面。

## 14. 已知限制

- 推荐只看文件路径与目录。目录与文件名都改了（含跨 root 移动）的版本推荐不出来，需要手动搜索。
- 认领之后，被移走的修正与核对的原记录不能再单独撤销（旧版本的版本号已变）。
- 归组依据的路径最多 100 条，超出部分的文件不参与推荐。
- 旧版本的专辑关系以它现在所在的组为准。同一张专辑的几个版本先后被替换，而前一个的新版本没有进入这张专辑（它已在别的多版本专辑里）时，
  后面的旧版本可能看不出原来的专辑关系，需要认领之后手动归组。
