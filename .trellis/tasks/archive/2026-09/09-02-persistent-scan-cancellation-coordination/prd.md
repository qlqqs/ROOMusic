# 持久化扫描取消与跨进程协调

## 目标

让管理员可以可靠地停止长时间运行的音乐库扫描，并保证多个 ROOMusic
进程不会并发执行相互冲突的全库扫描。取消、进程退出和协调失败都不能把
未访问的音乐误判为缺失；管理员能够从可解释的终态判断是否需要重新发起扫描。

## 用户价值

- 长时间扫描可以由管理员从浏览器或 REST 客户端请求停止，客户端断开不影响
  已写入数据库的取消意图。
- 多实例部署不会因为各自的进程内锁而重复遍历同一音乐目录。
- 发生崩溃、数据库连接丢失或执行权失效时，系统宁可报告
  `incomplete`，也不把未验证的来源标记为 `missing`。

## 背景与证据

- `roomusicApplication` 目前只用进程内 `scanMutex` 和 `runningScan` 防止重复启动，
  多个进程仍可各自创建 `running` 行并遍历目录（`backend/cmd/roomusic/application.go:17-23`、
  `backend/cmd/roomusic/scans.go:17-30`）。
- 扫描 goroutine 使用 `context.Background()`，虽然状态枚举已有 `canceled`，
  但没有持久化取消意图或用户取消端点（`backend/cmd/roomusic/scanner.go:33-57`）。
- 启动时 `recoverInterruptedScans` 无条件把所有 `running` 行改成 `incomplete`，
  会误伤另一进程正在执行的扫描（`backend/cmd/roomusic/database.go:68-82`）。
- `markMissing` 当前按 root 分开提交，并在终态行更新前执行；中途崩溃可能留下
  部分负向对账（`backend/cmd/roomusic/scanner.go:395-401`）。
- 现有数据库状态为 `running | succeeded | failed | canceled | incomplete`，
  PostgreSQL 是唯一业务权威（`backend/migrations/0002_core_slice.sql:26-32`、
  `.trellis/spec/backend/core0-runtime-contracts.md:41-64`）。

## 需求

- **R1 持久化取消**：管理员可以对指定活动扫描发出取消请求；取消意图写入
  PostgreSQL，而不是只保存在 HTTP 请求或单个进程内存中。重复取消必须幂等，
  终态扫描不能被改回 `canceled`。
- **R2 协作式停止**：执行器以可取消上下文和有界检查点观察取消意图，停止
  遍历新的文件，并把正常观察到的取消收敛为 `canceled` 与完成时间。取消请求
  本身不等待整个扫描 goroutine 结束。
- **R3 全局单任务**：PostgreSQL 同时承担扫描状态和执行权；多个独立实例并发
  启动时最多一个实例获得执行权。没有等待队列，也不自动接管另一个实例的扫描。
- **R4 活动任务复用**：已有活动扫描时再次启动返回同一个 `scan_run_id`，不创建
  第二条排队记录或第二次目录遍历。
- **R5 人工恢复**：执行进程异常退出、持有执行权的连接失效或协调资格丢失后，
  遗留 `running` 记录在持有协调资格的恢复路径中收敛为 `incomplete`；不会自动
  接管、断点续扫或隐式创建替代 worker。管理员必须显式重新发起。
- **R6 负向对账安全**：只有完整成功的 `succeeded` 扫描可以执行 `missing` 对账。
  `canceled`、`failed`、`incomplete`、协调失败及任何未完成根目录均不得改变
  已有来源的缺失状态；取消前已提交的合法观察可以保留。
- **R7 跨层合同**：启动、查询、取消、竞争、异常恢复和终态写入具有稳定的
  REST 响应/错误码、结构化日志和 PostgreSQL 集成测试；后台操作不因客户端
  断开而自动取消。
- **R8 管理界面**：管理员在现有扫描界面看到启动、正在运行、取消请求中、已取消、
  失败和不完整等服务端状态，并可重试失败的取消请求；普通用户不显示管理操作，
  后端仍对每次请求重新鉴权。
- **R9 兼容边界**：音乐根目录保持只读；不引入 Redis、通用任务队列、工作流引擎、
  播放能力或前端全量拆分作为本任务依赖。既有成功扫描、状态查询、诊断、Release
  浏览和目录安全合同继续有效。

## 验收标准

- [ ] 管理员取消活动扫描后，数据库的持久化取消字段可查询；重复取消返回同一
      扫描标识和取消请求时间；普通用户、匿名请求分别得到稳定的 403/401。
- [ ] 执行中的扫描观察到取消后停止开始新的文件遍历，最终状态为 `canceled`，
      `finished_at` 已写入；取消请求的 HTTP 响应不被误当作终态证明。
- [ ] 两个独立应用实例同时启动扫描时，只有一个实例持有数据库执行权并遍历目录；
      另一个请求不会创建第二个 `running` 行，活动任务可复用同一 `scan_run_id`。
- [ ] 启动恢复在无法取得协调资格时不会更新其他实例的活动 `running` 行；取得资格
      后遗留行收敛为 `incomplete`，且不会自动启动替代扫描。
- [ ] 取消、失败、执行权/连接丢失和不完整扫描均不运行 `missing` 对账；成功终态
      的所有 root 对账与 `succeeded` 写入要么一起提交，要么一起回滚。
- [ ] 启动/取消竞争、重复取消、终态后取消、跨实例锁竞争、恢复保护、连接池边界、
      取消检查点和终态事务崩溃窗口均有自动化测试；并发代码通过适用的 race 检查。
- [ ] 管理员从现有界面请求取消并能看到服务端的“取消请求中”和最终 `canceled`；
      取消失败显示可重试错误，刷新页面后仍能从服务端恢复活动扫描状态。
- [ ] 既有登录/权限、成功扫描、状态查询、诊断、Release 浏览、目录只读和错误
      envelope 测试保持通过；新增字段为向后兼容的加法。

## 范围外

- Redis 或其他外部任务队列、通用后台作业平台、优先级队列、定时扫描和任意任务编排。
- 多扫描排队；已有活动扫描时只复用现有任务。
- 扫描断点续传、自动接管或从中断文件位置继续执行。
- owner/lease/heartbeat/fencing 的完整租约状态机；若未来需要应用存活期间的严格
  TTL 或可验证接管，另立任务评估该方案。
- 真实音频播放、M4A/ALAC 扩展、Meilisearch、Agent runtime 和前端全量
  feature/router/query-cache 重构。

## 关键决策

- **恢复策略**：异常退出或协调资格失效只标记 `incomplete`，由管理员手动重新发起；
  不自动接管或断点续扫。这样优先保证负向对账安全和恢复可解释性。
- **协调路线**：规划采用“专用 `database/sql` 连接持有 PostgreSQL session advisory
  lock + 持久化取消字段 + lock-aware 恢复”，暂不引入完整 lease/fencing 状态机。
  该路线与当前边遍历边短事务写入模型兼容，且不增加 Core 0 的外部基础设施依赖。
- **终态竞争**：活动 worker 和取消请求都通过锁定 `scan_runs` 行的终态事务线性化；
  只有仍为 `running`、没有取消请求且所有根目录完整时才允许 `succeeded`。
- **规划决策路线**：采用人类选择；选择者为项目负责人 `qlqq`。选择依据是先守住
  扫描安全边界和可解释恢复，再控制 Core 0 的实现复杂度。该选择只完成规划评审，
  不等同于实现批准。

## 风险与延期事项

- session advisory lock 没有严格 TTL；网络分区且 PostgreSQL 尚未检测到断开时，
  `running` 可能暂时保持。运行合同须说明只有数据库恢复检查或管理员显式启动才会
  触发人工收敛。
- 持有锁的专用连接会占用一个连接池槽位；实现必须避免 `MaxOpenConns=1` 导致
  worker 与状态/取消请求互相等待，并覆盖该边界测试。
- 旧版本二进制不认识新锁和取消字段，滚动期间可能破坏单任务保证；发布时需先
  完成兼容迁移并避免新旧扫描执行器并存，回滚以停机/forward-fix 为准。
