# M0：Classical 设计定稿与规范清理

## 目标与用户价值

为[Classical 重设计 / Core 1](../../../09-27-classical-core-1/prd.md)建立可靠的实施依据：
让后续执行者明确哪份设计生效、哪些能力已经存在、哪些仍待批准，以及先实现什么。
M0 只整理文档、规范和决策提案，不实现界面或后端功能。

## 启动时事实（2026-09-27）

- Classical 原型和设计系统已位于 `frontend-desgin/`，其 `github.md` 明确尚未对齐 `frontend/DESIGN.md`。
- 前端源码和设计指南缺失，但现有规范仍描述旧月刊视觉、hash 路由和模拟播放。
- 后端有认证、目录、扫描和 Release API；不能据此认定原型中的整理、通用审批或播放已可用。
- 详细事实、定位和候选调整统一记录于[基线记录](research/baseline.md)。

## 需求与验收

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| R1 | 建立 Classical 设计锚点 | `frontend/DESIGN.md` 记录原型来源、布局/组件/状态/可访问性约束、设计变量使用规则，以及原型与落地差异；不继续指向不存在的旧设计 |
| R2 | 明确能力和阶段边界 | 有逐页面的“现有 API / 缺口 / 目标阶段”矩阵；Core 0 不变量与 Core 1 范围提案分开，M1 的现有管理写操作不被“只读”误禁 |
| R3 | 清理冲突规范 | 前端索引、目录/状态/播放器规范及相关共享/运行合同不再把已删除源码或旧视觉写成当前实现；保留仍适用的安全、解码和队列语义 |
| R4 | 形成四类 ADR | 前端依赖、修正覆盖层、通用操作记录、ffmpeg/串流各有决策草案，包含证据、方案、取舍、适用阶段、验证/回退和状态；未经确认不得标为已采纳 |
| R5 | 可追溯地承接旧任务 | 记录旧任务与新路线的差异和待迁移交互约定；不把模拟能力视作真实能力，不伪称旧任务已交付；归档操作待单独确认 |
| R6 | 形成可拆分路线 | 父任务映射 M0–M6/B0，M1 与 B0 可独立验收，M4 依赖 M3；新增接口、角色、搜索及个人数据能力不被隐含塞入 M0/M1 |

验收时逐条区分“仓库事实”“候选建议”“用户已批准决策”。四类 ADR 的草案状态可以是
M0 的文档交付结果，但不构成对应业务子任务的实施授权；Core 1 截止范围同理。

## 范围外

- 不写 React/Go 业务代码、SQL 迁移、测试实现或生产构建产物。
- 不安装或升级依赖，不修改锁文件、CI、Compose，不运行真实媒体扫描。
- 不实现播放、元数据修正、审批、ReleaseGroup 聚合、角色扩展或 Steward。
- 不修改/搬迁 `.dc.html`、`_ds`、`support.js` 等设计源文件，不删除历史任务。
- 不写入真实音乐文件，不提交私有音乐路径、凭据和媒体数据。
- 不重新探索四套视觉方向；以本轮已有 Classical 原型为输入，只记录无法直接落地的差异。

## 风险与明确延期

- 范围切分、角色/风险等级、浏览器播放措辞及依赖采纳仍是后续需用户确认的决策；先形成显式提案，不默认批准。
- 依赖版本、浏览器/编解码器兼容性、ffmpeg 部署与许可证要求由 ADR 研究验证，不照搬上一轮建议为事实。
- `candidate_anchor` / `source_identity` 的重扫与身份演进合同需在修正覆盖层实施前验证。
- 设计目录改名、设计工具运行时取舍、旧任务归档均留作独立确认，不扩大本轮创建范围。

## 最终规划决策记录

- 路线：人工选择。
- 选择者：用户（qlqq）。
- 已选结果：用户于 2026-09-27 在最新规划摘要后回复“批准”，确认仅按 R1–R6 开始 M0 文档整理。
- 获批边界：整理文档与决策草案，保留源设计和旧任务；具体产品/技术决策与 Core 1 截止范围仍待后续评审。
- 理由：先消除设计、规范和运行能力之间的冲突，避免后续实现依据失真。
- 状态：人工审阅已通过，准许启动 M0；不授权 M1/B0 或其他业务实施。
