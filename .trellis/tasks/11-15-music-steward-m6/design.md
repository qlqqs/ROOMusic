# Music Steward 总体设计

本文件只写跨子任务共用的结构与合同。各子任务的表结构、接口样本和细节在各自的 `design.md` 里定；
涉及第三方协议与 SDK 的具体写法，在对应子任务规划时查当前文档确定，不在这里凭印象写死。

## 结构

```text
对话页（SSE）──┐
               ├─> 运行时（循环）──> 工具注册表 ──> 现有服务层 / operations.Run ──> PostgreSQL
MCP 客户端 ────┘        │                │
   （访问令牌）          │                └─> 出站：音乐数据源、搜索、网页抓取
                        └─> Provider（OpenAI 兼容 / Messages）──> 模型端点
```

- 对话页和 MCP 是两个入口，共用同一个工具注册表。对话页经过运行时（模型在服务端）；
  MCP 入口不经过运行时，模型在客户端一侧，服务端只暴露工具。
- 权威留在 Go 后端：工具只是现有服务层能力的类型化描述，不含业务规则，不直接访问业务表。

## 包划分

```text
backend/internal/steward/
├── tool/       工具定义、注册表、按主体过滤、调用入口
├── provider/   Provider 接口与两种协议的适配器
├── runtime/    循环、确认与方案、对话持久化
├── httpapi/    对话接口、SSE、设置、令牌管理
└── mcp/        MCP 传输与工具暴露
```

工具的实现由拥有对应业务的包提供，经 `internal/app` 注册给 `steward/tool`，做法与 `operations.Kind`
一致（`backend/internal/operations/kind.go`）。这样 `steward` 不依赖具体业务包，依赖规则测试
（`backend/internal/app/dependency_rules_test.go`）随之增加条目。

## 工具合同

每个工具登记：

| 字段 | 含义 |
| --- | --- |
| 名称与说明 | 给模型和 MCP 客户端看的描述 |
| 输入、输出 schema | JSON Schema；输出有大小上限，超出时截断并说明 |
| 最低身份 | 成员或管理员 |
| 影响范围 | `read`、`personal`（只影响调用者自己）、`shared`（曲库或配置） |
| 可撤销 | 是否经 `operations.Run` 且有逆操作 |
| 输出可信度 | 是否含不可信文本（标签、歌词、网页） |

调用入口对每次调用按当前主体重新鉴权，名称不代表权限。`shared` 工具由调用入口负责确认规则，
工具自身不关心调用来自哪个入口。

## 确认规则

| 影响范围 | 确认模式 | 审查模式（`steward`） | 直接执行模式（`operator`） | MCP 只读令牌 | MCP 读写令牌 |
| --- | --- | --- | --- | --- | --- |
| `read` | 直接执行 | 直接执行 | 直接执行 | 允许 | 允许 |
| `personal` | 直接执行 | 直接执行 | 直接执行 | 拒绝 | 允许 |
| `shared` | 进入方案，用户确认后执行 | 进入方案，审查批准后执行 | 直接执行 | 拒绝 | 允许 |

模式只决定 `shared` 工具的审批路径。鉴权在审批之前：调用者没有权限的工具不出现在工具列表里，
调用也会被拒绝，所以普通成员在三种模式下的实际行为相同。

- 方案是一组待执行的 `shared` 调用，持久化保存。确认绑定方案内容的摘要和过期时间；
  方案内容变化后旧确认失效。执行时每一项仍各自经过后端的 revision 与幂等校验。
- “本次会话内同类操作不再询问”按工具名记在会话上。
- 会话模式记在会话上，操作记录里标明模式；`steward` 模式的记录另带审查运行的标识与结果。

## 审查子代理

- 一次独立的模型调用，有自己的系统提示词，不带主对话的历史；输入是方案和后端生成的证据摘要
  （不是主代理转述的内容），输出是结构化结果：`approved`、`rejected` 或 `needs_human_confirmation`，带理由与风险。
- 批准绑定方案摘要、证据摘要、策略版本和过期时间；任何一项变化都要重新审查。
- 后端只认审查调用返回的结果，不读主代理输出里的任何批准字段。
- 审查调用失败或超时按不可用处理，方案不执行，也不转成直接执行。
- 默认与主代理用同一个端点和模型，可以另选模型。两者同源时独立性有限，这一点写进 ADR。

## 循环

- 一轮：把对话与工具定义发给模型，流式接收；模型要求调用工具时分发执行，把结果送回，重复到模型给出最终回答。
- 有步数上限、单次对话的 token 上限和用户取消；达到上限时停下并说明。
- 遇到需要确认的方案时循环挂起，状态落库；用户确认或拒绝后从落库的状态恢复，不依赖进程内存。
  后台任务（C9）沿用同一机制。
- 不可信文本进入上下文时带明确的来源标记；具体做法由 C1 的 ADR 规定。

## Provider

```go
type Provider interface {
    // 发送对话与工具定义，流式返回文本增量、工具调用请求与用量。
    Stream(ctx context.Context, request Request) (Stream, error)
}
```

两种协议各一个适配器，用标准库的 HTTP 与 SSE 解析实现，不引入厂商 SDK。运行时内部用自己的消息与
工具调用表示，适配器负责双向转换。

端点能力（S13）分两步得出，结果存进设置并可手动修改：

1. 预设：按地址匹配一张常见服务商的表，得到协议、自带搜索的调用方式等已知信息。
2. 探测：保存设置或点“测试连接”时实际请求端点，确认协议、列出模型、用一次带工具的最小请求确认工具调用，
   预设标明有自带搜索时再用一次最小请求确认。探测会产生少量调用费用，只在管理员主动触发时执行。

探测结果与预设不一致时以探测为准。常见服务商的专有接口只在预设里的能力需要时才加适配器。

## MCP

- 传输用可流式的 HTTP，挂在主服务的一个路径下，用访问令牌认证。
- 协议实现用官方的 MCP Go SDK；版本与接口在 C3 规划时查文档确定，并评估它带入的间接依赖。
- 工具列表按令牌所属用户的身份与令牌范围过滤。

## 数据

新增的表（名称与字段在子任务里定）：按用户的管家设置（含显示名字）、全局的成员开关、会话、消息、工具调用、待确认方案、审查记录、记忆、访问令牌。

端点地址由每个用户自己填，服务端会向这个地址发请求。普通成员因此能让服务端访问它所在网络里的地址，
出站请求允许访问哪些地址由 C1 的 ADR 规定。
对话记录与记忆按用户隔离。迁移从 0051 起编号。

密钥与令牌的存放方式由 C1 的 ADR 决定；需要回答的问题是备份文件里会不会包含模型密钥明文，
以及令牌是否只存哈希。

## 前端

新增 `frontend/src/features/steward`：对话面板与完整页面、工具调用过程的展示、确认卡片、设置页里的 Agent 栏目与令牌管理。
按路由按需加载，与管理页的做法一致。流式用 SSE，参照分区事件的现有用法。

- 面板停靠在右侧，宽度用已预留的 `--layout-steward-width`；面板与完整页面是同一个会话的两种显示方式。
- 显示名字存在按用户的设置里，空值表示默认的“管家”。前端从设置接口取一次，侧栏、面板标题、输入框提示共用；
  名字只用于界面显示，不写进工具名、模式名和操作记录。是否写进系统提示词在 C4 规划时定。
- 当前对话用的模型记在会话上，新会话取设置里的默认模型；审查模型只在设置里选。
- Shift+Tab 只在焦点位于输入框时轮换模式，不影响页面其余部分的键盘导航。
- 已确认的静态原型在 `temp/steward-design/`（不入库），C4 实现时以它为准；手机端入口、未配置时的引导、
  出错状态和后台任务的显示原型里没有，在 C4、C10 规划时补。

## 取舍

- 自己实现循环而不用框架：代价是多写一份循环与两个协议适配器，换来确认挂起可以落库恢复、依赖不增加。
- MCP 读写令牌不走服务端确认：依赖客户端的权限提示；用操作记录与撤销兜底。
- 不提供 shell：能力上限是已注册的工具，新需求要先加工具。

## 回退

管家是增量功能：用户没有配置模型端点时只显示配置引导，其余功能不受影响。每个子任务的迁移带 down 脚本。
