# Music Steward 管家（M6）

状态：规划中（父任务）。本文件记录需求、决策、子任务划分与跨子任务验收；总体技术设计见 `design.md`，
子任务顺序见 `implement.md`。父任务本身没有实现工作，不启动；每个子任务单独规划、实施、验收和归档。

## 目标

给 ROOMusic 一个内置的管家（Music Steward）：用户用自然语言提出目标，管家自己决定调用哪些工具、
看结果再继续，直到完成，过程可见。体验参照 Claude Code，但能力边界由后端注册的工具决定，
所有写入仍由 Go 后端鉴权、校验、记录并可撤销。

用户价值：把“查证据、搜资料、比对、逐项修改”这类多步的曲库管理工作交给管家，同时能用它做日常问答、
控制播放和管理个人库；也能让 Claude Code 等 MCP 客户端直接管理 ROOMusic。

## 背景

- 路线图 M6 原定“只读 Steward → 受控提案 → 独立审查”，前置是 M3、M4 的工具、权限与执行边界，
  另需一份覆盖提示注入与数据外发的 ADR（`docs/architecture/core-1-roadmap.md`）。
- 产品合同规定一个 Agent、三种审批模式（`assistant`、`steward`、`operator`），Agent 只是调用方，
  不提供 shell、SQL 或任意路径入口（`.trellis/spec/guides/product-goals.md`、
  `.trellis/spec/backend/agent-and-operation-guidelines.md`）。
- 目前没有任何 Agent 运行时代码；侧栏没有 Steward 入口（`frontend/src/app/shell/nav-items.ts`）。
- 已有共同写入流程 `operations.Run`（revision、幂等、操作记录、单条撤销），覆盖字段修正、归组、默认版本、
  问题核对、认领、艺人别名与合并拆分（`backend/internal/operations`）。
- 已注册约 130 个接口，其中 `/me` 下 48 个（历史、收藏、歌单、播放与分区等）。
- 服务端目前没有出站 HTTP 请求；已有一处 SSE（`backend/internal/zones/httpapi/events.go`）可参照。
- 后端依赖只有 pgx 与 `golang.org/x`；数据库里没有存放第三方密钥的先例；认证只有会话 Cookie。
- 用户身份只有管理员与普通成员两种（`backend/internal/identity/guard.go`）。
- 生产镜像是 Alpine，带 `psql` 和数据库连接串，应用以 uid 1000 运行，`/music` 只读挂载
  （`deploy/production/Dockerfile`、`deploy/production/README.md`）。
- 本机工作区没有可沿用的 agent 或 MCP 项目。

## 决策记录（2026-11-15，选择者 qlqq）

| 编号 | 决策 | 理由 |
| --- | --- | --- |
| S1 | 形态是自主多步工具循环，不是一问一答；过程流式可见 | 用户要的是能自己干活的管家 |
| S2 | 不引入 agent 框架，循环自己实现 | 工具全是自有业务能力；难点在权限与确认，已在后端；保持依赖干净 |
| S3 | 模型接入只支持 OpenAI 兼容接口与 Messages 接口两种协议，不做订阅接入；模型不支持工具调用时管家不可用，不降级 | 覆盖云端与本地模型，不需要 OAuth |
| S4 | 入口为内置对话页加 MCP 服务，两者共用一套工具 | MCP 可让 Claude Code 等客户端直接管理 ROOMusic |
| S5 | 不做部署层操作（Compose、环境变量、升级、宿主机文件） | 避免管家把自己修坏 |
| S6 | 不在应用容器内提供 shell；用诊断工具与只读查询工具代替 | 容器内有数据库凭据与应用进程，shell 等于任意 SQL 且绕过操作记录 |
| S7 | 不做物理文件整理，“只读源文件”合同不变；整理只在目录层面，走现有受治理操作 | 物理文件操作需要单独的恢复策略 |
| S8 | 支持联网：结构化音乐数据源、通用搜索、网页抓取 | 整理专辑与日常问答都需要外部资料 |
| S9 | 所有登录成员都能用管家，工具按各自权限过滤；管理员可以关闭成员的使用 | 成员也能用问答与播放控制 |
| S10 | MCP 用个人访问令牌认证，令牌代表签发它的用户；签发时选只读或读写，可设过期时间，可随时吊销。读写令牌的写操作直接执行，由 MCP 客户端自己的权限提示把关 | 让 MCP 客户端能完整管理 ROOMusic；写操作仍经后端校验、有记录、可撤销 |
| S11 | 通用搜索支持三种来源，由管理员在设置里选：自建 SearXNG、一家商业搜索 API、模型端点自带的搜索能力。具体商业 API 在联网子任务规划时由用户指定 | 自带搜索配置最省事；另两种保证端点不带搜索时仍可用 |
| S12 | 三种会话模式（确认 `assistant`、审查 `steward`、直接执行 `operator`）对所有用户开放，由用户按会话选择。模式只决定审批路径，不改变权限：工具仍按调用者的身份鉴权，普通成员在任何模式下都改不了曲库和配置 | 普通成员能做的都是只影响自己的操作，直接执行更顺畅；产品合同里“operator 仅管理员”的条文随之修改 |
| S13 | 端点能力自动探测：管理员填地址和密钥后，系统按地址匹配常见服务商的预设，并实际探测协议、可用模型、工具调用与自带搜索，结果自动填入设置；探测结果可以手动改。两种通用协议是基础，常见服务商的专有接口只在它的自带搜索等能力需要时才加适配，具体哪些服务商进预设、各自怎么调用，在 C2、C7 规划时查文档确定 | 用户不想手动判断端点支持什么；预设表会过时，所以以实际探测为准并保留手动修改 |
| S14 | 做 `steward` 模式：改动曲库或配置的方案交给独立的审查子代理，批准后自动执行；审查结果是 `approved`、`rejected`、`needs_human_confirmation` 三种，后者转为人工确认；审查不可用时拒绝执行，不降级为直接执行 | 用户要求；与产品合同的 steward 定义一致 |
| S15 | 模型端点与密钥由每个用户自己配置，只供本人使用，没有管理员提供的共享密钥；不做用量上限 | 用户选择；费用由各自承担 |
| S16 | 对话界面按已确认的原型做：任意页面右侧可停靠的面板加带会话列表的完整页面；过程按条目列出而不是聊天气泡；修改方案逐项列出旧值与新值，可逐项勾选；输入框下有模式按钮（Assistant、Steward、Operator，Shift+Tab 轮换）和模型按钮，切换模型只影响当前对话，默认模型和审查模型在设置里选；设置里这一栏叫 Agent | 用户审阅原型后确认 |
| S17 | 显示名字默认是“管家”，每个用户可以改成自己起的名字（例如“小蓝”）；侧栏入口、面板标题、输入框提示等界面上称呼它的地方都跟着变。名字只对本人生效；设置栏目名 Agent、模式名和管理员的成员开关不随名字变 | 用户要求 |

规划时由主代理按惯例取的默认值（用户审阅最终摘要时可改）：

- 对话记录与记忆按用户隔离，管理员不能读其他成员的对话；保留到用户自己删除为止，用户可以查看和删除自己的记忆。
- 会话模式按会话选择，新会话默认是确认模式。
- 搜索来源（SearXNG 地址、商业搜索密钥）也由每个用户自己配置。
- 审查子代理默认用用户配置的同一个端点和模型，可以另选一个模型专门做审查。

## 需求

### 工具范围

- R1 曲库只读：搜索、专辑与版本、曲目、艺人、证据、待关注问题、扫描状态与记录、操作记录。
- R2 播放与个人库：控制播放与队列、分区、收藏、歌单、播放历史。
- R3 目录层面的整理：字段修正、归组、默认版本、问题核对、认领、艺人别名与合并拆分，以及撤销。
  全部经 `operations.Run`。
- R4 联网：结构化音乐数据源查询、通用搜索（S11）、网页抓取。
- R5 诊断与只读查询：日志、磁盘占用、按曲目 ID 的音频探测、数据库状态；受限的只读查询。
- R6 应用内配置：目录、扫描与扫描计划、成员、播放设置、DSP、备份。未走 `operations.Run` 的写操作
  逐项决定补记录与撤销，或标为不可撤销。

### 行为

- R7 管家以当前登录用户（或令牌所属用户）的身份调用工具，权限等于该用户的权限，后端校验不因调用方是管家而放宽。
- R8 确认规则：只读操作和只影响当前用户的操作直接执行；改动曲库或配置的操作合并成一份方案，
  由用户确认后执行，可选本次会话内同类操作不再询问；`steward` 模式下方案交审查子代理（S14）；
  `operator` 模式下全部直接执行（S12）。
- R9 对话带上当前页面与正在播放的曲目作为上下文。
- R10 对话与工具调用记录持久化；管家能记住用户偏好。
- R11 耗时长的任务可以在后台继续，完成后可查看结果。
- R12 每个用户在自己的设置里配置模型端点、密钥、模型名与搜索来源；协议与端点能力自动探测并可手动修改。
  管理员的设置里只有是否允许成员使用管家的开关（S9、S11、S13、S15）。
- R15 每个用户可以给管家起名字，默认“管家”；界面上称呼它的地方用这个名字（S17）。
- R16 对话界面有面板和完整页面两种形态，模式与模型可以在输入框下按会话切换（S16）。

### 安全

- R13 曲目标签、歌词、文件名、网页内容都按不可信文本处理；另立 ADR 规定发给模型的数据范围、
  提示注入的处理、出站请求的边界、密钥与令牌的存放。
- R14 模型密钥、搜索密钥与访问令牌不出现在日志、操作记录和接口响应里。

## 跨子任务验收标准

- A1 在对话页说一句整理某张专辑的目标，管家不需要中途追问就能连续调用多个工具（查证据、查外部资料、
  比对），给出一份修改方案；确认后修改生效，操作记录里能看到每一项，且每一项可撤销。
- A2 普通成员能用管家问答、控制播放、管理自己的歌单与收藏；向管家要求修改曲库或配置时被后端拒绝，
  没有任何副作用。管理员关闭成员使用后，成员看不到入口，接口返回拒绝。
- A3 用只读令牌接入的 MCP 客户端能调用只读工具，调用写工具被拒绝；用读写令牌能完成 A1 同样的修改，
  操作记录标明来源；吊销令牌后立即失效。
- A4 同一组工具在对话页与 MCP 下的权限判定结果一致（同一用户、同一工具、同一目标）。
- A5 三种模式所有用户都能选；普通成员在 `operator` 模式下要求修改曲库或配置仍被后端拒绝。管理员在 `operator` 模式下写操作不再确认但仍有操作记录；新会话回到确认模式。
- A6 标签、歌词或网页里含有指令文本时，默认模式下不会出现未经确认的曲库或配置修改。
- A7 模型密钥、搜索密钥与访问令牌在日志、操作记录、接口响应和导出的对话里都查不到。
- A8 模型端点不可用或不支持工具调用时，对话页给出明确的不可用提示，其余功能不受影响。
- A10 填入常见服务商或本地模型的地址后，设置页显示探测到的协议、模型列表、是否支持工具调用和自带搜索；探测结论与实际调用的结果一致，探测失败时说明原因并允许手动填写。
- A11 `steward` 模式下，审查批准的方案自动执行，操作记录带审查结果；审查拒绝的不执行；审查要求人工确认的出现确认卡片；
  审查的模型调用失败时不执行。主代理在自己的输出里写批准字段不能让方案通过。
- A12 一个用户配置的端点和密钥，其他用户（包括管理员）用不到也读不到；没有配置的用户看到的是配置引导。
- A13 在设置里把名字改成“小蓝”后，侧栏入口、面板标题和输入框提示都显示“小蓝”，其他用户看到的仍是各自的名字；
  清空后恢复为“管家”。在对话里切换模型只影响这一个对话，新对话用设置里的默认模型。
- A9 没有新增 shell、任意 SQL 写入或任意路径入口；`/music` 仍是只读挂载。
