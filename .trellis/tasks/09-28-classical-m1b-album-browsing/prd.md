## 目标与用户价值

所有登录用户能浏览、搜索资料库里的专辑，查看一张专辑的版本、介质、曲目、署名与来源证据。界面从第一天起就是“组 → 版本”的最终形态：
M3 人工归组之前每组只有一个版本，页面自然退化，不出现版本字样，后续不用返工；也不因标题相似而暗示“同一专辑”的聚合。

## 已核实事实（2026-10-02）

**接口**（全部只读，登录即可读，证据除外）

- `GET /release-groups?q=&attention=required&page=&page_size=`：默认 50、上限 100；顺序固定为代表版本的标题、艺人、ID，没有其他排序参数；
  搜索命中标题、艺人、专辑艺人与曲目（`backend/internal/catalog/read.go:56`）。组摘要 `{id, release_count, attention_count, representative}`。
- `GET /release-groups/{id}`：组摘要加 `releases`（成员摘要，按代表版本规则排序，最多 100 条，`release_count` 是完整数量）；非 UUID 400，
  不存在或没有可见成员 404（`backend/internal/catalog/httpapi/groups.go`）。
- `GET /releases/{id}`：摘要加 `candidate_kind`、`genre`、`catalog_number`、`edition`、`label`、`barcode`、`media`（含 `tracks` 与曲目署名）、
  `credits`（Release 级）、`evidence`（安全摘要）。上限：介质 256、曲目 10000、Release 署名 100、单曲署名 100、证据 100
  （`backend/internal/catalog/read.go:18`–`:26`）。曲目 `source` 只是文件名（`read.go:644`），`source_kind` 为 `cue_virtual` 时是 CUE 分轨。
- `GET /releases/{id}/evidence`：仅管理员；字段值、候选（每字段最多 20）、原因码、分组证据（规则、来源引用最多 100、原因码）与 `truncated`。
- `GET /artworks/{resource_id}`：登录即可读；资源 ID 是内容哈希加扩展名，响应为 `private, no-cache` 加 `ETag: "<资源 ID>"`（F3，2026-10-02），
  带匹配的 `If-None-Match` 返回 304 且不读文件；未登录 401、资源不存在 404，都不会是 304。
  原图大小不受限（扫描时只拒绝超过 16 MB 的图片），没有缩略图接口。
- 阶段 I 之后每个新 Release 各自一个组；多版本的组目前只能直接写库构造（M3 才有人工归组）。

## 关键决策

| 编号 | 事项 | 选择 | 依据 |
| --- | --- | --- | --- |
| K1 | URL 形状 | 列表 `/albums`，查询参数 `q`、`attention=required`、`page`（第 1 页不写）；详情 `/albums/$groupId`，`release` 只在选中非代表版本时出现。不合法的值显式返回 `undefined`；总数非零而页码超出末页时替换为末页；`release` 不在本组成员里时替换掉。从列表进入详情时把列表参数放进路由的 history state，详情页“返回专辑列表”据此恢复筛选与页码，直接打开详情时回到 `/albums` | 推荐；参数名沿用接口与 state-management 规范 |
| K2 | 列表呈现与顺序 | 封面卡片网格，每页 48 张（列数随容器宽度变化）；顺序就是接口的“标题 → 艺人 → ID”，不提供排序控件；卡片整张是一个链接，显示封面、标题、专辑艺人（没有则用艺人）、年份、介质与曲目数，多版本时显示“N 个版本”，需要关注时显示标签 | 推荐；PRD 初稿已定“按组卡片”；排序超出接口能力 |
| K3 | 搜索与筛选 | 搜索框加“搜索”按钮（回车提交），提交与切换筛选时回到第 1 页；有搜索词时显示“清除”；“只看需要关注”复选框立即生效；不做输入即搜 | 推荐：每次提交一条历史，请求与读屏播报可预期 |
| K4 | 封面 | 保留裱边、不加滤镜；四态：加载中（同尺寸静态占位）、已加载、无封面（确定性的文字版面：深色底上排标题）、加载失败（同样的版面加“封面无法加载”说明，详情页可重新加载）；图片带接口给的宽高、懒加载与异步解码；卡片中的封面是装饰（标题已在链接里），详情页的封面有替代文字；不做缩略图 | 推荐；DESIGN 第 5、8 节要求三态分开处理、滤镜默认不用 |
| K5 | 详情结构 | 头部：封面、标题、专辑艺人、年份与流派、介质数/曲目数/总时长（有未知时长则不写总时长）。版本导航只在 `release_count > 1` 时出现，用链接加 `aria-current`。介质按顺序逐段列出（多于一张时顶部有跳转链接），不做原型的分段切换。曲目行：序号、标题、与专辑艺人不同的曲目艺人、曲目署名、时长（未知显示“—”）、CUE 标记；不显示来源文件名。侧栏“此版本”（厂牌、编号、条码、版本说明、流派、来源与介质类型）和“制作人员”（Release 级署名）。不做原型的“结构树”侧栏 | 推荐；顺序依 DESIGN 第 4 节。逐段列出能完整呈现任意张数的介质，原型的分段切换只适合两三张 |
| K6 | 证据按权限呈现 | 所有登录用户在详情底部有折叠的“来源与证据”，内容取自详情响应的证据摘要（字段、来源、可信度、处理方式），并说明“需要关注”不等于已确认的错误；管理员多一个“查看完整证据”，展开时才请求管理员接口（字段值、候选、原因码、分组规则与来源引用、截断提示）；普通用户从不请求该接口 | 推荐；与接口权限一一对应 |
| K7 | 未实现的原型入口 | 播放、收藏、版本对比、交给 Steward、艺人链接都不出现（不做禁用占位），艺人名是纯文字 | 推荐；与 M1a“导航只列可用页面”一致 |
| K8 | 导航与概览 | 所有用户的导航在“概览”之后加“专辑”；概览“资料库”区块的专辑数链接到 `/albums`，需要关注数链接到 `/albums?attention=required` | 推荐 |
| K9 | 视觉待实测项 | DESIGN 第 10 节“仍待确认”第 2 项按默认实现：封面不加滤镜，密集信息仍用衬线字体；收尾时附合成数据的真实页面截图，由用户确认或另提调整 | DESIGN 原文要求“随 M1b 的真实页面实测后确认” |
| K10 | 接口样本 | 在 `TestPostgreSQLAPIResponseSamples` 中：用合成 FLAC 扫描出一张双碟专辑（厂牌、编号、条码、作曲/指挥/演奏署名），记录组详情、发行版本详情与管理员证据；记录既有单曲专辑的发行版本详情（大多字段为空）；直接写库构造两版本的组，记录多版本组详情；记录组与发行版本的 404 | 推荐；不新增后端接口或行为 |

## 需求与验收

| 编号 | 需求 | 验收标准 |
| --- | --- | --- |
| A1 | 专辑列表 | 卡片网格每页 48 张，顺序与接口一致；首次加载为同结构占位；空库按角色给出不同说明（管理员提示去扫描目录）；筛选无结果可一键清除；加载失败可重试；401 进入会话恢复 |
| A2 | 可恢复的 URL 状态 | 搜索、需要关注筛选与页码可刷新、可前进后退；不合法的参数被规范化而不是原样请求；页码超出末页时替换为末页；从详情返回列表恢复原筛选与页码 |
| A3 | 封面 | 有封面、无封面、加载中、加载失败四态分别可见，不引用外部封面；详情页加载失败后可重新加载；列表滚动时封面按需加载，布局不跳动 |
| A4 | 详情层级 | 组头、版本（单版本时没有版本导航与“版本”字样；多版本时可切换且 URL 记录选择）、介质分段与曲目、曲目与 Release 级署名、厂牌/编号/条码；未知值显示为未知，不伪造；所选版本在两次请求之间变得不可见时有提示，可回到代表版本；组不存在显示“专辑不存在” |
| A5 | 证据按权限 | 普通用户只看到证据摘要，测试断言没有请求管理员接口；管理员按需加载完整证据，403、404、503 与截断各有提示 |
| A6 | 不暗示聚合 | 单版本组不出现版本字样；多版本只来自接口的组成员；“需要关注”的说明不把它写成已确认的错误 |
| A7 | 长内容与混排 | 超过 1000 字的标题、超长艺人名、无空格长串、中日英混排、10 张以上介质的专辑，在 375/768/1024/1280/1440 五种宽度下页面与主内容区都没有横向溢出、没有遮挡，完整文字可以获取 |
| A8 | 字体回退 | 拦截全部字体请求后，列表与详情仍满足 A7，文字不小于 12px |
| A9 | 无障碍与键盘 | axe（WCAG 2.1 A/AA）无严重或关键问题；只用键盘可以完成 搜索 → 筛选 → 翻页 → 打开详情 → 切换版本 → 展开证据 → 返回列表，焦点始终可见 |
| A10 | 样本与契约 | K10 的样本全部登记到 `src/test/api-contract.test.ts`，decoder 往返与样本相同；decoder 的数组与字符串上限与后端一致 |
| A11 | 质量门禁 | 与 M1a 相同：lint、typecheck、Vitest、生产构建与内嵌资产漂移、Playwright（五种宽度、axe、键盘路径）、集成测试（样本比较）；另在隔离 PostgreSQL 与合成素材上做一次真实接口冒烟并留截图 |
| A12 | 文档同步 | DESIGN（URL 形状、落地差异、第 10 节 M1b 验收与仍待确认项）、前端规范（URL 形状、封面与新组件、证据权限）、Core 1 路线与架构图、父任务、README 的前端检查说明（如有变化）与本任务记录一致；改动文档的相对链接逐个检查 |

## 风险与延期

- **封面原图大小**：没有缩略图，列表首屏要下载可见封面的原图（常见几百 KB 到数 MB）。靠懒加载与 F3 的 304 缓存缓解；若真实使用中首屏明显过慢，
  另立后端缩略图任务（需要图像缩放依赖，单独决策）。
- **超大发行版本**：接口允许一次返回 10000 首曲目。每个介质段用 `content-visibility: auto` 降低布局成本，Vitest 用 1000 首曲目的替身验证可渲染。
- **两次请求之间的重扫**：组详情与发行版本详情分开请求，中途重扫可能让所选版本不可见，按 A4 处理。
- 阶段 I 已于 2026-09-30 完成，按组接口不再是阻塞项。

### 与设计的差异

1. **K10 多一个样本** `releases/get-cue`：设计没有列出；CUE 分轨的标记要靠真实响应形状验证。
2. **版本导航的标签**用成员摘要里有的字段（年份、介质或来源类型、介质数与曲目数），各版本标题不同时才附标题：摘要里没有版本说明与编号，
   读详情才有，列表里不为每个版本各发一次请求。设计写的“版本说明 → 厂牌编号 → 年份 → 版本 N”取舍链做不到。
3. **没有“专辑”小标题**：`Page` 的 `h1` 加专辑艺人说明已足够，多一行小标题只会挤占长标题的空间。
4. **侧栏标题**：多版本时是“此版本”，单版本时是“发行信息”（见 A4）。
5. **`Page.compactTitle`**：标题超过 80 个字符时降一级字号（设计写在头部组件里，实际放进 `Page`，因为 h1 由它给出）。
6. **介质跳转用焦点管理而不是 hash 链接**：点“第 N 张”滚到该段标题并把焦点放上去，地址与历史不变（hash 会被路由当作地址变化）。
7. **`Panel.headingRef`** 与 **`useClampedPage`**：前者让翻页后焦点落在结果标题上，后者把列表与概览共用的页码钳制逻辑抽成一个 hook。
8. **导航**：“专辑”在“资料库”分组里，紧跟“概览”，所以成员也能看到“资料库”这个分组小标题（只有“专辑”一项）。
9. **翻页的滚动与焦点**（设计没有写）：点页码后结果标题滚到视野顶部并获得焦点；改搜索词或筛选不挪动焦点，用户还在筛选区里。AppShell 只在路径变化时重置滚动与焦点，
   只改搜索参数的跳转保持焦点。
10. **证据按钮**：加载完成后“查看完整证据”按钮仍然保留（文案改为“重新加载完整证据”），方便在被截断或失败之后重试。
11. **版面修正（暴露于第 4 步的浏览器检查，在本任务内修，没有放宽断言）**：
    - M1a 外壳：绝对定位的“仅读屏可见”元素（`VisuallyHidden`、`DataTable` 的 caption）在 `.main` 与 `.sidebar` 都不是定位祖先时，会让文档比窗口更高，长页面底部出现空白滚动区。
      给两个滚动容器加 `position: relative`。第一版自测在没有 `<!doctype html>` 的页面上空过（怪异模式的 `scrollHeight` 不同），补了 doctype 与确定性的夹具。
    - 375px 宽的长内容详情出现横向溢出：`contain-intrinsic-size` 的单值简写同时设定了宽度（改用 `contain-intrinsic-block-size`），
      且被 `content-visibility` 跳过的分段在窗口收窄后保留旧宽度（网格项加 `min-width: 0`）。两处都做了变异验证。
12. **A3/A4 与 A6 的字面解释**：见上面的验收对照。

### 发现与遗留

- **后端：CUE 专辑拿不到文件夹封面**：CUE 虚拟曲目的 `relative_path` 形如 `cue-album/album.cue#track-1@cue-album/image.flac#index-0`，
  `saveArtworkForRelease` 用 `filepath.Dir` 取曲目所在文件夹，得到不存在的目录，`cover.png` 没有被发现。页面按“没有封面”显示文字版面，没有出错。
- **后端：多碟专辑只在第一张碟的文件夹里找封面**：放在多碟专辑父目录里的封面不会被发现，而真实资料库里常见这种布局。
- 以上两项是后端行为，M1b 范围外不改，已记入[后端运行合同](../../spec/backend/core0-runtime-contracts.md)的技术债，由用户另行安排；合成冒烟已经能复现。
- 运行合同文件已超过 32 KB，值得按主题拆分（本任务只追加了一条技术债，没有动结构）。
- 后续任务沿用的东西：`features/catalog` 的 decoder 与端点、`Cover`、`labels.ts`/`format.ts`、`Panel.headingRef` 的焦点约定、`e2e/support/albums-data.ts` 的长内容数据，以及 `expectNoDocumentScroll` 与变异验证的做法。
