## 发现

1. **接口与页面完全对得上**：后端的响应信封、状态码、字段名与样本一致，没有出现 decoder 拒绝响应（`invalid_response`）的情况；完整证据里的来源引用确实是安全的相对路径。
2. **CUE 专辑拿不到文件夹封面（后端缺口，未修）**：CUE 虚拟曲目的 `relative_path` 形如 `cue-album/album.cue#track-1@cue-album/image.flac#index-0`，
   `saveArtworkForRelease` 用 `filepath.Dir` 从中取“曲目所在文件夹”，得到不存在的目录 `…/cue-album/album.cue#track-1@cue-album`，于是 `cue-album/cover.png` 没有被发现
   （数据库里该发行版本没有 `release_artworks` 记录，`GET /release-groups` 里 `artwork` 为 null）。页面按“没有封面”显示文字版面，没有出错。
   这属于后端行为，M1b 范围内不改，记入后端运行合同的技术债。
3. **多碟专辑只在第一张碟的文件夹里找封面（后端行为，未修）**：封面来源取“按碟序排列的第一首曲目”所在的文件夹，所以放在 `double-album/` 父目录里的 `cover.png` 不会被发现，放进 `CD1/` 才行。
   第一次运行因此看不到封面，是素材摆放的问题，不是页面的问题；真实资料库里常见“封面在父目录”的多碟布局，同样记入技术债。
4. 完整证据接口在整个管理员会话里只被请求一次（点“查看完整证据”那一次），成员会话里一次也没有；直接请求时成员得到 403。

## 没有覆盖及原因

- 多版本的组只能直接写库构造（本冒烟用 `UPDATE releases SET group_id`），M3 才有人工归组；版本导航的真实数据形状由这个写库样本验证。
- 一万首曲目的版本：合成素材太大且意义有限；千首曲目的渲染由 Vitest 覆盖（`album-detail.test.tsx` 1000 首），布局成本靠分段的 `content-visibility`，没有在真实库上量化。
- 封面大图的加载耗时：合成封面只有几百 KB，真实封面可能几 MB，没有缩略图接口的风险记在 PRD 的“风险与延期”里。
- 页面打开期间会话过期与跨标签页广播：M1a 已在真实后端验证，本次没有改动。
- 这次冒烟不进入 CI：它需要 Docker 与 PostgreSQL，步骤依赖本机环境；后端的 API 契约由样本与集成测试在 CI 中守住。
