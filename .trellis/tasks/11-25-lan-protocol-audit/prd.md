# 审查现有 AirPlay、Cast、UPnP 的局域网实现

状态：规划中。父任务 `11-25-lan-hires-multiroom`。

## 目标

按一组与来源无关的局域网音频工程经验，审查现有局域网输出，修复确认的问题。审查范围包括 UPnP、Google Cast、AirPlay，以及它们共用的 mDNS、SSDP、PTP 和托管输出代码。目标是让多网卡、坏报文、设备卡死、链路变差这些情况下，ROOMusic 不挂起、不泄漏，也不连累其他设备与播放区。

## 范围

- 代码：`backend/internal/devices/`（`upnp`、`cast`、`airplay`、`mdns`、`lan`）、`backend/internal/ptp/`、`backend/internal/zones/` 中与托管输出相关的部分，以及 `cmd/roomusic-ptp`。
- 审查清单见下表。每条要么给出“已满足”的代码证据，要么给出问题与修复方案。

| 编号 | 检查项 |
| --- | --- |
| C1 | 组播：每个活动网卡各自加入组播组（不只用默认接口），出站指定网卡；网卡和地址变化后能重建；多网卡时每个网段都能发现设备 |
| C2 | 回包：单播应答可能回到发送套接字的临时端口，要能收到 |
| C3 | 报文解析：先校验长度再分配，长度字段有上限，截断或越界的包被丢弃且不 panic。涉及 CASTV2 帧、RTSP 头与正文、plist、mDNS、SSDP、PTP、HAP |
| C4 | 等待回复：每个“发请求等回复”都有超时或随连接关闭释放，设备永远不回也不会挂死 goroutine 或占着锁 |
| C5 | 故障隔离：一台设备卡死或变慢，不拖住其他设备、其他播放区或全局锁。重点查持锁期间的网络 IO |
| C6 | 背压与内存：发送队列与重传缓存有上限；对端不消费（零窗口、拔网线不发 FIN）时有超时断开，内存不随时间增长 |
| C7 | 时钟与延迟：时钟测量取往返最小的样本；设备上报或约定的延迟进入起播与进度计算；单位一致（毫秒、纳秒、帧） |
| C8 | 兜底超时：超时后的兜底分支（例如“当作就绪继续”）不会静默破坏行为 |
| C9 | 重连：断线重连后把需要的状态全量重发，旧会话的数据（旧序号、旧流）被丢弃 |
| C10 | 目标地址：不向组播、广播、回环、未指定地址发单播应答或控制请求；设备通告的地址只接受局域网 IPv4（与现有出站规则一致） |
| C11 | 身份归并：同一设备的多条公告、多个服务实例、地址变化，归并为一台设备；地址变化时重建连接 |
| C12 | 资源释放：关闭协议开关、停止输出、进程退出时，套接字与 goroutine 都退出；接收出错后能自愈，不会永久停收 |
| C13 | 文档：入站端口需求（UPnP 拉流、AirPlay 时间与控制端口、PTP 319/320）在部署文档里写清 |

## 要求

- R1：审查结果写入 `research/audit.md`。按检查项逐条记录结论、证据（`文件:行`）、问题严重程度与修复方案。
- R2：确认的问题按严重程度修复，每条修复配一个能复现原问题的测试；测试由不同于实现的子代理编写。
- R3：只改上述范围内的代码与对应 spec；不改协议行为之外的产品功能，不加新开关。
- R4：没有问题的检查项不改代码。

## 验收

- `research/audit.md` 覆盖 C1–C13，每条都有结论与证据。
- 每个修复都有对应测试，测试在修复前失败、修复后通过（交付说明里列出）。
- 受影响包的 Go 测试、`go vet` 与现有集成测试通过；实际运行的与沿用之前结果的分开汇报。
- 局域网设备开关关闭的实例行为不变。

## 规划决定记录

- 路线：按 qlqq 的长期要求“规划完直接实现，能自己定的自己定”，由主代理决定修复范围（design.md 的 F1–F10），随交付请 qlqq 审阅。
- 审查结论（`research/audit.md`）：没有高危项。中等缺陷有 C1、C5、C7（主代理已抽查 C5、C7 属实），另有 C2 待验证；低等缺陷有 C8、C11、C12、C13。C11 地址变化后重连不做，理由见 design.md 的 F10。

## 不做

- 新协议、新设备种类、多设备编组（属于 `11-25-slimproto-squeezelite`）。
- 提高现有协议的音质上限（UPnP 的高码率放开另行评估，见父任务）。
