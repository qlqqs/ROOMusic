# 外部数据源与自动整理

状态：规划中（父任务）。本文件记录需求、决定、子任务划分与跨子任务验收；总体技术设计见 `design.md`，
子任务顺序见 `implement.md`。父任务本身没有实现工作，不启动；每个子任务单独规划、实施、验收和归档。

现状调研在 `research/`：

- `research/overlays-and-operations.md`：元数据分层、受治理操作、撤销、问题计算。
- `research/steward-runtime.md`：管家运行、方案、审查、凭据、用量、既有决定。
- `research/scan-evidence-and-sources.md`：扫描可比对的标识、封面与歌词、后台任务、出站请求、数据目录。

## 目标

接入外部音乐数据源，并让曲库整理默认自动进行：程序处理能保证正确的事，模型对程序拿不准的做兜底判断，
人只处理模型也判断不了的例外。所有自动修改可撤销。

用户价值：扫描之后，封面、歌词、年份、厂牌、曲目与艺人的写法、重复艺人、版本归组这些事不需要一条条点确认；
用户偶尔看一眼“这次整理改了什么”，发现错的再撤销。

## 背景

与目标一致的既有合同：

- 产品合同把 `steward` 模式定义为“自主的、有证据支持的整理和有限维护”，并规定确定性的扫描与解析归程序、
  AI 只处理未决的解释（`.trellis/spec/guides/product-goals.md`“Long-Term Steward Model”）。
- 永久约束：标题、艺人、年份或目录的弱相似不能做跨目录的权威合并（同上“Permanent Invariants”）。

写入与撤销（`research/overlays-and-operations.md`）：

- 元数据只有两层：扫描值与修正意图；有效值由视图 `release_effective` 读取时叠加。没有留给外部源或模型的层。
- 修正行不记作者，一个字段只有一行，后写盖先写。现有结构只保证“扫描不盖修正”，保证不了“自动写入不盖人工修正”。
- 撤销一次一条，且只能撤目标上最近一次修改；发行的修正、归组、核对共用一个版本号。没有批次，不能按来源撤。
- 操作者必须是 `users` 里的用户；`origin.source` 只有 `chat`、`mcp`；没有任何后台代码调用 `operations.Run`。
- 可修正的只有发行级八个字段（标题、专辑艺人、年份、流派、厂牌、编号、版本说明、条码）；没有曲目级字段修正。
- 艺人合并、拆分、改名、忽略候选不可撤销，是 2026-11-03 的轻量标准（R4）定的；合并记录里存了前态但没用于撤销，
  “拆分并恢复”不保证回到合并前原样。
- “需要关注”由 SQL 实时算出三类：拿不准的字段、归组冲突、缺失曲目。

管家（`research/steward-runtime.md`）：

- 运行只能由登录用户的四个接口启动，必须属于某个用户的某个会话，登录会话过期即取消。没有定时或系统发起的入口。
- 方案只能由模型的工具调用产生；程序侧没有把待定项交给审查的入口。
- 模型端点与密钥按用户存放并按用户加密，没有实例级凭据。
- 审查策略第 1 版：不可撤销项、超过 20 项的方案、`approved` 且高风险的一律转人工。能自动放行的只有 5 个发行级可撤销工具。
- 审查证据只有本地摘要与字段前后值，不含外部资料；审查模型不能自己查资料，也不能用另一个端点。
- 转人工的项只以会话里的方案卡片呈现（24 小时过期，用户发新消息即作废），没有跨会话的例外队列，没有站外通知。
- 用量：每次运行 24 步、40 万 token，每用户 3 个并发；没有用量汇总与预算上限；审查调用的用量不计入运行上限。

扫描与外部资料（`research/scan-evidence-and-sources.md`）：

- 标签里的 MusicBrainz ID、Discogs ID、AcoustID 都没解析；已落库可比对的只有厂牌编号、条码、CUE 里的 ISRC。
  标签 ISRC 解析了但不落库。
- “内容指纹”是音频负载哈希，不是声学指纹；仓库、镜像与固定的 ffmpeg 都没有 Chromaprint。
- 证据表（`track_observations`、`release_field_decisions`）每次扫描先删后写，没有外部来源的常驻位置。
- 封面来源只有内嵌与文件夹两种（数据库约束写死），每发行一张，扫描选不出本地封面时删除关联；没有图片下载代码。
- 歌词来源只允许五种本地来源，每次落库整体覆盖。艺人没有简介与图片。
- 没有通用后台作业机制；音频分析是“按缺口查询、单线程、扫描期间让路”的独立循环。
- 出站请求全在管家里，统一走 `backend/internal/steward/egress/client.go`。MusicBrainz 查询与 Cover Art Archive 清单已有封装
  （只有自由查询与按 MBID 读取，无缓存，503 不重试，封面清单不走限速器）；AcoustID、LRCLIB 没有任何代码。
- 没有实例级的外部源配置；没有统一的全局应用设置表。
- 生产容器可写处只有 `/data`、`/backups` 与 64 MiB 的 `/tmp`；备份不含 `/data`。

## 决定记录（2026-11-22，选择者 qlqq）

| 编号 | 决定 | 理由 |
| --- | --- | --- |
| U1 | 三层分工：程序做能保证正确的事，大模型做兜底判断，人的参与减到最少 | 用户对产品的定位：借助模型的知识和能力来判断整理，而不是一直让人确认 |
| U2 | 替换“外部产出一律作为候选、等人确认”的原则 | 太严，实际操作不顺 |
| U3 | 局域网多协议设备发现与单设备串流另立任务，不在本任务范围 | 与本任务无依赖 |
| U4 | 外部数据源做成内置适配器加统一接口：每个源有声明（能力、启用条件、限速），设置页可开关。不建第三方插件宿主；以后有第三方需求时再把稳定的接口升级为宿主 | 目前没有非要第三方来写的源；整理体验取决于写入与模型判断，不取决于宿主 |
| U5 | 后台整理归开启它的管理员：用该管理员自己配置的端点与密钥，可单独选“整理用的模型”（不选则用对话模型）；自动产生的修改记在该管理员名下，来源标为自动整理；该管理员被停用、清除密钥或关掉开关即停止 | 不引入实例级共享密钥，M6 的 S15 不推翻；ADR 0005 补充“管理员开启的自动整理视为该管理员本人的请求” |
| U6 | 自动整理能动的范围：① 补空缺（封面、歌词、空的字段、外部 ID），程序直接做；② 改发行级八个字段的已有值，本地与外部冲突时由模型判断；③ 问题核对、默认版本、认领，由模型判断；④ 专辑归组，只在有强证据时自动做（外部源确认是同一个 release group），弱相似仍不自动合并；⑤ 艺人合并、改名、忽略候选，先把合并与改名做成可撤销；⑥ 发行的合并与拆分一起做 | 覆盖“需要关注”的全部问题类型与重复艺人；④ 守住永久约束；⑥ 取代 2026-11-03 的 R1 搁置 |
| U7 | 范围与方案按“适合所有用户的曲库”来定，不按某一个库定制，也不靠读取真实曲库做决定。要覆盖的曲库形态：整轨抓的 CD、Picard 打过标签的、流媒体下载的单曲、标签很差或没有标签的文件、华语与欧美 | 这是产品，不是为一个人的库写的工具 |
| U8 | 首批外部源四个：MusicBrainz、Cover Art Archive、LRCLIB 默认开；AcoustID 在管理员填入应用密钥后启用，密钥由各实例管理员自己注册，不在仓库内置共用密钥。授权在生产镜像里增加 Chromaprint。扫描把标签里的 MusicBrainz 各类 ID、ISRC、AcoustID 解析并落库 | 单曲与标签差的文件没有条码和编号，只能靠 ISRC 或声学指纹；同类工具都以 AcoustID 兜底 |
| U9 | 曲目级字段修正纳入本任务：范围限定为曲目标题与曲目艺人，曲序与碟号不动 | 单曲的核心信息就是这两项；没有修正通道，外部源和模型的判断无处可写 |
| U10 | 后台整理的模型用量设每日上限：单位 token，默认每天 1000 万，设置里可改，可设为不限；当天用完即暂停，次日继续；只统计后台整理，用户自己在对话里使用管家不受限；审查调用计入 | 后台无人值守，花的是管理员自己的密钥；修订 S15 的“不做用量上限”，只针对后台整理 |
| U11 | 审查模型与整理用的模型相同时，后台整理照常自动执行，设置里提示“建议另选一个审查模型” | 审查是全新上下文的独立调用，只看后端生成的证据与前后值；自动修改全部可撤销；强制两个模型会让单模型用户用不上 |
| U12 | 自动整理默认关，由管理员打开；一个总开关加各源的分开关；模型那层只在管理员配置了模型时才跑，没配就只做程序能确定的部分。不设定时，后台按缺口持续处理，扫描进行时让路。打开开关时存量曲库一次全进队列，受外部源限速与每日上限约束，进度可见，可暂停。匹配不上的记为“已尝试”，文件变了或匹配规则升级后才再试 | 打开后会向外部服务发查询词并使用管理员的密钥，这一步由人来做；之后不再问 |

规划时由主代理取的默认值（审阅最终摘要时可改；界面形态在界面子任务里用原型另行确认）：

- 用户亲手改的，以及用户在对话里让管家改的，都算人工修正；只有后台自动整理的产出写在自动层。现有对话与 MCP 的行为不变。
- 用户撤销过的自动修改不会被再次自动应用；用户处理例外时选“不采纳”的同理。
- 外部封面与外部歌词首版只补空缺：本地有封面或歌词时不替换。
- 模型后台判断复用管家的运行、方案与审查，每批待定项是一个归管理员所有、标为自动整理的会话，可以点开看过程，也可以接着对话纠正。
- 例外（审查转人工或没通过的项）有自己的持久队列，不随方案 24 小时过期。
- 后台整理全实例同一时刻只跑一个模型运行。
- 外部下载的封面、指纹与查询缓存放在 `/data` 下，属于可重新获取的数据，不进备份。

## 原则（替换架构文档的旧表述）

替换 `docs/architecture/architecture-decisions.md`“扩展边界的两步走”中“产出只作为候选或证据”的表述
（原文标注为指导原则，立项时须复核）：

1. 三层分工：程序判定能确定的 → 模型判断程序拿不准的 → 人只处理模型上交或判断不了的。
2. 默认自动，例外才问人：程序和模型能定的直接生效，不进待确认队列。
3. 安全靠事后可撤，不靠事前确认：每次自动修改有记录、依据与来源，可单条撤销，也可按批或按来源撤销。
4. 人工修正永远优先：用户亲手改过的，程序和模型都不再改。
5. 音乐文件只读。
6. 能力由宿主分配：外部源只拿到自己那类能力的口子，不能自行取得其他权限。

## 跨子任务验收

用合成曲库验收，曲库覆盖 U7 列出的各种形态；外部源在自动化测试里用受控的本地服务代替，不请求真实服务。

- [x] V1 总开关关闭时，后端不向任何外部源发请求，也不发起后台的模型调用。（`TestPostgreSQLCurationSourcesGate`、`TestPostgreSQLCurationProgramGates`、`TestPostgreSQLCurationDisabledBeforeFirstEnable`）
- [x] V2 打开开关、不配置模型：扫描后不需要任何人工操作，能匹配上的发行补上了封面、歌词和空的字段，建立了外部对应；每一项在整理记录里有来源与依据。（`TestPostgreSQLCurationProgramEndToEnd`、`TestPostgreSQLCurationScannedAlbumProvenance`）
- [x] V3 人工修正过的字段，自动整理给出不同的值时，显示的仍是人工的值；清除人工修正后显示自动层的值；再清除自动层后显示扫描值。（`TestPostgreSQLCurationFieldPriority`）
- [x] V4 按批撤销后，这一批改过的字段、封面、歌词回到这一批之前的状态；这一批之后有人工修改的发行同样能撤。（`TestPostgreSQLCurationBatchRevert`、`TestPostgreSQLExternalScopeRevert`、`TestPostgreSQLCurationBatchRevertKeepsManualEdit`）
- [x] V5 撤销过的自动修改，在之后的整理里不会再次出现；重扫不清掉自动层、外部封面、外部歌词和外部对应。（`TestPostgreSQLCurationSuppression`、`TestPostgreSQLCurationRescan`、`TestPostgreSQLExternalArtworkRescan`、`TestPostgreSQLCurationTrackAutoSurvivesRescan`）
- [x] V6 配置模型后：程序拿不准的项由模型提出修改，审查通过的自动执行；审查转人工或没通过的出现在例外队列，采纳后执行，不采纳后不再提出。（`TestPostgreSQLCurationModelReviewPaths`、`TestPostgreSQLCurationExceptionAcceptDecline`、`TestPostgreSQLCurationExceptionMergeAcceptDecline`）
