# 外部数据源与自动整理：总体设计

本文件给出父任务层面的边界、数据流与关键取舍。表名、字段、接口路径在这里只到“形状”，
确切定义由各子任务自己的设计给出；子任务规划时发现与本文冲突的，回到本文修订。

## 一、三层分工的落点

```text
扫描（现有，不变）
  └─ 扫描值、字段决定、归组证据、标签里的外部标识（新）
        │
        ▼
程序层：匹配与补全（新，curation）
  ├─ 从外部源取候选（sources）
  ├─ 把握足够 → 建立外部对应、写自动层、取封面与歌词
  └─ 拿不准 → 待定项
        │
        ▼
模型层：后台判断（新，复用管家运行时）
  ├─ 模型对待定项提出修改（方案）
  ├─ 独立审查（证据含程序收集的外部资料）
  ├─ 通过 → 经 operations.Run 写自动层或执行结构操作
  └─ 转人工、没通过 → 例外队列
        │
        ▼
人：整理记录（看改了什么、撤销）与例外（采纳或不采纳）
```

三层共用一条写入路径：所有持久修改经 `operations.Run`，带来源与批次。程序层和模型层的区别只在“谁做的判断”，
不在“怎么写”。

## 二、分层与优先顺序

现有两层（扫描值、修正）变成三层：

| 层 | 谁写 | 例子 |
| --- | --- | --- |
| 人工修正 | 用户亲手改；用户在对话或 MCP 里让管家改 | 现有 `release_corrections` 等，行为不变 |
| 自动层（新） | 后台自动整理：程序与模型 | 外部源给的年份、模型判断的标题写法 |
| 扫描值 | 扫描 | 现有 `releases` 等的列 |

有效值 = 人工修正 → 自动层 → 扫描值，逐字段取第一个有值的。

结构保证沿用现有做法并延伸一层：扫描只写扫描列；自动整理只写自动层；人工修正只由人工路径写。
三者互不覆盖，优先顺序只在读取时体现。因此：

- “人工修正永远优先”不依赖任何运行时判断，自动写入的执行器根本不接触人工修正的行。
- 用户清除人工修正后，显示的是自动层的值（如果有），再往下才是扫描值。

各类数据在自动层的形态：

| 数据 | 自动层的形态 | 首版规则 |
| --- | --- | --- |
| 发行级八个字段 | 每个发行每个字段至多一行，带来源与写入它的操作 | 程序只补空缺；改已有值由模型判断 |
| 曲目标题、曲目艺人（子任务 I） | 同上，按曲目 | 同上；同时新建曲目的人工修正层 |
| 外部对应 | 本地实体（发行、专辑、曲目、艺人）与外部 ID 的对应，带匹配方式、把握程度、状态 | 一个本地实体在一个源里至多一个生效的对应 |
| 封面 | 外部下载的封面单独存放，不占本地封面的位置 | 只补空缺：本地有封面时不用外部的；扫描不删除外部封面 |
| 歌词 | 外部歌词单独存放，不写进扫描覆盖的那两列 | 只补空缺：本地有歌词时不用外部的 |
| 结构操作（归组、默认版本、核对、认领、艺人合并改名、发行合并拆分） | 不是字段值，没有“层”；靠操作记录的来源区分人工与自动 | 见第四节 |

自动层内部只有一行：程序先写、模型后来改写同一字段时，后写的替换先写的，前一个值留在操作记录里。

## 三、记录、批次与撤销

### 记录

- 操作者：开启自动整理的管理员（U5）。`operations.actor_id` 的约束不变，不新造系统用户。
- 来源：`origin.source` 增加“自动整理”一种取值，并记下是哪个外部源或模型、哪一批、对应的待定项。
- 批次（新）：一次后台整理的一段连续工作是一批（程序层按时间或数量切，模型层一次运行是一批）。
  批次有自己的表，存起止时间、层（程序或模型）、各类改动的数量、用量。操作记录带批次。
- 操作记录的读取增加按来源、按批次筛选。

### 撤销

现有撤销要求“目标的版本号等于这条操作留下的版本号”，同一发行上之后的任何修改都会让更早的操作撤不了。
自动修改不能沿用这条规则，否则用户改过一次之后整批就撤不了。

自动层的撤销改为按“这一格还是不是我写的”判断：

- 自动层的每一行记着写入它的操作。撤销一条自动修改时，如果这一格现在仍是这条操作写的，就恢复到它之前的自动层状态
  （之前的值或没有）；如果已经被更晚的自动修改改写，返回冲突，不动。
- 人工修正在另一层，不参与判断。用户之后改了同一发行的任何字段，都不妨碍撤销自动层。
- 自动层的写入不递增发行的 `edit_revision`，因此也不会让人工修改的撤销失效。

按批撤销 = 按时间倒序逐条撤销这一批里仍可撤的操作，返回撤了多少、跳过多少及原因。按来源撤销同理，范围换成某个来源。
它们是普通的受治理操作，自己也有记录。

结构操作的撤销沿用各自现有的规则（版本号核对）。之后被人工改过的结构，自动撤销会被拒绝并在结果里列出，
这是对的：人已经在这个结构上做了新的决定。

### 撤销之后不再应用

用户撤销一条自动修改，等于表达“这个改动不对”。记下一条“不再提出”的标记（目标、哪一格或哪种结构操作、被撤销的值或对象），
程序层与模型层在提出修改前都先查它。例外队列里选“不采纳”写同一种标记。

这个标记只挡同一个改动，不挡同一格上不同的值。用户可以在整理记录里清掉标记。

## 四、结构操作的自动使用

| 操作 | 现状 | 自动使用的条件 |
| --- | --- | --- |
| 问题核对、默认版本、认领 | 可撤销，审查已可放行 | 模型判断，审查通过 |
| 专辑归组（归入、移出） | 可撤销，审查已可放行 | 只在强证据下：两个发行的外部对应指向同一个 release group。程序层可以直接做；模型层提出时证据里必须有这条对应 |
| 艺人合并、改名 | 不可撤销 | 子任务 G 做成可撤销之后。程序层：两个本地艺人的外部对应指向同一个外部艺人 → 合并。其余由模型判断 |
| 艺人拆分、忽略候选 | 不可撤销 | 忽略候选改为可撤销后可自动；拆分不自动提出（它是纠正错误合并的手段，由撤销合并覆盖） |
| 发行合并与拆分（子任务 H） | 不存在 | 只在强证据下：外部对应表明这些曲目属于同一个外部发行（合并），或属于不同的外部发行（拆分）。一律经模型提出并审查，程序层不直接做 |

“强证据”的定义是硬规则，写在后端，不由模型自述：证据必须是已保存的、状态为生效的外部对应。
模型在方案里声称有依据但库里没有对应记录的，审查证据里看不到，后端按规则转人工。

## 五、外部源

### 接口与声明

每个源是一个编进程序的适配器，放在与管家无关的包里（方向：`backend/internal/sources/<源名>`）。
每个源有一份声明，内容至少包括：标识与显示名、提供的能力、启用条件、限速、需要的配置项。

能力是一组窄接口，源按自己的情况实现其中几个：

| 能力 | 输入 | 输出 |
| --- | --- | --- |
| 发行查找 | 外部 ID、条码、厂牌与编号、曲目表（数量与时长）、标题与艺人 | 候选发行（含所属 release group、曲目表、厂牌、日期等） |
| 录音查找 | 外部 ID、ISRC、标题与艺人与时长 | 候选录音与它出现在哪些发行 |
| 艺人查找 | 外部 ID、名字 | 候选艺人（含别名） |
| 指纹识别 | 声学指纹与时长 | 候选录音 ID 与分数 |
| 封面 | 外部发行或 release group 的 ID | 图片清单与下载 |
| 歌词 | 标题、艺人、专辑、时长 | 同步或纯文本歌词 |

首批：MusicBrainz 实现前三种；AcoustID 实现指纹识别；Cover Art Archive 实现封面；LRCLIB 实现歌词。

调用方（程序层的匹配、管家的工具）只面向能力接口，不直接依赖某个源。管家现有的 `search_music_metadata`、
`get_music_metadata` 改为走同一个 MusicBrainz 适配器，工具的名字与输出不变。

### 共用的东西

- 出站客户端：现有 `backend/internal/steward/egress` 已与管家解耦，迁到平台层（方向：`internal/platform/egress`），
  管家与外部源共用。地址策略不变；固定地址的源允许其官方的重定向目标（封面图片实际由 archive.org 提供）。
- 限速：每个源一个全实例的限速器。MusicBrainz 与 Cover Art Archive 的清单请求共用每秒 1 次；
  用户在对话里的查询与后台匹配共用同一个限速器，对话优先。
- 缓存：按请求内容缓存响应，有身份的结果缓存时间长，空结果与失败缓存时间短；放在数据库或 `/data`，由子任务 B1 定。
- 重试：503 与限流按源的要求退避重试，有上限；超过上限记为“稍后再试”，不算匹配失败。
- 源的配置（开关、AcoustID 密钥）是实例级的，由管理员设置；密钥用现有的密钥库加密，按“实例加用途”绑定。

### 发给外部源的数据

| 源 | 发出的内容 |
| --- | --- |
| MusicBrainz | 外部 ID、条码、ISRC、厂牌编号、标题与艺人的查询词、由曲目时长推出的光盘目录 |
| Cover Art Archive | 外部 ID |
| LRCLIB | 曲目标题、艺人、专辑名、时长 |
| AcoustID | 声学指纹与时长 |

不发送音频、文件路径、实例标识。声学指纹是由音频算出的摘要，不能还原音频，但它是音频派生的数据，
ADR 0005 现有“音频字节不发”的条文要补一句说明指纹可以发给 AcoustID。

外部源返回的一切都是不可信文本，进入模型前照现有规则加来源标记。

## 六、程序层：匹配与补全

形状照现有的音频分析：按缺口查询、单线程、扫描进行时让路、失败有重试上限。

每个发行（以及不属于任何多曲发行的单曲）有一条匹配状态：匹配规则的版本、输入的摘要（标识、曲目表、内容指纹）、
状态（未处理、已匹配、拿不准、没匹配上、稍后再试）、尝试次数。规则版本或输入摘要变了才重新处理。

匹配依据按可靠程度排列，前面的命中就不再用后面的：

1. 标签里的外部 ID。
2. 条码；厂牌加编号。
3. 曲目里的 ISRC 集合。
4. 由曲目数与时长推出的光盘目录（整轨抓的 CD）。
5. 声学指纹（AcoustID，子任务 B3 接入后）。
6. 标题、艺人、曲目数与时长的查询：只产生候选，从不直接判定。

“把握足够”的规则是程序层正确性的核心，由子任务 C 逐条定义并用测试固定。方向：必须是唯一候选，
并且有至少一项独立的佐证（曲目数一致、各曲时长在容差内）；有任何相反的证据就降为拿不准。
宁可多交给模型，不可错判。

把握足够时：保存外部对应；补空缺字段到自动层；本地没有封面时取封面；本地没有歌词时取歌词；
符合第四节条件的结构操作直接做。拿不准或没匹配上时：形成待定项，带上候选、本地证据与冲突点。

待定项是持久的工作单元，也是例外队列的载体。状态：等模型、处理中、已解决、等人、已搁置（没配模型或超出上限时停在等模型）。

## 七、模型层：后台判断

### 复用管家运行时

每批待定项对应一个归管理员所有、类型为“自动整理”的管家会话；运行沿用现有的循环、工具、方案与审查。
这样过程完整可见，用户可以点开看模型查了什么、为什么这么判断，也可以接着对话纠正。

需要改动的地方：

| 现状 | 改动 |
| --- | --- |
| 运行只能由登录用户的接口启动 | 增加由后台调度启动的入口；第一条消息由程序生成，内容是这批待定项的摘要 |
| 运行依赖发起者有效的登录会话 | 自动整理的运行改为检查：总开关开着、该管理员仍是启用的管理员、端点与密钥仍在 |
| 会话列表只有一种 | 自动整理的会话不混在用户自己的对话里，从整理记录进入 |
| 模式由用户选 | 固定为 `steward`：必须审查，不能直接执行 |
| 写工具写人工修正 | 自动整理的运行里，字段类写工具写自动层；工具对模型的名字与参数不变，由运行的来源决定落在哪一层 |
| 每用户 3 个并发 | 自动整理全实例一次只跑一个，不占用户自己的并发名额 |
| 用量只有单次运行的上限 | 增加每日上限（U10），审查用量计入；达到上限后不再启动新的运行，正在跑的跑完当前这一步后结束 |

### 审查策略第 2 版

| 规则 | 第 1 版 | 第 2 版 |
| --- | --- | --- |
| 不可撤销项 | 转人工 | 不变。子任务 G、H 完成后，范围内的操作都可撤销 |
| 方案超过 20 项 | 整份转人工 | 后台按批组织待定项，一批的方案项数由调度控制在上限内；超出的拆到下一批，不整份转人工 |
| `approved` 且高风险 | 转人工 | 不变 |
| 审查证据 | 只有本地摘要与前后值 | 增加：程序保存的外部对应与候选摘要（来自数据库，不来自模型的参数），带来源标记 |
| 强证据类操作（归组、发行合并拆分） | 无 | 证据里没有生效的外部对应时，后端直接转人工 |
| 审查不可用 | 不执行 | 不变；后台按退避间隔重试有限次数，仍不可用则待定项停在等模型 |

用户在对话里的 `steward` 模式也改用第 2 版；对话里的行为变化只有“证据里多了外部对应”这一点。

### 例外

审查转人工或没通过的项，记到对应的待定项上（提出的修改、前后值、审查的理由），状态变为等人。
它不依赖方案的 24 小时有效期。管理员采纳时，后端按当时的状态重新校验后执行，记为人工确认的操作，
字段类的写入人工修正；不采纳时写“不再提出”的标记。

## 八、子任务 G、H、I 的要点

- **G 艺人操作可撤销**：合并记录里已经存了前态（每个名字键原来的归属、每条作用域覆盖原来的归属、涉及的旧身份）。
  撤销按这份前态逐项恢复，包括链式重定向与绑定行原来的操作标识，而不是用“拆分并恢复”近似。
  合并期间新产生的收藏等用户数据留在合并后的艺人上。改名的撤销恢复原来的主名意图。
- **I 曲目级字段修正**：照发行级的做法给曲目建修正与有效值，一开始就是三层。曲目艺人的修正要同步生成署名事实，
  与现有专辑艺人修正生成署名事实的做法一致。所有读曲目标题与艺人的地方（列表、搜索、播放队列、歌词匹配、管家工具）改读有效值。
- **H 发行的合并与拆分**：扫描按曲目成员关系认发行。合并与拆分记为人工或自动的“成员归属意图”，扫描落库时尊重它，
  重扫不打回原形。修正、核对、默认版本、收藏的去向在操作时确定并记入前态，撤销按前态恢复。
  这是本任务技术风险最高的一项，子任务规划时先做调研与失败用例清单，再定方案。

## 九、数据与部署

- 迁移全部是新增表、新增列与放宽约束，不改写既有数据；`release_effective` 视图加一层。没有开启自动整理的实例，
  读取结果与现在逐项相同，现有接口样本不变。
- 新增的可写内容都在 `/data` 下：外部封面（沿用现有的内容寻址存储）、查询缓存。它们可以重新获取，不进备份；
  自动层、外部对应、待定项、批次在数据库里，随数据库备份。
- 生产镜像增加 Chromaprint（子任务 B3）。同步 `scripts/check-production-compose.sh` 与发布检查。
  没有 Chromaprint 或没填密钥时，AcoustID 这个源显示为未启用，其余功能不受影响。
- 回退：关掉总开关即停止一切后台请求与写入；已写入的自动层可以按来源整体撤销。迁移不需要回退脚本。

## 十一、主要取舍

| 取舍 | 选择 | 放弃的做法与原因 |
| --- | --- | --- |
| 自动产出放哪 | 独立的自动层 | 在现有修正表上加作者列：一格只有一行，自动与人工会互相覆盖，优先顺序要靠运行时判断 |
| 自动层的撤销 | 按“这一格是不是我写的” | 沿用版本号：用户改一次就让整批撤不了 |
| 后台运行的身份 | 开启它的管理员 | 系统用户加共享密钥：推翻 S15，多一套密钥管理 |
| 模型层的实现 | 复用管家运行时 | 另写一条“一次调用出结论”的流水线：省 token，但过程不可见、不能接着对话纠正，审查与工具要重做一遍。子任务 D 实测消耗后可再评估 |
| 例外的载体 | 待定项自己持久 | 沿用会话里的待确认方案：24 小时过期，发新消息即作废 |
| 外部封面与歌词 | 首版只补空缺 | 允许替换本地的：要定“哪张更好”的规则，容易引起争议，放到以后 |
| 外部源的形态 | 内置适配器 | 插件宿主：没有第三方源的需求（U4） |

## 十二、已知风险

- 外部源对华语与冷门录音的覆盖可能不足，这些内容主要靠模型层；实际匹配比例要到 V12 的真实试用才知道。
- 复用管家运行时的 token 消耗可能偏高；每日上限兜住费用，但会拖慢存量曲库的首次整理。
- 存量曲库首次整理受 MusicBrainz 每秒 1 次的限制，几千张专辑需要数小时到数天。
- Alpine 的 `chromaprint` 包是否带命令行工具未确认；不带的话子任务 B3 要改用库或自行构建。
- 由曲目时长推出光盘目录去查 MusicBrainz 的做法未经验证，子任务 B1 规划时核实，不可行就去掉这一条依据。
- 发行合并与拆分与扫描的身份规则直接相互作用，是最可能返工的一项。
