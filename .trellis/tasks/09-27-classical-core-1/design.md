# 总体架构候选方案

## 定位

本文承接上一轮建议，供 M0 整理和后续子任务研究，不宣称这些能力或依赖已经存在。
当前事实以[基线记录](../archive/2026-09/09-27-classical-m0-alignment/research/baseline.md)为准。

## 能力边界

- 前端：保留 React、TypeScript、Vite 与边界解码；应用外壳组合 auth、catalog、library、player、curation、operations 等能力。
- 后端：保留单进程模块化单体；按真实职责向 `internal/` 拆分，不为目录对称性预建空层。
- 数据：扫描观察、用户修正、有效展示值分开；catalog 拥有 ReleaseGroup/Release/Medium/Track 规则。
- 操作：整理、人类管理和未来 Steward 提案复用后端权限、变更集、日志与恢复合同。
- 播放：player 拥有队列和播放生命周期；媒体读取复用受限路径与会话授权；源音频不被改写。
- 个人数据：服务端按用户隔离，与共享资料库治理审批区分。

## 建议的数据流

```text
扫描观察 ───────────────┐
                       ├─ catalog 有效读模型 → REST → 边界解码 → 页面
用户/Steward 提案 → 授权与审批 → 修正覆盖层 ────┘
                         └─ 操作日志 / 最小恢复信息

播放器 → 受保护曲目接口 → 安全文件读取 / 派生转码缓存 → 浏览器音频
```

扫描产生的观察不伪装成逐字段变更集；只有支持恢复的操作才能展示恢复点。
跨模块只使用公开类型合同或窄接口，不直接依赖对方的私有表和适配器。

## 需由 ADR 评审的四类候选

| 决策主题 | 上轮建议 | 进入实施前需澄清 |
| --- | --- | --- |
| 前端依赖与状态 | TanStack Router / Query、CSS Modules、自托管字体 | 当前需求、替代方案、兼容版本与锁定方式、Cookie/URL/decoder 边界 |
| 修正覆盖层 | 扫描值与用户修正分离，展示有效值 | 稳定身份、重扫/重命名/重新分组映射、字段清除语义和冲突策略 |
| 通用操作记录 | 变更集、审批、检查点、逆操作 | 操作风险、权限、revision/幂等、撤销链原子性、不可逆与冲突拒绝 |
| 媒体处理 | 受保护串流与 ffmpeg 派生缓存 | 浏览器能力、Range/拖动、CUE 边界、缓存失效、资源限额与许可证审查 |

`candidate_anchor` 和 `source_identity` 依赖路径，不保证重命名、移动或重新分组后的稳定性。

实体 UUID 上。直出格式与转码策略仍需兼容性证据，不将格式名称等同于所有浏览器支持。

## 兼容与交付

- M1a 沿用现有 API；M1b 使用阶段 I 的 ReleaseGroup 只读接口，初期一组一个版本，不伪造聚合。
- B0 是独立的行为保持重构（catalog 先拆）；新接口、数据库迁移分别属于阶段 I 等行为变更，
  `/api/` 404 与目录幂等指纹由 F1、F2 单独修复，均有回归测试。
- 已共享迁移不改写；未来数据模型仅通过批准的新迁移演进。
- 每个阶段都保留可用的已交付路径；功能未完成时隐藏或明确禁用，不展示虚假成功。
- 回退按子任务确定：代码可独立撤回，数据库依仓库既有备份/前向修复合同，不预设 down migration。
