## 2. 样本与标注

每个样本一条记录，字段：

- `id`、`shape`（形态，见下表）、`negative`（是否反例）、`program_decidable`（按现有设计程序应能定的）。
- `local`：本地文件。目录名、格式（FLAC 为主，少量 MP3、M4A）、每首的标签（标题、艺人、专辑、专辑艺人、曲号、碟号、条码、目录号、ISRC、各类 MusicBrainz ID）与时长；可以没有任何标签；可以带 CUE 整轨。
- `external`：这个样本向受控服务提供的外部数据（发行、发行组、录音、艺人与别名、搜索命中）。不提供即外部库未收录。
- `expect`：期望结果。外部对应（发行编号、发行组编号、录音编号，或“不应建立”）、应写入的字段值、应发生的艺人合并与专辑归组、不应发生的合并与修改。

形态与最低样本数（总数 60 到 100 张专辑，另加散放单曲）：

| 形态 | 最低数 |
| --- | --- |
| 整轨 CD 带 CUE | 4 |
| Picard 打过标签（带 MusicBrainz ID） | 6 |
| 流媒体下载的专辑（标签完整，无条码、目录号、ISRC） | 15 |
| 流媒体下载的散放单曲 | 8 |
| 带条码或目录号 | 6 |
| 标签很差或没有标签（含文件名形如“01 - 艺人 - 曲名”的） | 8 |
| 华语（含繁简不同写法） | 10 |
| 合辑与古典 | 6 |
| 别名艺人（“Jay Chou”与“周杰伦”两边都有专辑） | 1 组 |
| 专辑名有错字、外部源有这张专辑 | 3 |
| 同一专辑的多个版本（同一发行组） | 3 组 |
| 外部源未收录 | 6 |
| 反例（父任务 V17 列出的六类） | 每类至少 2 |

受控服务的外部数据要贴近 MusicBrainz 的真实形态：同一发行组下多个版本、曲目数不同的版本、搜索结果超过 25 条的常见标题、
艺人别名只在别名里登记。

## 3. 受控服务

- 计数：每个来源、每个端点种类（MusicBrainz 分搜索、按编号读取、ISRC、光盘目录、浏览；封面分清单与图片）累计计数，
  由 `GET /_mock/counters` 读取、`DELETE /_mock/counters` 清零。现有的 500 条环形日志保留。
- 503 注入：新增按速率的情景，同一来源两次请求间隔小于设定值时返回 503 并带 `Retry-After`，用来模拟 MusicBrainz 的限流。默认关闭，度量的主结果不开。
- 外部数据从回归曲库生成，用 `-data` 指定的目录或测试里直接构造服务时传入。

## 4. 受控的模型端点

度量用测试里的模型端点（不用固定脚本），两种模式：

- `oracle`：知道标注，按标注给出正确答案——读待定项、对“可解决”的项提交标注里的外部编号、其余搁置；审查一律按标注判断（错误的提案不通过）。
  度量的是管线在模型理想时能做到的完成比例，以及程序层自身的错误。
- `first_candidate`：沿用现有默认脚本的行为（选第一个候选，审查一律通过），度量模型不可靠时错误能漏进多少。

token 按请求与响应正文的字节数除以 4 计算并写进响应的用量字段，结果是确定的估算值，汇报时注明。
调用按种类分开计数：待定项批次的运行步、审查、艺人身份（网络搜索）、其它。

## 5. 驱动与排空

- 程序层用现有的可注入时钟推进；模型调度器用同一时钟或直接触发。循环推进，直到程序层没有可做的项、模型层没有可领取的项，且一整轮没有新的写入；
  轮数设上限，超过上限算作测试失败并输出停在哪里。
- MusicBrainz 限速器在度量里不按真实时间等待（否则百张专辑要几分钟）；请求数照常计数，耗时按“MusicBrainz 请求数 × 1 秒”另行估算。
- AcoustID 关闭：合成的静音音频声纹相同，不能用来度量。度量结果里注明声纹未覆盖。

## 6. 度量的定义

按形态汇总，另给全体合计：

| 度量 | 定义 |
| --- | --- |
| 外部请求数 | 每张专辑平均、最多；按来源与端点分开 |
| 估算耗时 | MusicBrainz 请求数 × 1 秒 |
| 进入模型的项数 | 建过待定项的发行与曲目数 |
| 模型调用与 token | 按种类分开 |
| 不需要人处理的完成比例 | 排空后结果与标注一致、且没有未结束的待定项或例外的样本所占比例；标注为“保持本地原样”的样本，没有写入即算完成 |
| 等人处理的数量 | 排空后仍未结束的待定项与例外 |
| 错连 | 建立了与标注不同的外部对应，或标注为“不应建立”的建立了 |
| 错并 | 发生了标注之外的艺人合并、专辑归组、发行合并 |
| 错改 | 自动层写入了与标注不同的值，或改了标注为“不应改”的值 |
| 程序可定的进模型数 | 标注为程序可定的样本里进入模型的数量 |

输出：测试日志里一张汇总表；设置 `ROOMUSIC_CURATION_METRICS_OUT` 时另写一份 JSON。度量的数值不作为测试断言
（基线本身就有错误），测试只在驱动失败、样本生成失败或排空超时时失败。重复运行两次，JSON 除耗时外应完全相同。

## 7. 实测工具

`roomusic-curation-bench`，只发少量真实请求，用程序自己的 MusicBrainz 客户端与标识：

- `mb-rate`：按程序的限速器连续发 N 个（默认 60）读取请求，记录成功数、503 数、实际成功速度。
- `tolerance`：取一组公开的发行组（华语、欧美流行、古典、电子各若干），读出每个发行组下的全部版本与曲目时长，
  对曲目数相同的版本两两比较，统计不同容差（现行 max(3 秒, 1%)、±4 秒、±2 秒）下“可比时长全部在容差内”的比例。
- `real-corpus`：按一份提交在仓库里的清单（MusicBrainz 发行编号加本地改动：去掉条码、加错字、去掉标签等）读出真实的标签与时长，
  在指定目录生成静音的合成曲库。生成的文件放 `temp/`，不提交。

请求只含公开的专辑与艺人名或编号，不含任何本地曲库的信息。
