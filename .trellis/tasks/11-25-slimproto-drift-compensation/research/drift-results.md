# SlimProto 服务器端漂移补偿实测

## 环境与口径

两台 Squeezelite 2.0.0-1613 在独立 Compose 网络内播放合成 FLAC，PCM 写到宿主机 FIFO。读端按单调时钟和采样率记录计划出声时间。同步套件每秒配对一次脉冲，以两台出声时刻差的绝对值统计 p50、p95、峰值。修正命令分别统计跳帧 `strm a` 和有正间隔的静音 `strm p`。用户主动暂停的零间隔 `strm p` 单独排除。

## +800 ppm 可听性与逐帧核对

`sg docker -c scripts/test-slimproto-skip.sh` 退出码 1。独立 Compose 项目为 `roomusic-compose-test-slimproto-skip-kscxqxil2j`。原始 PCM、每块的时刻、`report.json` 和试听文件保存在 `temp/slimproto-skip/20261125T082011.816699336Z/`。

主设备的 4,101,300 个双声道帧与 93 秒合成源逐字节一致。成员共 **1,315 次插帧、253 次删帧**，全部 1,568 个调整点都满足 24 位双声道整数均值，最小相邻调整间隔为 2,000 个输出帧，首次调整位于源时间 20.759 秒。独立于日志，PCM 比对还发现两段各 882 帧的静音，与成员两条 20 ms 的 `strm p` 时长一致。所有设备合计 `strm a` 0 次，主设备 `strm p` 0 次。

每段以 31 个整秒的相同源帧作同步采样。对**每一个**调整点，取左声道插值样本与前、后样本绝对差中的较大者，除以该段源相邻差的 p99。以该点为中心，在 441 帧 Hann 窗内测量 8 kHz 以上的能量，与该段每秒中点窗口的平均能量比较。右声道额外带有合成位置标记，参与逐帧校验。表中超限数依次为跳变、高频能量。

| 信号 | p50 / p95 / 峰值（ms） | 插 / 删 | 成员 strm a / p | 最差跳变 / p99 | 最差高频增量 | 超限数 | 可听性指标 |
| --- | --- | ---: | ---: | ---: | ---: | ---: | --- |
| 正弦 | 10.734 / 19.047 / 19.348 | 195 / 24 | 0 / 0 | 1.499 倍 | +56.937 dB | 12 / 219 | 失败 |
| 和弦 | 5.359 / 20.251 / 20.552 | 518 / 166 | 0 / 1 | 1.921 倍 | +63.143 dB | 14 / 684 | 失败 |

**补偿能力与硬修正。** `drift_frames.go` 的最小间隔限制了每秒最多约 500 ppm 的补偿。在 +800 ppm 的 93 秒里，即使从首帧就连续插帧，从零偏差起算仍会积累约 27.9 ms。当前 `group_timing.go` 的 `correct` 在绝对偏差超过 20 ms 时会发送硬修正，因而这组验收条件与持续补偿上限存在冲突。本次两段静音分别位于源时间约 34.73 秒和 71.22 秒。

**可听性指标。** 最差点在和弦段的源帧 2,437,527，恰好是删帧点。该点的均值正确，左右两边较大的一跳为段内 p99 的 1.921 倍，8 kHz 以上能量高出 63.143 dB。对应实现为 `backend/internal/playback/render/drift_frames.go` 的 `adjustPCM`：将相邻两帧合成一个均值样本时，该点与相邻未改样本的间隔相当于约 1.5 个原采样周期；插入均值时，局部步长也会改变。两端的斜率变化在低高频底噪的正弦、和弦上产生明显的高频增量。这里判定的是指定的信号指标，没有进行主观盲听。

### +300 ppm 可听性与录音核对

`sg docker -c scripts/test-slimproto-skip.sh` 退出 1，临时项目 `roomusic-compose-test-slimproto-skip-qoeefiy9ud`。主设备的 4,101,300 帧双声道全部与源相等。主设备读端欠载 2 次（6.179、11.009 ms），成员欠载 0 次。主设备无硬修正；成员收到 1 条 20 ms 的正间隔 `strm p`，无 `strm a`。命令后 47.719 ms，成员录音的第 2,738,661 帧开始出现 882 帧数字静音，位于和弦调整块内。

首次分析遇到这段静音，无法将块尾与源对齐。补齐夹具对录音中协议静音的识别后，直接在原录音运行 `python3 -Bu scripts/slimproto/skip-analysis.py analyze temp/slimproto-skip/20261125T084559.709765990Z`，退出 1，三个信号的跳变与成员静音均保留为失败。块定位跨过已验证的静音，测量跳变、频谱、同步与导出 WAV 均使用原录音时间轴。命令日志在 `temp/drift-round2-skip.log` 与 `temp/drift-round2-skip-analysis.log`。

## 欠载定因

**无漂移持续播放的欠载来自宿主机 FIFO 夹具。** 读线程晚醒后按原采样时钟追读。旧实现只要看见当下管道为空，就把本次读取完成时间相对计划出声时间的全部迟到算成欠载，并据此重置该台时钟。两台各自重置的时长差会进入脉冲偏差和播放器位置回报。

### 供流与调度证据

在补偿分支无漂移段采集两台真实播放器的上行 STAT。三次 FIFO 欠载前后的相邻 STMt，解码输出缓冲均至少有 3,309,568 字节（44.1 kHz、8 字节/帧时约 9.38 秒），压缩流缓冲至少有 234,710 字节。播放器固定版本的 stdout 输出线程在解码缓冲为空时也会写静音。成员调整路径可以改变脉冲间的帧数；本轮主设备扣除 FIFO 重置后，239 个间隔均为 44,100 帧。成员相邻间隔为 44,078–44,123 帧，累计净多 529 帧，这是脉冲间的净量，不能换算为 Adjust 调用次数。

编组正常播放时，协调器采用主设备的位置回报推进渲染播放头，`pruneEncodedLocked` 按已过的 PCM 检查点推进 `encodedPlayed`。`waitToRender` 使用 20 秒领先额度及少于 64 KiB 未播编码字节的进料例外。分发器从共享 Body 持续读取，超过保留上限会剔除落后的读者。成员独立解码、补偿与编码，两端 ffmpeg 输出都启用 `-flush_packets 1`。本轮主、成员均保持可读的输出缓冲，分发器没有剔除设备。

按 cgroup 的 CPU 使用时间差计，无漂移段 main 的应用及其两个 ffmpeg 合计占单核 2.86%（覆盖 186.6 秒），分支的应用及四个 ffmpeg 占 4.15%（覆盖 238.7 秒）。两轮应用及播放器的 CPU 配额节流计数增量均为 0。整段宿主机 CPU 空闲分别为 89.78% 和 80.97%。分支首次欠载所在 0.502 秒内，空闲降至 15.59%，虚机 steal 为 8.96%；两台 Python 读端的 `/proc/<pid>/schedstat` 运行队列等待分别增加 88.72、66.76 ms。另两次事件所在半秒，实际欠载一侧分别累计等待 23.35、21.52 ms。这些是采样窗口的累计量，单次唤醒的精确迟到时间不可从该计数还原。第二、三轮的旧事件也只记录总迟到，无法逐次拆出读端等待调度与写端补页各占多少。

### 独立 FIFO 复现与修复

用 `python3 -B temp/underrun-diagnosis/probe.py <读端脚本>` 单独驱动读端和合成 PCM 写端。只暂停读进程 200 ms，写端继续每 2 ms 提供 512 帧（每块足以播放 11.61 ms），管满时由内核背压。旧代码在追读时把实测阻塞 **1.578 ms** 的一次 read 记成 **178.435 ms** 欠载。只扩大缓冲并增大读块的对照仍把 **1.996 ms** 记成 **138.825 ms**。这条复现路径不需要 ROOMusic、编组、ffmpeg 或漂移。

最终修复位于 `scripts/slimproto/sync-clock.py`，使用原有的 4 KiB FIFO 和 64 帧读块，继续按采样率和 ppm 计算每帧的出声纳秒。追读过期的帧直接读取。时钟只累计观察到空管道后实际等待 PCM 的时间，以上述帧相对计划的迟到为上限，再扣除收到的 PCM 可覆盖的时长。累计欠供超过原有 5 ms 才移动计划出声时刻，移动量等于已确认的欠供时间。

先用 8 KiB FIFO 和 256 帧读块尝试了同一等待记账。该候选在独立对照中只暂停读端时收到全部 30,720 帧，欠载 0 次。暂停写端 200 ms 则记录 173.203 ms 欠载；空管道启动后延迟约 8 ms 供数，记录 8.153 ms；每 2 ms 仅提供 64 帧时，连续约 2 ms 的短读等待累计触发欠载 35 次，完整收到 19,200 帧。逐次数据见 `before-probe.jsonl`、`buffer-only-probe.jsonl`、`clock-candidate-probe.jsonl`。同步、漂移、硬修正、排除窗口和脉冲配对的验收代码均沿用各自版本。
