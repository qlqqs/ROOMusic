# ④ 增量扫描

父任务：[扫描子系统对标](../11-08-scan-reference-port/prd.md)，S 线第 3 项。对照依据：[gap-analysis.md](../11-08-scan-reference-port/research/gap-analysis.md) G9；参考设计 6.3、6.6、12.5、20 章（单调标记、算法版本化、保守取向）。

## 目标

库里大部分文件没变时，重扫只做必要的工作：没变的文件不再打开解析，没变的专辑不再重写，重扫时间从“和首扫差不多”降到主要花在遍历目录上。

## 现状

- 每次重扫都对每个文件调用 `ParseAudioFile`（`backend/internal/library/scanner.go:454`），内嵌封面也每次写进暂存表。
- 只有内容指纹会复用：来源身份匹配且 size、mtime 都相等（`backend/internal/catalog/ingest/identity_plan.go:167-179`）。目录改名后来源身份变了，下面的文件要全部重算指纹；MP3、M4A、WAV 和 MD5 为零的 FLAC 要把整段音频读一遍（`identity_plan.go:205-209`）。
- 每个候选每次扫描都在独立事务里替换 current decisions、grouping evidence、credits 和 track observations（`library-scan-contracts.md:62-64,81`），organizer 在规划和写入阶段各跑一遍（`scanner.go:724-769`）。
- size、mtime 来自 `os.Stat`，暂存时 mtime 截断到微秒（`backend/internal/catalog/ingest/staging.go:65-70`）。
- 没有“强制完整重扫”的入口；扫描入口只有 `POST /api/v1/scans`（`backend/internal/library/httpapi/scans.go:12-34`）。

## 需求

- **R1 跳过未变文件的解析**：上一次成功写入的观察结果持久保存。本次遍历时来源身份、size、mtime 和解析器版本都相同，就直接用保存的结果，不打开文件；任一项不同就重新解析。CUE 虚拟轨要求 sheet 和父音频文件都没变。
- **R2 解析器版本号**：解析结果的结构或规则改变时升版本，升版本后的下一次扫描对受影响格式重新解析。版本号随代码维护，写进合同。
- **R3 归组算法版本号与未变候选跳过**：一个候选的全部成员观察都没变、归组算法版本也没变时，跳过该候选的写入（含封面重新发现，封面文件本身的 size/mtime 变化要能被发现）。升归组算法版本后的下一次扫描全部重写。
- **R4 改名与移动时复用指纹**：文件被移动或目录改名后，若能以足够强的条件（至少 size + mtime + 文件名都一致，且在本 root 消失曲目中唯一）对上原曲目，复用其指纹，不再整段读文件。定稿条件：文件名 + 大小 + 修改时间相同，且旧侧（本根 present、未被本轮匹配）与新侧各恰好一个文件；对不上的照常计算（design 3.6）。
- **R5 完整重扫**：扫描按钮旁提供“完整重扫”，忽略观察缓存与候选跳过，每个文件重新读取；仍走同一个扫描入口与协调锁，扫描记录里标明是完整重扫。
- **R6 正确性不变**：曲目身份、Release 沿用、missing 对账、诊断、扫描反馈计数与现在一致；跳过只是不重复做相同的工作。
- **R7 合同同步**：更新 `library-scan-contracts.md` 与 `scan-feedback-contracts.md`（“读取标签”阶段的计数口径可能变化）。

## 验收

- 单测与集成测试：未变文件不调用解析器；改了标签（mtime 变）会重新解析；升解析器版本后重新解析；候选跳过与升归组版本后的全量重写；改名、移动后指纹复用且曲目 UUID 不变；对不上时照常计算。
- 真实库只读 smoke：同一份库连续扫两次，记录两次耗时与解析调用次数；第二次未变文件的解析次数为 0。

## 不做

- 内存目录树缓存与磁盘换出、降精度时间戳比较、实时文件监听（理由见 gap-analysis §4）。
- 三点采样指纹（破坏“身份与标签无关”）。

## 已裁决

- 2026-11-08 用户裁决：提供完整重扫入口（R5）。
- 2026-11-08 主会话裁决（设计审阅）：解析缓存不存封面字节，需要重写候选时现读文件取内嵌封面；完整重扫保留“大小和时间没变就复用已存指纹”。缓存容量不另估：真实库只有 284 个音频文件。
