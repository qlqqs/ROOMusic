# DSP 处理链与服务端渲染

父任务：[音频算法对标](../11-08-audio-dsp-reference-port/prd.md)。参考稿（本机 `~/.local/share/roomusic-reference/reference-design.md`） §2.4、§5.7、§6.1、§6.5、§6.6（Headroom）、§6.10、§7.1–§7.5。算法默认照参考稿的参数和公式实现，只有确信同样好或更好时才偏离，并写明理由。所有算法只在后端（Go）实现（父任务 A1）。

## 目标

在后端建起一条拉取式处理链，把“解码 → 电平化 → 处理 → 定点编码”的结果作为一条跨曲目连续的无损流，交付给播放区的输出端。其他算法子任务都是挂在这条链上的节点。

## 需求

- **P1 装配顺序**：照参考稿 §6.1 的十步固定顺序装配，第一批装 ① Headroom、⑧ 位深转换与抖动、⑨ 声道映射（恒等）；② 兼容性采样率转换与 ③ 降混第一批暂由 ffmpeg 完成、信号路径照样标出，第二批换成链内节点；⑤ 用户处理项链（PEQ、卷积，按用户配置的顺序）第二批装。电平化增益在进入处理链前按曲施加（§2.4）。开始播放或修改处理配置时重建整条链，300 ms 去抖在播放区线；“自动模式下最小间隔 1 s”第一批没有触发来源，不实现（父设计 §5.3）。
- **P2 拉取模型与量子**：唯一取帧入口按 §7.1 的顺序工作（确保当前曲目就绪 → 格式检查 → 淡化截断 → 读样本 → 混音 → 异常映射 → 短读换轨 → 上报位置），处理量子是 `采样率/5`（200 ms，§7.2）。
- **P3 解码**：用现有 ffmpeg 解码成 PCM。输入是已安全打开的文件，定位用输入侧 `-ss`（偏离参考稿 §5.7 的“输入永远是管道、定位重开解码器”，理由见父设计 §10：本地文件可定位，部分容器需要定位才能解）。参考稿 §14 第 4、5 条列为已知限制的“外部解码无超时、无并发上限”在这里补上（偏离理由：参考稿自己建议这样改）。
- **P4 预缓冲**：10 s 环形缓冲，填到 33% 即可起播；起播等待期间不计入处理速度（§7.3）。
- **P5 位置**：按 §7.4 的未来事件队列上报位置：每条事件带流帧号，到达播放头才派发；每 200 ms 一条 Time 事件，跨块时补插；自然结束时补发剩余事件，错误结束时清空。
- **P6 电平化移到后端**：现有 `frontend/src/features/player/engine/leveling.ts` 的增益选择规则搬到后端（Off/Track/Album/Auto、目标 −14 LUFS、提升时真峰值留 0.5 dB（现行规则不变，`backend/internal/playback/analysis/analysis.go:21`）、响度未知时固定 −5 dB）。渲染流里按 §6.5 以“增益区域”随缓冲区传递，在重采样等节点按比例搬运，施加后清空，避免重复施加。
- **P7 Headroom**：默认 −3.0 dB，范围 −30…0，步进 0.1，默认关闭；启用后强制走浮点链（§6.6）。
- **P8 削波与处理速度**：按 §6.10 实现。削波只在位深转换、截断/抖动、SDM 三处统计，是否统计由 Headroom 项的“削波指示”开关决定；显示窗口 450 ms，250 ms 定时器复评；处理速度 = 累计音频时长 / 累计墙钟时长，量化到 0.1，最快 1 s 上报一次。
- **P9 交付**：所有播放都走渲染流。无损档按输出端声明的能力协商格式（FLAC/WAV、位深、采样率）；有损档由服务端编成 Opus 或 AAC（按输出端能解的选），供在外省流量，播放设置里可选。无损档在不开任何处理时（只有无缝拼接），样本必须逐位等于源（§1.1），不施加抖动。
- **P10 派生退役**：渲染流现场解码所有格式（ALAC、APE、WavPack、AIFF……），上线后退役现有的 ALAC/⑩ 派生缓存与预检里的派生等待。
- **P11 信号路径**：每个启用的节点都在信号路径里显示，有损环节显式标出；命中兼容性转换时标注并降低质量评级（§6.2）。
- **P12 CUE 虚拟分轨**：整轨 + CUE 的曲目按起止帧截取播放，格式表放开 `cue_virtual`；同一整轨的相邻两轨无缝拼接后逐位等于整轨（2026-11-08 用户裁决）。

## 验收

- 关掉所有处理、只开无缝时，渲染流解出的 PCM 与源文件解码结果逐位相同（MD5 比对）。
- 开 Headroom 后信号路径出现对应节点；人为造成削波时削波指示亮起，约 0.5 s 后熄灭。
- iPhone Safari、桌面 Chrome/Firefox/Safari 能播放渲染流，锁屏后继续出声（先做小验证，见风险）。
- 定位、改处理设置后 1 s 内听到新结果。
- 电平化的增益在渲染流里与现有前端规则一致（复用现有前端单测的用例作为后端用例）。
- 有损档能在手机上播放，信号路径标出有损编码。
- CUE 虚拟分轨能播；同一整轨的相邻两轨无缝拼接后与整轨对应区间逐位相同。
- 升级后旧的派生缓存目录被删掉，日志记一条 `playback.derivation.cache_removed`。

## 已裁决

- 2026-11-09 iOS 交付小验证（iPhone，iOS 27，WebKit 内核的 Edge，经 HTTPS 反代，`isSecureContext` 为真）：
  - FLAC/WAV 长流每次先发 `Range: bytes=0-1` 探测，回 200 整条流时 `play()` 报 NotSupportedError；
  - 改用伪长度后能出声，但 WebKit 会跳到远处偏移反复探测，实时流只能用当前数据冒充，很脆弱；
  - 锁屏约 7 分钟内页面没有任何上报（没有位置回报，第 3 分钟的换流和标题更新都没发生）；
  - AAC/Opus 先探测、再发无 Range 请求后能播；
  - HLS（fMP4 ALAC）锁屏下能一直放到结尾，页面照常运行：每 5 秒上报位置，脚本每 30 秒设置一次标题。但用户在锁屏上没看到标题，Edge 里长流和 HLS 都不显示；Safari 里是否显示还没测。
- 2026-11-09 用户：**iPhone/iPad 用 HLS 交付服务端渲染流**（采纳推荐）。桌面浏览器继续用长流（FLAC/WAV/Opus/AAC）。理由：手机上同样有无缝、电平化、耳机校正与省流量档，锁屏连续播放与位置回报已实测正常；没有选“iOS 本地直放原文件”，因为那样 iPhone 上没有无缝、锁屏电平化与第二批的处理。交付设计等真机验证全部做完再写（还差：Safari 里的锁屏标题），协议上按能力声明区分，播放区“期望状态 + 回报”的形状不变。

## 风险

- （已验证，结论见“已裁决”）iOS Safari 能否用一条没有长度的长 FLAC/WAV 响应锁屏连续播放，要先用真机小验证确认（[design-delivery.md](./design-delivery.md) §4，用户在 iPhone 上约 20 分钟）；各种结果对应的交付方案见同节 §4.5，其中改 HLS 或改播放区规则的几种要交主会话裁决。
