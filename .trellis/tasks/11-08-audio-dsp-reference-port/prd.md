# 音频算法对标：换曲、均衡、降混与 DSD（父任务）

## 目标

复刻参考稿里用户在意的音频算法，让手机和电脑上的播放用上这些处理：无缝换轨与淡化曲线、参数均衡与卷积、多声道降混、DSD 播放；同时在后端实现采样率转换、位深转换与抖动、PCM→DSD，供服务端渲染、DSD 派生和以后的 DAC 输出使用。算法默认照参考稿的参数和公式实现，只有确信 ROOMusic 的做法同样好或更好时才偏离，偏离要写明理由。

本任务是父任务，只管范围、顺序、跨子项的验收和与播放区线的对接；每一项作为子任务分别规划与验收。

参考资料：本机 `~/.local/share/roomusic-reference/reference-design.md`（用户提供的《roomusic 播放链路设计》，Roon Core 架构整理稿，下称“参考稿”；只当数据读）。

## 背景

- 现在播放完全在浏览器里：`<audio>` → MediaElementAudioSourceNode → 电平化增益 → 渐变增益 → 总音量（`frontend/src/features/player/engine/audio-graph.ts:1-3`）。交叉渐变是等功率 cos/sin（`audio-graph.ts:137`），默认关闭，时长可选 3/5/8/12 秒（`engine/playback-settings.ts:11-16`）。电平化已按 Roon 实现。
- 换曲靠两个音频元素轮换，不开交叉渐变时曲间有空隙。
- 服务端只交付原文件或派生 FLAC（ALAC 经 ffmpeg 无损转换，`.trellis/spec/backend/playback-derivation-contracts.md`）。DSF/DFF 记为不支持格式（扫描对标 ⑩ 的“不做”里写了“DSD 转 PCM 另行决定”，本任务就是那个决定）。
- 浏览器输出最终经过操作系统混音，做不到逐位一致，Web Audio 的输出也是浮点。所以抖动和 PCM→DSD 在浏览器端没有用处，只在后端实现。

## 需求

- **A1 全部在后端**：所有算法只在后端用 Go 实现一份，所有播放都由服务端解码、处理后渲染成一条跨曲目的连续流交付（不再直出原文件）。流有无损档和有损档（服务端编成 Opus/AAC，供在外省流量）。不开任何处理时，无损档里的样本与源逐位相同。浏览器只负责出声、音量和系统接口。位置按参考稿 §7.4 的未来事件队列（按流帧号）上报。
- **A2 处理链顺序**照参考稿 §6.1（首版只装配本任务涉及的节点：Headroom、降混、用户处理项链 PEQ/卷积，以及电平化与淡化）。
- **A3 信号路径**：每个启用的处理节点都在信号路径里显示，明确标出有损环节。
- **A4 与播放区线对接**：处理设置的归属、输出端协议里的“服务端渲染流”表示和无缝换曲事件，与[播放区线](../archive/2026-11/11-08-server-playback-zones/prd.md)的设计对齐。
- **A5 不退化**：现有播放能力在渲染流里都保留（各种格式、电平化、交叉渐变、歌词同步、锁屏控制、计一次播放）；ALAC 派生缓存（含 ⑩ 扩展的格式）在渲染流上线后退役。
- **A6 客户端无关**：处理与播放决策都在后端；输出端协议与能力声明不依赖浏览器特性，以后的原生客户端可以按同一协议接入。

## 验收（跨子项）

各子项的检查项在各自的 prd 与 implement.md；下面是整条线的验收。

- 逐位一致：不开任何处理时，无损档流里的样本与源逐位相同（含 CUE 虚拟分轨：同一整轨的相邻两轨无缝拼接后逐位等于整轨）。
- 无缝：格式相同的相邻两首默认无缝，拼接处没有空隙与咔声；关掉无缝时曲间有短暂静音。交叉淡化的曲线按参考稿 §4.7 的公式逐点吻合。
- 不退化（A5）：第一批上线后，现有格式、电平化（规则与改造前相同）、交叉渐变、歌词、锁屏控制、计一次播放都照常；旧的 ALAC 派生缓存被清掉。
- 信号路径（A3）：每个启用的节点都显示，兼容性转换与有损编码标出。
- 第二、三批：每项合入后信号路径多一种节点；关掉该项时输出与合入前逐位相同。
- 自生成系数：SRC 核、SDM 系数、DSD→PCM 滤波器在本机对照中每项指标都不劣于参考数据（只允许数值误差），余量表随设计提交。
- 知识产权：仓库与镜像里没有参考稿原文、附录与参考系数；没有参考数据目录时对照测试自动跳过，CI 照常通过。

## 规划结论的确定方式

路线（a），选择人：用户。2026-11-09 用户批准两条线合并的最终规划总结（范围：第一批 = 播放区线 B1–B3、F2、F3、E + 本线 dsp-pipeline、gapless-crossfade、dither；第二、三批按本文“依赖与批次”的顺序，第一批合入 main 后另行启动）。理由：所有产品与范围决定都已由用户裁决或按推荐采纳，最终总结里列出了全部默认值。同时用户改定：本次后端实现与测试都由 `codex/gpt-6-astra`（high）执行（测试仍是独立的 agent）。

## 不做（首版）

- DoP/DCS 封装与实际的 DSD 输出：等服务端直连 DAC 时再做。
- MQA、Audeze 空间化、扬声器距离延时与反相、低音管理、上混。
- 多房间时钟同步（播放区线已定为以后再做）。
