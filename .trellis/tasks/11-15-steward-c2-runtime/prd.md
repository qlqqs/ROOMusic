# 管家 C2：运行时与只读工具

父任务：`.trellis/tasks/11-15-music-steward-m6`（S1–S3、S9、S13、S15、R1、R7、R10 的对话部分、R12）。
总体结构见父任务 `design.md`。

## 目标

做出管家的后端地基：用户配置自己的模型端点后，能通过接口发起一次对话，模型在循环里连续调用曲库只读工具，
过程流式返回，对话落库。之后的子任务只在这个地基上加工具、加入口。本任务不含前端页面、MCP、写操作和联网。

## 依赖

- C1 的 ADR 批准后才开始实施。规划可以先做；出站地址、密钥存放、发给模型的数据范围三处按 ADR 的结论填。

## 已确认的事实

  library、listening、operations、personal、platform、playback、zones。
- 业务包向 `operations` 注册 `Kind` 的做法可沿用到工具注册（`backend/internal/operations/kind.go`）；
  依赖方向由 `backend/internal/app/dependency_rules_test.go` 检查。

- 后端依赖只有 pgx 与 `golang.org/x`；迁移到 0050，新迁移从 0051 起。

## 需求

- R1 工具注册表：每个工具登记名称、说明、输入输出 schema、最低身份、影响范围、是否可撤销、输出是否含不可信文本；
  调用入口每次按当前主体鉴权；工具列表按主体过滤。
- R2 曲库只读工具：搜索、专辑与版本、曲目、艺人、证据、待关注问题、扫描状态与记录、操作记录。
  每个工具调用现有服务层，不直接查业务表。
- R3 Provider：OpenAI 兼容与 Messages 两种协议的适配器，标准库实现，流式返回文本、工具调用和用量。
- R4 按用户的设置：端点地址、密钥、对话模型、显示名字；只有本人能读写，密钥不在响应里返回。
- R5 端点探测：按地址匹配预设，实际请求确认协议、模型列表、工具调用；结果存进设置，可手动修改。
  自带搜索的探测留给 C8。
- R6 循环：多步调用工具直到模型给出最终回答；有步数上限、单次对话的 token 上限和取消。
- R7 对话持久化：会话、消息、工具调用落库，按用户隔离；可列出、读取、删除自己的会话。
- R8 流式接口：发消息后用 SSE 返回文本增量、工具调用的开始与结果、结束原因。
- R9 成员开关：管理员可以关闭成员使用；关闭后成员的接口返回拒绝。
- R10 模型端点不可用、不支持工具调用、未配置时，接口返回各自明确的错误码。

## 验收标准

- [ ] 对着本地的假模型服务（两种协议各一个），发一条消息能看到多步只读工具调用和最终回答，SSE 事件顺序正确，
  会话重新读取时内容完整。
- [ ] 成员调用管理员才有的工具被拒绝，且该工具不在发给模型的工具列表里。
- [ ] 一个用户的设置、会话，其他用户（包括管理员）读不到；响应、日志里查不到密钥。
- [ ] 探测能区分两种协议和“不支持工具调用”，失败时返回原因；手动改过的结果不会被下次探测以外的操作覆盖。
- [ ] 达到步数或 token 上限、用户取消、端点中途断开时，循环停下，会话状态可读，没有悬挂的后台协程。
- [ ] 管理员关闭成员使用后，成员的对话与设置接口返回拒绝。
- [ ] 依赖规则测试通过：`steward` 不依赖具体业务包；没有新增第三方依赖。
