# Core 1 各阶段交付基线

2026-11-03 从 [Core 1 路线](core-1-roadmap.md) 的“当前基线”一节原样移出：逐阶段记录交付时的代码事实。现状以各合同与代码为准。

后端入口位于 `backend/cmd/roomusic`，能力代码位于 `backend/internal/`（B0 于 2026-09-30 完成拆分，见
[后端目录结构](../../.trellis/spec/backend/directory-structure.md)）。阶段 I（2026-09-30）已实施身份稳定：扫描暂存表归 catalog，
`ingest.PlanStagedRoot` 在写入前规划曲目与 Release 的沿用——曲目按来源身份与音频内容指纹延续，同一 root 遍历完整时
改名、移动、互换按指纹唯一 1:1 保守重绑定；Release 按曲目成员关系匹配，`candidate_anchor` 只是位置信息，
每个新 Release 仍新建一个 ReleaseGroup；`GET /api/v1/release-groups` 与 `/{id}` 提供按组只读读取
（没有人工归组时每组一个版本）。生产部署仍由一个 Go 应用提供 REST 与同源 Web 资产，PostgreSQL
是唯一必需业务权威。

M1a（2026-10-01）已重建 `frontend/src/`：应用外壳、初始化与会话（会话代次、跨标签页同步）、扫描目录与扫描详情、成员管理、
简版概览；Go 内嵌的是它的生产构建（`backend/cmd/roomusic/web`，随源码提交）。`.github/workflows/ci.yml` 的前端作业运行
lint、typecheck、Vitest、生产构建、内嵌资产漂移检查与 Playwright 冒烟（含无障碍与五种宽度的响应式检查），接口响应样本由集成作业把关。
Classical 原型与 `_ds` 设计系统已经入库，源目录不搬迁。

M1b（2026-10-03）在这个外壳上增加了专辑浏览，只改前端与样本测试，没有新增后端接口：`/albums`（搜索、需要关注筛选、分页，每页 48 张封面卡片，搜索与页码都在地址里）与
`/albums/$groupId`（头部、多版本时的版本导航、按介质逐段列出的曲目与署名、发行信息、折叠的来源与证据；管理员可按需读完整证据，普通用户从不请求）。
所选版本在两次请求之间被重新扫描掉时就地提示。真实接口冒烟（隔离 PostgreSQL 与合成素材）同时发现后端封面发现的两处缺口：CUE 专辑拿不到文件夹封面，
多碟专辑只在第一张碟的文件夹里找封面（已由 F4 修复，见下）。

F3（2026-10-02）补齐了 M1a 暴露的后端缺口，没有迁移：管理员的 `GET /api/v1/scans`（分页）与扫描目录页的“扫描记录”；`/auth/me`、登录与初始化管理员的响应都带用户 `id`，前端按 ID 判断“你”与同一查看者；成员与初始化接口只把唯一约束冲突映射为 409，密码按字节限制在 12 到 72；静态资源、JSON 与封面带明确的缓存头（封面 `private, no-cache` 加 `ETag` 与 304，`assets/` 下的文件 `immutable`，JSON `no-store`，不再列目录）。成员写操作的幂等键延到 M3。M1b 因此可以直接使用共用的分页组件与封面缓存。

F4（2026-10-03）修复了 M1b 冒烟发现的封面发现缺口，只改后端扫描，没有迁移，REST 与前端不变：CUE 专辑用 sheet 所在目录找封面；严格多碟专辑先查各碟的父目录，再按碟序查各碟目录；封面文件名不区分大小写（Linux 上 `Cover.JPG` 之前找不到）。查找不超出发行自己的目录，Box 叶子不取 Box 父目录。内嵌封面仍然优先；重扫即绑定，不需要迁移。

M3（2026-10）让管理员能修正扫描得到的发行信息、调整版本所属的专辑并撤销自己的修改（迁移 0017，新包 `internal/operations`）：发行的八个字段（标题、专辑艺人、年份、流派、厂牌、编号、版本说明、条码）
可以改成某个值、设为空或恢复为扫描值，修正存放在独立的表里，所有读取（列表、详情、搜索、排序、按组读取、最近播放）经有效值视图显示修正后的值，重扫只更新扫描值与证据、不会覆盖修正；
版本可以归入另一张专辑或移出为独立专辑，重扫不改人工归组；每次成功的修正、归组与撤销在同一事务里写一条操作记录（操作者、时间、版本、前后状态），
记录只有管理员能读（“资料库”下的“操作记录”页与专辑详情的“修改记录”），发行最近一次修改可以单条撤销。普通成员没有任何编辑入口，只看到有效值与“人工修正”标记。
共同写入流程（幂等键、同键同义重放、同一事务写记录）见[受治理操作合同](../../.trellis/spec/backend/governance-contracts.md)；成员写操作、审批队列、`editor` 角色与认领不在 M3。

M4 的第一项（2026-10，迁移 0018）让管理员为多版本专辑指定默认版本：它成为专辑的代表版本（卡片、列表排序、打开专辑时先显示的版本、版本导航的顺序），
没有指定的专辑仍按“年份最早”自动选择；默认版本不可见或被移出时静默回到自动规则，回来时重新生效，重扫与归组都不改它。设定、改回自动选择与撤销走 M3 的共同写入流程，
专辑有自己的人工修改版本号，记录出现在操作记录页与专辑详情的“修改记录”里。所有登录成员可以在多版本专辑上打开“对比版本”，逐项比较发行字段与内容（介质、曲目、
总时长、音频格式的具体参数），只如实列出，不做音质结论。合同见[默认版本与版本对比合同](../../.trellis/spec/backend/default-version-contracts.md)。

M4 的第二项（2026-10，迁移 0019）把“需要关注”拆成可以逐条处理的问题：管理员的“元数据问题”页按版本列出扫描拿不准的字段、同一目录的归组冲突与缺失曲目，
写明原因与依据；字段沿用“编辑发行信息”，来源与介质类型、归组冲突与缺失曲目可以标记为已核对（走共同写入流程、可撤销），不再计入“需要关注”；
核对记住依据，扫描之后情况变了就重新提醒（缺失曲目逐首判断）。不做新的检查规则、外部参照与 Steward。合同见[元数据问题与核对合同](../../.trellis/spec/backend/issue-review-contracts.md)。

M4 的第三项（2026-10，迁移 0020）让管理员把**已不可见的旧版本**上的人工修改认领给扫描新建的版本：“待认领”页列出旧版本，按文件路径与目录推荐新版本、也能手动搜索任意可见版本，预览逐项说明后，把字段修正、所在的专辑、默认版本与问题核对一次迁移（新版本已有的以新版本为准），走共同写入流程、可撤销，预览令牌拦住预览之后变了的状态；不自动认领，不做“放弃”，普通成员没有入口。合同见[认领合同](../../.trellis/spec/backend/claim-contracts.md)。
