03

受治理写路径

所有资料库写操作走同一条路。人类和 Steward 只是不同的发起方；批准状态和执行状态分开保存，“已批准”不等于“已执行”，有日志也不等于能撤销。

1 · 发起
意图

人类界面提交 · Steward 提案（M6）

2 · 入口
解码与授权

以当前会话主体和角色为准；不信任请求里自报的身份、角色或模式。

3 · 预览
Change Set

目标集合 · 预期 revision · 证据摘要 · 风险 · 逆操作计划

4 · 批准
按政策

免审批，或人工 / 独立审查；批准绑定具体提案、证据与有效期。

5 · 执行
单一事务

重验授权、版本和批准 → 资源变化 + 检查点 + 日志 + 幂等结果一起提交。

6 · 撤销
类型化逆操作

逆序链先全部预检，再原子执行；不可逆的操作明确标注。

批准状态 · 与执行分开保存Operator 用 not_required，不伪造自动批准
not_required｜ awaiting_user｜ reviewing→ approved｜ rejected｜ needs_human_confirmation｜ review_unavailable
执行状态 · 来自后端操作日志界面不自行推断能否恢复
planned→ running→ succeeded｜ partially_failed｜ failed→ rolling_back→ rolled_back｜ rollback_failed

状态名取自 .trellis/spec/frontend/state-management.md 的语义示例，不是最终的接口格式。

M3 试点 · 已批准字段修正 + ReleaseGroup 成员调整。后者只改 releases.group_id，而扫描器更新已有 Release 时不碰这个字段。
不走这条路个人数据（按用户隔离直接写）· 扫描（只写观察层）
永远禁止任意 SQL、shell 或主机路径 · Agent 自己批准 · 审查失败时降级为 Operator

06

扩展边界

最终结构是“不可替换的内核 + 第一方模块 + 受控扩展层”。插件只能从两个口子进入：观察层和意图侧；任何插件都不能直接写结果层，也不能给自己授权。本节是指导原则，插件宿主等未来立项时复核。

扩展层 · 远期
格式解析器插件

新增音频或元数据格式；产出与内置解析器同形的观察。

扩展层 · 远期
元数据与封面提供方

例如 MusicBrainz；结果只作候选或证据，不覆盖人工修正。

扩展层 · 远期
Agent 与审查插件

只读结果层的受限工具；只能提交提案，不能批准自己的提案。

扩展层 · 最后
执行插件

文件或标签操作；须等受治理操作与恢复策略成熟，并服从音乐源默认只读。

接入口一 · 观察层
观察、候选与证据

与扫描观察同层；由 catalog 决定是否采纳，弱证据只产生候选。

接入口二 · 意图侧
Change Set

提案带目标、revision、证据与风险；批准与执行分开记录。

operations · M3
授权与执行

重验授权、版本和批准；执行插件只能由这里在授权包裹下调用。

结果层 · 有效值投影
插件不能直接写入这里，也不能给自己授权

观察经 catalog 计算、修正经 operations 写入覆盖层，两者合成后才成为 API 读取的结果。

内核 · 永远不做成插件（部分已有）
身份与权限 · 变更管理 · 工具授权 · 持久化（PostgreSQL）
第一步 · Core 1 期间只做“插件形状”：各模块由使用方定义窄接口，外部依赖做成同一二进制内的适配器，例如 M2b 的 ffmpeg、以后的元数据提供方和 M6 的模型服务。
第二步 · 出现第三方需求时把稳定接口升级为 extensions/ 合同，再建能力注册表与插件宿主。插件优先跑在独立进程、通过类型化 RPC 调用；不用 Go 的 plugin 包；WASM 只用于不受信任的第三方代码。
最后 · 执行插件在受治理操作和恢复策略成熟之后才考虑，并继续服从音乐源默认只读的不变量。
