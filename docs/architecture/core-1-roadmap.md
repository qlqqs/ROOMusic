2026-09-28 由 qlqq 裁决（D4）：**Core 1 = M0、B0、I、M1a、M1b、M2a、M2b、P（服务端播放历史）、

版本管理”。收藏、歌单、搜索规范化与艺人（M5）和 Music Steward（M6）进入后续阶段；外部元数据源
不作为 Core 1 前置。M0 曾列出的较小替代（先发 M1 + 必要 B0 + M2）未被选择，但 M1 与 M2a 仍须能
独立交付，不等待整条路线完工。

服务端播放历史（P）排在阶段 I 之后：它引用曲目 ID，必须等身份规则稳定；它只是真实播放的最小
用户隔离记录，历史页面、收藏和歌单属于 M5。

## 2026-11-03 路线调整

前提：实际只有一个管理员，基本不会多人同时整理（qlqq，2026-11-03）。代码与架构评估之后，用户按推荐方案裁决：

| 编号 | 裁决 |
| --- | --- |
| R1 | Release 合并与拆分（M4 ⑤）**搁置**：等真实库出现扫描分错、而现有的“归入其他专辑”“移出为独立专辑”解决不了时，再按 R4 立项 |
| R2 | 扫描反馈（M4 ④）**移到 M5 之后**，作为体验改进，不再是 Core 1 的一部分 |
| R3 | **删除播放中每 10 秒的复核**（修订 ADR 0004 K3 的在途部分）：只在建立传输时鉴权并核对来源；停用成员、撤销会话或停用目录后，正在传输的那首播完为止，之后的请求被拒绝；C1 已于 2026-11-03 实施 |
| R4 | **新写操作的轻量标准**：接入现有的 `operations.Run`（操作记录与幂等是现成的）；有反向操作可以恢复的不提供撤销（`Revert` 返回 `not_revertible`）；预览令牌只在预览依赖版本号覆盖不到的状态时才加。已实施的治理代码不拆（幂等防超时重试，认领令牌防预览后的扫描，撤销纠正误操作，都与人数无关）。M3 的 G6（成员写操作接入操作记录）**撤销，不再做** |
| R5 | **流程减负**，从下一个任务起：一般任务只写一页 `prd.md`（范围、关键决定、验收），`design.md` 与 `implement.md` 只在跨包改动或有迁移时才写；导出树验证只在收尾做一次；归档后的链接修正与日志合成一个提交，不要求每个中间提交都没有断链；变异检查只用于并发、权限与数据迁移等关键逻辑；ADR 与规范只在决定真的变了时更新。保留：包依赖规则测试、隔离的测试数据库、收尾时的 Playwright 与真实服务用例、界面改动的截图复核 |

## 静态审查发现的现有风险

`internal/library/httpapi/root_operations.go` 的停用/恢复指纹原先没有包含路由 root ID，重放查询只按 actor、操作类型
和幂等键查记录；同键同 body 用于不同目录时会返回前一个目标的结果。已记录于
[ADR 0003](adr/0003-governed-operations.md)与运行合同技术债，**2026-09-29 由 F2 动态复现并修复**：
指纹含目标，同键请求串行，旧记录不做兼容。修复没有与纯拆包混合，也没有等通用操作平台。
