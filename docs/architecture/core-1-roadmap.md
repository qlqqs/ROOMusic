# Classical / Core 1 能力边界与实施路线

## 状态与阅读方式

核对日期：2026-09-27；代码基线：`6cf76ec`。**已批准的是 M0 文档整理，不是下列全部功能
或依赖。** 本文是范围提案；设计规则见 [DESIGN.md](../../frontend/DESIGN.md)，架构总览见
[架构决策摘要](architecture-decisions.md)。

- **当前事实**：以实际注册 API、数据库迁移、源码和 CI 为准，原型不构成运行证据。
- **保留合同**：只读源文件、后端鉴权/路径/事务权威、来源可解释、保守分组及完整扫描才进行缺失对账。
- **候选方案**：标为草案的 ADR、Core 1 截止范围和尚未立项阶段，须另外批准才能实施。
- **历史资料**：旧视觉、本地模拟播放器和本地个人库只用于提取适用经验，不自动继承其实施授权。

## 当前基线

后端位于 `backend/cmd/roomusic`，共用一个 `package main`；`internal/` 是目标而非已完成拆分。
生产部署仍由一个 Go 应用提供 REST 与同源 Web 资产，PostgreSQL 是唯一必需业务权威。

`frontend/src/` 已删除，保留工具链配置和依赖声明；Go 内嵌资源是重置占位页。
`.github/workflows/ci.yml` 在没有 `frontend/src/main.tsx` 时跳过真实构建与资产漂移检查，
所以 CI 通过不代表已有可用客户端。Classical 原型与 `_ds` 设计系统已经入库，源目录不搬迁。

## 页面 / API / 缺口矩阵

下列路径均相对于 `/api/v1`，是已注册的现有接口；表中没有的新能力不通过假数据补齐。

| 页面或用户动作 | 当前 API / 数据证据 | M1 可交付的真实范围 | 缺口与候选阶段 |
| --- | --- | --- | --- |
| 初始化与会话 | `GET /setup/status`、`POST /setup/admin`、`POST /auth/login`、`POST /auth/logout`、`GET /auth/me` | 初始化关闭、登录/退出、失效恢复和 401/403 区分 | 无需新增认证方案；不引入浏览器 bearer token |
| 专辑库、基础搜索 | `GET /releases` 的 `q`、`attention=required`、`page`、`page_size` | 有界 Release 列表、筛选、分页和可恢复 URL 状态 | 不是 ReleaseGroup 聚合；全局搜索/别名和艺人发现属于 M5 |
| 发行详情与封面 | `GET /releases/{id}`、`GET /artworks/{resource_id}` | Medium/Track 层级、现有字段/credits、封面空态与错误态 | 多版本聚合/默认版本/对比属于 M4；作词/编曲角色和歌词需额外数据合同 |
| 来源与待关注信息 | 管理员 `GET /releases/{id}/evidence`，普通详情含安全摘要 | 按现有权限查看证据；仅 `attention` 筛选不能冒充问题工单 | 忽略/修正/审批等处理状态属于 M3/M4 |

| 成员 | `GET/POST /users`、`PATCH /users/{id}`、`POST /users/{id}/sessions/revoke` | 当前 admin/user 范围内的创建、禁用和会话撤销 | `editor` 是 M3 候选，不在前端单方面授予 |

| 概览 | 可组合已公开的 Release 分页总数、活动扫描和有权限的目录状态 | 有真实来源的摘要与跳转，缺少数据就省略 | 不生成“本次新增 N 张”“全部扫描历史”“收藏总数”或 AI 便笺等不存在的统计 |

## 推荐的范围切分（待用户确认）

推荐 **Core 1 = M0 + M1 + B0 + M2 + M3 + M4**，以“可用客户端 → 真实播放 → 可审计的
元数据与版本管理”作为阶段完成结果。M5 是后续增量候选，M6 是更晚的独立能力；
外部元数据源不作为 Core 1 前置。该切分保住版本学价值，但交付面明显大于只做播放器。

可行的较小替代是先把 **M1 + 必要 B0 + M2** 定为首个可发布批次，将 M3/M4 纳入下一阶段。
这样更快恢复日常使用，但本批次不承诺整理或版本管理。无论阶段如何命名，M1 和 M2
都应能独立交付，不等待整条路线一次性完工。

M2 的服务端播放历史仅为真实播放记录的最小用户隔离能力；M5 再增加历史页面、收藏和
歌单，不强行要求 M2 提前实现整个个人库。

## 阶段、依赖与验收出口

| 阶段 | 独立交付 | 前置与允许并行 | 验收出口 |
| --- | --- | --- | --- |
| M0 | 设计依据、能力矩阵、四类 ADR 草案、规范/旧任务承接 | 本轮文档授权 | 现状与提案区分清楚，没有业务变更；尚未采纳的决定仍可识别 |
| M1 | Classical 外壳、初始化/会话、Release 浏览/详情/基础搜索、现有目录/扫描/成员管理、简版概览 | M0 文档就绪，相关前端选择获批；可与 B0 并行 | 真实 API 主路径、权限/错误/空态、键盘/窄屏、实际构建及内嵌资产检查通过 |
| B0 | 解析器 → 平台 → 身份 → 目录/扫描 → catalog 的渐进边界重构 | 各步单独可测，不要求所有层目录齐全；不阻塞 M1 消费旧 API | 重构前后接口/扫描/安全/事务行为不变；每步相关测试证明行为保持 |
| M2 | 鉴权串流、直出/派生缓存、CUE 分轨、真实播放器与歌词、最小播放历史 | 播放 ADR 与客户端边界就绪；不依赖通用治理写路径 | 约定浏览器/格式可播放、拖动/取消/错误可恢复、切页不断播，不宣称硬件 Bit-perfect |
| M3 | 修正覆盖层、受控执行、通用日志/审批/检查点与候选角色扩展 | 覆盖层/操作 ADR 和所需身份/catalog 边界就绪；与 M2 无必然顺序 | 重扫不覆盖修正、越权拒绝、并发冲突、幂等与支持的撤销有证据 |
| M4 | 本地可解释问题、ReleaseGroup 实体与版本工具、合并/拆分/默认版本 | 治理写操作依赖 M3；分组只依据强证据或用户确认 | 证据可追溯，结构变更走统一执行；无自动弱相似合并 |
| M5 | 增强搜索、艺人/别名、收藏、歌单、历史页 | 检索按分组/别名依赖排序；个人数据不绑定整个 M4 | 按用户隔离、真实服务端持久化，不重建本地演示系统 |
| M6 | 只读 Steward → 受控提案 → 独立审查 | 工具、权限与执行边界已交付；外部源另评 | Agent 只提供意图/证据，不能自批危险操作或绕过后端 |

扫描进度/报告、定时/增量扫描是 M4 周边候选，不是版本治理的逻辑前置；创建子任务时应
按最小可验收能力拆开。B0 不夹带新增端点、schema、业务规则或 `/api/` JSON 404 修复。
后者是已知路由问题，应单列有回归测试的行为修复；M0 不直接修复它。

## 静态审查发现的现有风险

`root_operations.go` 的停用/恢复指纹没有包含路由 root ID，重放查询只按 actor、操作类型
和幂等键查记录；同键同 body 用于不同目录时可能返回前一个目标的结果。已记录于
[ADR 0003](adr/0003-governed-operations.md)与运行合同技术债，**本轮未动态复现或修复**。
建议独立补复现及目标绑定/旧记录兼容的定向修复，不与纯拆包混合，也不等到通用操作平台
完成才处理。M1 不能把未经验证的跨目标重试视为安全功能。
