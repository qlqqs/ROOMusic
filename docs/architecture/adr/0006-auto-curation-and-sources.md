## 2. 问题

扫描之后，曲库里还剩很多需要整理的地方：缺封面、缺歌词、年份与厂牌是空的、标题与艺人的写法不统一、
同一个艺人有几种名字、同一张专辑的几个版本没有归到一起。现在这些事要么没有数据来源，要么要人一条条确认。

要解决的问题：

1. 外部数据源与模型的判断怎样写进曲库，又不盖掉人改过的内容。
2. 没有人逐条确认时，怎样保证错了能改回来。
3. 哪些事程序可以直接定，哪些交给模型，哪些必须留给人。
4. 没有人发起的运行以谁的身份、花谁的钱、什么时候停。
5. 哪些数据会发给外部源。

适用的曲库不限于某一种：整轨抓的 CD、用 Picard 打过标签的、流媒体下载的单曲、标签很差或没有标签的文件、
华语与欧美，都在范围内。

## 3. 原则

替换[架构决策摘要](../architecture-decisions.md)“扩展边界的两步走”里“产出只作为候选或证据”的表述：

1. **三层分工**：程序判定能确定的 → 模型判断程序拿不准的 → 人只处理模型上交或判断不了的。
2. **默认自动，例外才问人**：程序和模型能定的直接生效，不进待确认队列。
3. **安全靠事后可撤，不靠事前确认**：每次自动修改有记录、依据与来源，可以单条撤销，也可以按批或按来源撤销。
   不可撤销的操作不自动执行。
4. **人工修正永远优先**：用户亲手改过的，程序和模型都不再改。
5. **音乐文件只读**。
6. **能力由宿主分配**：外部源只拿到自己那类能力的口子，不能自行取得其他权限。

2026-11-25 修订（第 16.1 节，尚未实现）：原则 1、2 改为“结局只有三种”与“本地能定的不联网，程序能定的不用模型，模型只做可核对的事”，
另加“核对代替确认”“中断安全”“错了要看得见”三条；原则 3–6 不变。

没有变的：后端是鉴权、事务、版本冲突与幂等的唯一权威；所有持久修改经 `operations.Run`；
弱相似（标题、艺人、年份或目录相近）不能作为合并的依据。

## 4. 三层与优先顺序

| 层 | 谁写 | 说明 |
| --- | --- | --- |
| 人工修正 | 用户亲手改；用户在对话或 MCP 里让管家改 | 现有的修正，行为不变 |
| 自动层（新） | 后台自动整理：程序与模型 | 外部源给的值、模型判断的值 |
| 扫描值 | 扫描 | 现有的扫描列 |

- 有效值 = 人工修正 → 自动层 → 扫描值，逐字段取第一个有值的。
- 结构保证：扫描只写扫描值，自动整理只写自动层，人工修正只由人工路径写。三者互不覆盖，优先顺序只在读取时体现。
  “人工修正永远优先”因此不依赖运行时判断：自动写入的执行器不接触人工修正。
- 用户清除人工修正后，显示自动层的值；再清除自动层后，显示扫描值。
- 重扫不清除自动层、外部封面、外部歌词与外部对应。
- 自动层的一个字段只有一个值：程序先写、模型后来改写同一字段时，后写的替换先写的，前一个值留在操作记录里。
  2026-11-25 修订（第 16.5 节，尚未实现）：自动层内部按写入依据固定先后，低的不替换高的；自动值记录它依据的扫描值，扫描值变化后作废。

各类数据：

| 数据 | 规则 |
| --- | --- |
| 发行级八个字段（标题、专辑艺人、年份、流派、厂牌、编号、版本说明、条码） | 程序只补空缺；改已有的值由模型判断 |
| 曲目标题、曲目艺人 | 同上；同时新建曲目的人工修正。曲序与碟号不可修正 |
| 外部对应 | 本地的发行、专辑、曲目、艺人与外部 ID 的对应可以保存，带匹配方式、把握程度与状态；一个本地对象在一个源里至多一个生效的对应 |
| 封面、歌词 | 外部来的单独存放，不占本地的位置；只补空缺，本地有时用本地的。一个发行至多一张外部封面、一首曲目至多一份外部歌词；已经有了就不再写第二份，要换先撤销（外部封面与歌词实施时补充） |
| 结构操作（归组、默认版本、核对、认领、艺人合并改名、发行合并拆分） | 不是字段值，没有“层”；靠操作记录的来源区分人工与自动，条件见第 7 节 |

## 5. 记录、批次与撤销

### 记录

- 三层共用一条写入路径：所有持久修改经 `operations.Run`。程序层与模型层的区别只在“谁做的判断”，不在“怎么写”。
- 操作者是开启自动整理的管理员；不新造系统用户。
- 来源增加“自动整理”一种，并记下是哪个外部源或模型、哪一批、依据是什么。
- 批次：后台整理的一段连续工作是一批（程序层按时间或数量切分，模型层一次运行是一批）。批次记录起止时间、
  属于程序层还是模型层、各类改动的数量与用量。
- 操作记录可以按来源、按批次筛选。

### 撤销

现有规则要求目标的版本号等于这条操作留下的版本号，同一发行上之后的任何修改都会让更早的操作撤不了。
自动修改不沿用这条规则：

- 自动层的每个值记着是哪条操作写的。撤销一条自动修改时，如果这个值现在仍是这条操作写的，就恢复到它之前的自动层状态
  （之前的值，或没有值）；如果已经被更晚的自动修改改写，返回冲突，不改动。
- 人工修正在另一层，不参与判断。用户之后改了同一发行的任何字段，都不妨碍撤销自动层。
- 自动层的写入不递增发行的 `edit_revision`，因此不会让人工修改的撤销失效。
- 按批撤销：按时间倒序逐条撤销这一批里仍可撤的操作，返回撤了多少、跳过多少与原因。按来源撤销同理。
  它们本身是受治理操作，也有记录。
- 结构操作的撤销沿用各自现有的规则。之后被人工改过的结构，自动撤销被拒绝并在结果里列出：
  人已经在这个结构上做了新的决定。

### 撤销之后不再应用

用户撤销一条自动修改，等于表达“这个改动不对”。后端记下“不再提出”的标记，程序层与模型层提出修改之前都先查它。
例外里选“不采纳”写同一种标记。标记只挡同一个改动，不挡同一处的其他值；用户可以清掉标记。

外部封面与外部歌词的“同一个改动”按两样判定，撤销时两样都记，命中任一样就不再写：内容（图片字节或规范化后的歌词文本），
与外部编号（哪个源的哪一张图、哪一条歌词记录）。只按内容挡不住同一张图的另一档缩略图（外部封面与歌词实施时补充）。
外部封面与外部歌词的撤销就是去掉这一份：它们只在没有时写入，没有“之前的值”可恢复。歌词的自动修改记在曲目当时所在的发行上（同上）。

## 6. 程序层的判定

程序层按缺口工作：还没处理过的、输入变了的、匹配规则升级了的才处理；扫描进行时让路。

匹配依据按可靠程度排列，前面的命中就不再用后面的：

1. 标签里的外部 ID。
2. 条码；厂牌加编号。
3. 曲目里的 ISRC 集合。
4. 由曲目数与时长推出的光盘目录。接入 MusicBrainz 时已核实可行：整轨抓取的 CD 可以由各轨时长重建目录并算出 disc ID 做精确查询；
   没有精确命中时退为按时长的模糊结果，它只能缩小到同一专辑的若干 CD 版本，两者的可靠程度要分开对待。
5. 声学指纹（AcoustID）。
6. 标题、艺人、曲目数与时长的查询：只产生候选，从不直接判定。

“把握足够”才由程序直接定：必须是唯一候选，并且至少有一项独立的佐证（如曲目数一致、各曲时长在容差内）；
有任何相反的证据就降为拿不准。宁可多交给模型，不可错判。具体规则在程序自动整理实现时逐条定义并用测试固定（见[自动整理合同](../../../.trellis/spec/backend/curation-contracts.md)第 15 节）。
匹配的输入只取人工修正与扫描值：自动层是匹配的产出，不能拿来证明自己（程序自动整理实施时补充）。

2026-11-25 修订（第 16.3 节，尚未实现）：第 6 条“文字查询只产生候选”改为可以由程序按曲目结构判定，发行组唯一时在限定条件下认定到发行组一级；
巡检的规范名与模型整理的值可以作为搜索输入，但这类输入的结果只接受带时长的结构判定；占位值不进入搜索；拿不准的项分三档交给模型，
没配置模型、或各档都没有结果的记为未收录。“列表可能被截断时拿不准”保留。

- 把握足够：保存外部对应，把空缺的字段补到自动层，本地没有封面或歌词时取外部的，符合第 7 节条件的结构操作直接做。
- 拿不准或没匹配上：形成待定项，带上候选、本地证据与冲突点，交给模型层。没配置模型时停在那里。
- 匹配不上的记为已尝试，文件变了或规则升级之后才再试。

## 7. 结构操作的自动使用

| 操作 | 自动使用的条件 |
| --- | --- |
| 问题核对、默认版本、认领 | 模型提出，审查通过 |
| 专辑归组（归入、移出） | 只在强证据下：两个发行的外部对应指向同一个外部专辑（release group）。程序层可以直接做（只做归入）；模型提出时证据里必须有这条对应。发行最近一次归组是人做的，不再自动归组（程序自动整理实施时补充） |
| 艺人合并、改名 | 先做成可撤销。程序层：两个本地艺人的外部对应指向同一个外部艺人时合并；其余由模型提出并审查 |
| 忽略艺人候选 | 先做成可撤销，之后可以自动 |
| 艺人拆分 | 不自动提出；它是纠正错误合并的手段，由撤销合并覆盖 |
| 发行的合并与拆分 | 只在强证据下：外部对应表明这些曲目属于同一个外部发行（合并）或不同的外部发行（拆分）。一律由模型提出并审查，程序层不直接做 |

**强证据**是后端的硬规则，不由模型自述：证据必须是已经保存、状态为生效的外部对应。
模型在方案里声称有依据而库里没有对应记录时，后端转人工。

这是对 [ADR 0002](0002-metadata-overlays.md) 第六节“强证据路径”的批准：获批的共同分组标识是上面这一种，
并且只来自第 8 节批准的外部源。标题、艺人、年份、目录相似，或多个模型一致，仍然只能产生候选。

2026-11-25 修订（第 16.3、16.6 节，尚未实现）：“多个模型一致只能产生候选”保留。新增两种依据：发行组级对应可以用于专辑归组与艺人对应，
不用于发行合并；艺人合并另可依据外部登记的别名、库内佐证或带引用的网页加模型判断，并要求两个名字从未在同一首曲目上并列署名。
发行的合并与拆分不变。

## 8. 外部源

### 形态

- 每个源是编进程序的适配器，放在与管家无关的位置；不建第三方插件宿主、能力注册表或独立进程的插件协议。
  （2026-11-24 修订：第三方数据源插件见 [ADR 0007](0007-source-plugins.md)，内置来源仍按本节。）
  以后出现第三方来写源的需求时，再把已经稳定的接口升级为宿主，条件见架构决策摘要的“扩展边界的两步走”。
- 每个源有一份声明：标识与显示名、提供的能力、启用条件、限速、需要的配置项。设置页按声明列出各源的开关。
- 能力是几个窄接口，源按自己的情况实现其中几个：发行查找、录音查找、艺人查找、指纹识别、封面、歌词。
  调用方（程序层的匹配、管家的工具）只面向能力，不直接依赖某个源。
- 管家现有的两个音乐资料工具改为走同一个 MusicBrainz 适配器，工具的名字与输出不变。
  它们是 MusicBrainz 专用的工具（自由查询串与 include 列表），直接用适配器的实体级读取与查询；“只面向能力”约束的是程序层（接入 MusicBrainz 时补充）。

### 首批的源

| 源 | 能力 | 默认 | 启用条件 |
| --- | --- | --- | --- |
| MusicBrainz | 发行、录音、艺人查找 | 开 | 总开关打开 |
| Cover Art Archive | 封面 | 开 | 总开关打开 |
| LRCLIB | 歌词 | 开 | 总开关打开 |
| AcoustID | 指纹识别 | 开（2026-11-23 修订：原为关） | 管理员填入自己的用户密钥，并且镜像里有 Chromaprint（实际为静态 `fpcalc`）。2026-11-23 修订：发布镜像内置 ROOMusic 注册的应用密钥（原为“管理员填入自己注册的应用密钥，仓库不内置共用密钥”） |

- 扫描解析并保存标签里的 MusicBrainz 各类 ID、ISRC 与 AcoustID。
- 生产镜像增加 Chromaprint 用来计算声学指纹。没有它或没填密钥时，AcoustID 显示为未启用，其余功能不受影响。
- 没有官方开放接口的平台（网易云、QQ 音乐等）不内置。艺人图片与简介、Discogs、华语覆盖更好的封面与歌词源不在首批。

### 共用的规则

- 出站：管家与外部源共用同一个出站客户端（现有的客户端迁到平台层），地址规则沿用 [ADR 0005](0005-steward-data-and-egress.md) 第 5 节。
  地址由程序固定的源，允许它官方的重定向目标（Cover Art Archive 的图片实际由 archive.org 提供）。
- 限速：每个源一个全实例的限速器。MusicBrainz 与 Cover Art Archive 的清单请求共用每秒 1 次；
  用户在对话里的查询与后台匹配共用同一个限速器，对话优先。Cover Art Archive 的图片下载另设每秒 1 次：它的第一跳也经过 MetaBrainz 的网关，
  所以对这个网关合计每秒 2 次（Cover Art Archive 的文档写明目前没有限速规则；外部封面与歌词实施时补充）。
  2026-11-25 修订（第 16.4 节，尚未实现）：封面清单请求不再占 MusicBrainz 的限速额度；各来源各自一条队列，某个来源被限流只停它自己的队列。
- 缓存：按请求内容缓存响应；有结果的缓存时间长，空结果与失败的缓存时间短。
- 重试：服务不可用与限流按源的要求退避重试，有上限；超过上限记为稍后再试，不算匹配失败。
- 配置：各源的开关与 AcoustID 密钥是实例级的，由管理员设置；密钥用现有的密钥库加密，绑定实例与用途。
- 存放：外部下载的封面、指纹与查询缓存放在数据目录，属于可以重新获取的数据，不进备份。
  （2026-11-23 修订：声学指纹按需计算、量小，缓存放在数据库并随曲目删除，见决策记录“AcoustID 实施时的补充”。）
  自动层、外部对应、待定项与批次在数据库里，随数据库备份。恢复备份后外部封面的记录还在而图片文件不在：之后的整理把它当作缺口重新获取，
  新的写入替换旧记录（外部封面与歌词实施时补充）。
- 下载的图片沿用现有封面的校验（大小、格式）与内容寻址存储。

### 发给外部源的数据

| 源 | 发出的内容 |
| --- | --- |
| MusicBrainz | 外部 ID、条码、ISRC、厂牌与编号、标题与艺人的查询词、由曲目时长推出的光盘目录 |
| Cover Art Archive | 外部 ID |
| LRCLIB | 曲目标题、艺人、专辑名、时长 |
| AcoustID | 声学指纹与时长，以及应用密钥（2026-11-23 起发布镜像里是 ROOMusic 内置的）与管理员填入的用户密钥 |

- 不发送音频、文件路径与实例标识。
- 声学指纹是由音频算出的摘要，不能还原音频；它是音频派生的数据，只发给 AcoustID。
- 外部源返回的内容一律是不可信文本，进入模型之前按 ADR 0005 第 4 节加来源标记。

## 9. 模型层：后台运行

### 身份

- 后台整理归开启它的管理员：用他自己配置的端点与密钥，可以单独选一个“整理用的模型”，不选就用对话模型。
- 管理员开启的自动整理视为该管理员本人的请求：发给模型的数据范围、密钥的使用都按他本人使用管家时的规则。
- 不引入实例级共享的模型密钥，不新造系统用户。

### 运行

- 复用管家的运行、工具、方案与审查。每批待定项是一个归该管理员所有、标为自动整理的会话；
  它不混在他自己的对话列表里，从整理记录进入。可以点开看模型查了什么、为什么这么判断，也可以接着对话纠正。
- 运行由后台调度启动，第一条消息由程序生成。模式固定为 `steward`：必须经过审查，不能直接执行。
- 自动整理的运行里，字段类的写工具写自动层；工具对模型的名字与参数不变，由运行的来源决定写到哪一层。
- 全实例同一时刻只跑一个后台的模型运行，不占用户自己的并发名额。

2026-11-25 修订（第 16.6 节，尚未实现）：模型的任务扩为巡检、本地整理、三档识别兜底与联网兜底；模型选定或提交的外部编号通过完整结构核对的
直接写入、不另起审查；其余写入仍经独立审查。下文“例外”一节由“未采用的建议”取代，不再等管理员处理。

### 审查策略第 2 版

| 规则 | 第 1 版 | 第 2 版 |
| --- | --- | --- |
| 不可撤销项 | 转人工 | 不变 |
| 方案超过 20 项 | 整份转人工 | 后台按批组织待定项，一批的项数由调度控制在上限内，超出的拆到下一批 |
| 批准但高风险 | 转人工 | 不变 |
| 审查证据 | 只有本地摘要与前后值 | 增加程序保存的外部对应与候选摘要；它们来自数据库，不来自模型的参数，并带来源标记 |
| 强证据类操作（归组、发行合并拆分） | 无 | 证据里没有生效的外部对应时，后端直接转人工 |
| 审查不可用 | 不执行 | 不变；后台按退避间隔重试有限次数，仍不可用则待定项停在等模型 |

- 审查模型仍然不自己查资料，也不使用另一个端点。
- 用户在对话里的 `steward` 模式也改用第 2 版；对话里的行为变化只有“证据里多了外部对应”这一点。
- 审查模型与整理用的模型相同时照常自动执行，设置里提示另选一个审查模型。

### 例外

- 审查转人工或没通过的项，记在对应的待定项上（提出的修改、前后值、审查的理由），等管理员处理。它不随方案的 24 小时有效期过期。
- 管理员采纳时，后端按当时的状态重新校验后执行，记为人工确认的操作，字段类的写入人工修正。
- 管理员不采纳时，写“不再提出”的标记。
- 不做站外通知；例外在应用里看。

### 用量

- 后台整理的 token 设每日上限，默认每天 1000 万，可以修改，也可以设为不限。审查调用计入。
- 当天达到上限后不再启动新的运行，正在跑的运行跑完当前这一步后结束；次日继续。
- 只统计后台整理。用户自己在对话里使用管家不受这个上限限制，管家的单次运行上限照旧。
- 当天用量与排队的项数在设置里可见。

## 10. 开关与停止

- 自动整理默认关，由管理员打开。打开意味着向外部服务发送第 8 节列出的内容，并在配置了模型时使用他的密钥，
  这一步由人来做；之后不再逐项询问。
- 一个总开关，加各源的分开关。模型层只在该管理员配置了模型时运行；没配就只做程序层能确定的部分。
- 后台可以暂停：暂停只停后台的工作，不影响已写入的内容与撤销；重新打开总开关时自动解除。暂停与扫描进行中在每次出站之前生效（程序自动整理实施时补充）。
- 不设定时。后台按缺口持续处理，扫描进行时让路。打开开关时存量曲库一次全部进入队列，
  受各源限速与每日上限约束；进度可见，可以暂停。
  2026-11-25 修订（第 16.4 节，尚未实现）：队列按状态与优先级取项；扫描观测到仍在变化的专辑等它稳定后再整理；未收录的专辑 90 天后由程序重查一次，不进模型。
- 下列任一情况出现后，不再发起新的外部请求与模型调用：总开关关闭；该管理员被停用或不再是管理员；
  他的端点或密钥被清除（只停模型层）；某个源被关闭（只停这个源）。
- 总开关关闭时，后端不向任何外部源发请求。已经写入的自动层保留，可以按来源整体撤销。
- 本节的开关管的是后台自动整理。管家对话里的音乐资料工具是管家已有的功能，属于用户本人发起的请求，不受总开关与各源开关影响；
  否则默认关闭的开关会把它关掉，与第 13 节“没有开启自动整理的实例行为不变”相反（接入 MusicBrainz 时补充）。

## 15. 验收场景（实现时写成测试）

用合成曲库验收，曲库覆盖第 2 节列出的各种形态；外部源在自动化测试里用受控的本地服务代替，不请求真实服务。

- 总开关关闭时，后端不向任何外部源发请求，也不发起后台的模型调用。
- 打开开关、不配置模型：扫描后不需要任何人工操作，能匹配上的发行补上了封面、歌词与空的字段，建立了外部对应；
  每一项在整理记录里有来源与依据。
- 人工修正过的字段，自动整理给出不同的值时，显示的仍是人工的值；清除人工修正后显示自动层的值；再清除自动层后显示扫描值。
- 按批撤销后，这一批改过的字段、封面、歌词回到这一批之前的状态；这一批之后有过人工修改的发行同样能撤。
- 撤销过的自动修改在之后的整理里不再出现；重扫不清除自动层、外部封面、外部歌词与外部对应。
- 配置模型后：程序拿不准的项由模型提出修改，审查通过的自动执行；审查转人工或没通过的出现在例外里，
  采纳后执行，不采纳后不再提出。
- 审查不可用时什么都不执行；当天用量达到上限后不再发起模型调用，次日继续；管理员被停用、清除密钥或关掉开关后后台停止。
- MusicBrainz（含封面清单）的请求全实例不超过每秒 1 次；某个源关闭后不再向它发请求。
- 自动的专辑归组、艺人合并、发行合并只在有强证据时发生，每一项都能撤销并回到操作前原样。
- 曲目标题与曲目艺人：人工可改、自动可写、人工优先、可撤销；流媒体下载的单曲能靠 ISRC 或声学指纹匹配并补全。
- 音乐目录以只读方式挂载时全部功能可用，源文件的内容与修改时间不变。
- 真实环境试用一次：真实的四个外部源与一个真实的模型端点，对合成曲库跑完一轮，记录匹配比例、token 消耗与发现的问题。

## 16. 整理链重构（2026-11-25 批准，分步实施，尚未实现）

目标：管理员打开自动整理后，不需要手动整理，也不需要确认任何东西。本地标签能定的由程序即时定，外部源在后台按限流慢慢补，
程序定不了的交给模型，模型能定的经核对后直接写入，各环都没有结果的保持本地原样。

需求、默认值与验收见整理链重构的任务文档（`.trellis/tasks/11-25-curation-chain/`）。本节只写规则；每条规则在对应的实施完成之前不生效，
完成时更新本节的落地位置与对应合同。

### 16.1 原则

替换第 3 节的原则 1、2，原则 3–6 不变：

1. **结局只有三种**：自动写入（可撤销）、保持本地原样、稍后自动重试。没有“等人处理”这个去向。
2. **本地能定的不联网，程序能定的不用模型，模型只做可核对的事**。程序定不了、模型可能解决的都交给模型，不以节省模型用量为由放弃。
3. **核对代替确认**：模型的产出写入前由后端核对，依据是结构、外部源、库内写法或带引用的网页；核对不了的经独立审查，审查不通过即结束。
4. **中断安全**：每条队列按状态取下一项；做完一项存一项；“来源不可用”与“查无结果”分开记。
5. **错了要看得见**：每次自动写入记录核对方式，整理记录可以按核对方式筛选并整批撤销。

模型用量不是优化目标：限制模型只为防止写错、防止失控。花费由每日上限控制；各档每项另有防失控的上限。

### 16.2 本地一环

- 每个字段值带真实性标记：标签给的、推断的、占位的。占位值不进入外部搜索；交给模型的证据带这个标记。
- 每张发行有一个本地分类：带外部编号、有缺口、本地完整、信息不足。分类决定排队先后。
- 规则版本拆分：本地规则、外部匹配规则、巡检提示词各自计版本。本地规则升级不发外部请求；外部规则升级先用已保存的候选与缓存重新判定，
  只对结论会变的专辑重新请求。证据摘要只包含识别用到的字段。

### 16.3 程序的识别

- 条码、目录号、标题加艺人合并成一次搜索；结果先按曲目数与碟结构在本地筛选，再按需读取完整曲目。
- 四级判定：标识命中；发行组唯一；结构吻合（曲目数相等、可比时长在容差内）；定不下来。
- **发行组唯一**只在下列条件都满足时适用：输入是真实值；结果没有被截断；不是合辑或古典；曲目多于 4 首；全部通过的结果属于同一个发行组。
  它只建立发行组与艺人的外部对应（发行组级对应），不建立发行与曲目的对应。发行组级对应可以用于取封面、专辑归组与艺人对应，不用于发行合并。
- 同一发行组内多个版本都通过结构判定时不算歧义，认定到发行组一级。
- 推断值与模型整理的值可以作搜索输入，这类输入的结果只接受带时长的结构判定。
- 散放单曲：标题与艺人是真实值时，文字搜索的结果按标题、艺人与时长筛选；恰好一个录音通过则建立录音对应；多个通过且署名是同一个艺人则只建立艺人对应。
- 艺人对应：专辑已对上时，本地署名与外部署名人数相同、位置对应，名字相同或是外部登记的别名，即建立对应；艺人搜索用能查到别名的写法。
  名字对不上的交模型判断是否同一身份。
- 终止状态：候选都被撤销过或发行已有别的对应的，标为无可用候选，不调用模型。候选为零的先放宽条件重试，再查艺人是否在外部库：
  在的进识别兜底第二档；不在的进联网兜底；都没有结果或没有配置模型的，标为未收录。未收录的 90 天后由程序重查一次。

### 16.4 队列与限流

- MusicBrainz、封面、歌词、艺人资料、声纹各自一条队列，同时进行。封面清单不占 MusicBrainz 的限速额度。某个来源被限流或不可用时只停它自己的队列，等待时间逐步延长。
- 每条队列每次按状态与优先级取下一项，不记翻页位置。优先级：用户手动触发的 → 新入库的 → 带外部编号、条码、ISRC 的 → 有缺口的 → 本地完整的（艺人尚无外部对应的在前）。
- 扫描观测到仍在变化的专辑，等它不再变化后才进入整理。
- 做完一项存一项；重启、暂停、被扫描打断后不重复写入、不丢结果；来源不可用不计失败次数；根目录暂时不可用时不清除整理结果。

### 16.5 自动层

自动层内部按写入依据固定先后，低的不替换高的：程序依据外部源写的 → 模型依据外部源写的 → 模型依据库内或网页写的 → 模型从本地文字整理的。
自动值记录它依据的扫描值，扫描值变化后作废并重新判断。三层的有效值顺序（第 4 节）不变。

### 16.6 模型

| 任务 | 做什么 | 写入条件 |
| --- | --- | --- |
| 巡检 | 扫描稳定后查看新出现的艺人名与专辑名，给出规范身份与问题清单（同一身份的不同名字、错字、同一专辑的不同写法） | 按下面的佐证规则核对；只处理新出现或变化的名字，结果带模型与提示词版本持久化 |
| 本地整理 | 扫描解析不了、但文件名或目录名里有信息的专辑，整理出标题、艺人、曲目标题 | 整理出的值必须来自本地已有的文字；写在自动层最低一级，标为模型推断 |
| 识别兜底第一档 | 在程序取好的候选里选择，不带工具 | 选定的编号按下面的结构核对 |
| 识别兜底第二档 | 模型自己查 MusicBrainz，可以提交任何编号；在识别队列里高于“本地完整”的项排空后才启动 | 同上 |
| 联网兜底 | 开放库没有的艺人与专辑，联网找身份、图片、简介，带引用 | 带引用的网页作为佐证；单独的每日上限 |
| 纠正 | 纠正已有的真实值，与补空分开 | 身份已由结构确认，外部源或库内给出不同的值，判断为错字而不是写法或译名差异；规范化后相同的不改 |

- **完整结构核对**：曲目数相等、可比的时长全部在容差内、曲目多于 4 首。模型选定或提交的外部编号通过的直接写入，不另起审查；没通过的经独立审查，审查不通过即结束。
- **佐证规则**：模型的发现必须有佐证才写入，佐证是外部源、库内写法或带引用的网页。只有模型自己的判断（即使多次一致）不写入；
  “网络搜索”可用时先交联网兜底求证，仍无佐证的记为未采用的建议。模型凭记忆给出的事实类字段（年份、厂牌、目录号等）没有外部来源不写入。
  合并发行、改变曲目归属只接受结构或外部佐证。
- **未采用的建议**取代第 9 节的例外：审查拿不准或不通过的项不写入，该项结束；建议可以查看、可以手动采纳，不计待办。已有的待处理例外迁移过去。
- 合并艺人后显示库内出现次数最多的写法；次数相同取外部源的主名称；人工改名优先。
