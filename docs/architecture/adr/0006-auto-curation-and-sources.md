## 2. 问题

扫描之后，曲库里还剩很多需要整理的地方：缺封面、缺歌词、年份与厂牌是空的、标题与艺人的写法不统一、
同一个艺人有几种名字、同一张专辑的几个版本没有归到一起。现在这些事要么没有数据来源，要么要人一条条确认。

要解决的问题：

1. 外部数据源与模型的判断怎样写进曲库，又不盖掉人改过的内容。
2. 没有人逐条确认时，怎样保证错了能改回来。
3. 哪些事程序可以直接定，哪些交给模型，哪些必须留给人。
4. 没有人发起的运行以谁的身份、花谁的钱、什么时候停。
5. 哪些数据会发给外部源。

适用的曲库不限于某一种：整轨抓的 CD、用 Picard 打过标签的、流媒体下载的单曲、标签很差或没有标签的文件、
华语与欧美，都在范围内（U7）。

## 3. 原则

替换[架构决策摘要](../architecture-decisions.md)“扩展边界的两步走”里“产出只作为候选或证据”的表述（U1、U2）：

1. **三层分工**：程序判定能确定的 → 模型判断程序拿不准的 → 人只处理模型上交或判断不了的。
2. **默认自动，例外才问人**：程序和模型能定的直接生效，不进待确认队列。
3. **安全靠事后可撤，不靠事前确认**：每次自动修改有记录、依据与来源，可以单条撤销，也可以按批或按来源撤销。
   不可撤销的操作不自动执行。
4. **人工修正永远优先**：用户亲手改过的，程序和模型都不再改。
5. **音乐文件只读**。
6. **能力由宿主分配**：外部源只拿到自己那类能力的口子，不能自行取得其他权限。

没有变的：后端是鉴权、事务、版本冲突与幂等的唯一权威；所有持久修改经 `operations.Run`；
弱相似（标题、艺人、年份或目录相近）不能作为合并的依据。

## 4. 三层与优先顺序

| 层 | 谁写 | 说明 |
| --- | --- | --- |
| 人工修正 | 用户亲手改；用户在对话或 MCP 里让管家改（默认 1） | 现有的修正，行为不变 |
| 自动层（新） | 后台自动整理：程序与模型 | 外部源给的值、模型判断的值 |
| 扫描值 | 扫描 | 现有的扫描列 |

- 有效值 = 人工修正 → 自动层 → 扫描值，逐字段取第一个有值的。
- 结构保证：扫描只写扫描值，自动整理只写自动层，人工修正只由人工路径写。三者互不覆盖，优先顺序只在读取时体现。
  “人工修正永远优先”因此不依赖运行时判断：自动写入的执行器不接触人工修正。
- 用户清除人工修正后，显示自动层的值；再清除自动层后，显示扫描值。
- 重扫不清除自动层、外部封面、外部歌词与外部对应。
- 自动层的一个字段只有一个值：程序先写、模型后来改写同一字段时，后写的替换先写的，前一个值留在操作记录里。

各类数据：

| 数据 | 规则 |
| --- | --- |
| 发行级八个字段（标题、专辑艺人、年份、流派、厂牌、编号、版本说明、条码） | 程序只补空缺；改已有的值由模型判断 |
| 曲目标题、曲目艺人（U9） | 同上；同时新建曲目的人工修正。曲序与碟号不可修正 |
| 外部对应 | 本地的发行、专辑、曲目、艺人与外部 ID 的对应可以保存，带匹配方式、把握程度与状态；一个本地对象在一个源里至多一个生效的对应 |
| 封面、歌词（默认 3） | 外部来的单独存放，不占本地的位置；只补空缺，本地有时用本地的。一个发行至多一张外部封面、一首曲目至多一份外部歌词；已经有了就不再写第二份，要换先撤销（B2 说明） |
| 结构操作（归组、默认版本、核对、认领、艺人合并改名、发行合并拆分） | 不是字段值，没有“层”；靠操作记录的来源区分人工与自动，条件见第 7 节 |

## 5. 记录、批次与撤销

### 记录

- 三层共用一条写入路径：所有持久修改经 `operations.Run`。程序层与模型层的区别只在“谁做的判断”，不在“怎么写”。
- 操作者是开启自动整理的管理员（U5）；不新造系统用户。
- 来源增加“自动整理”一种，并记下是哪个外部源或模型、哪一批、依据是什么。
- 批次：后台整理的一段连续工作是一批（程序层按时间或数量切分，模型层一次运行是一批）。批次记录起止时间、
  属于程序层还是模型层、各类改动的数量与用量。
- 操作记录可以按来源、按批次筛选。

### 撤销

现有规则要求目标的版本号等于这条操作留下的版本号，同一发行上之后的任何修改都会让更早的操作撤不了。
自动修改不沿用这条规则：

- 自动层的每个值记着是哪条操作写的。撤销一条自动修改时，如果这个值现在仍是这条操作写的，就恢复到它之前的自动层状态
  （之前的值，或没有值）；如果已经被更晚的自动修改改写，返回冲突，不改动。
- 人工修正在另一层，不参与判断。用户之后改了同一发行的任何字段，都不妨碍撤销自动层。
- 自动层的写入不递增发行的 `edit_revision`，因此不会让人工修改的撤销失效。
- 按批撤销：按时间倒序逐条撤销这一批里仍可撤的操作，返回撤了多少、跳过多少与原因。按来源撤销同理。
  它们本身是受治理操作，也有记录。
- 结构操作的撤销沿用各自现有的规则。之后被人工改过的结构，自动撤销被拒绝并在结果里列出：
  人已经在这个结构上做了新的决定。

### 撤销之后不再应用（默认 2）

用户撤销一条自动修改，等于表达“这个改动不对”。后端记下“不再提出”的标记，程序层与模型层提出修改之前都先查它。
例外里选“不采纳”写同一种标记。标记只挡同一个改动，不挡同一处的其他值；用户可以清掉标记。

外部封面与外部歌词的“同一个改动”按两样判定，撤销时两样都记，命中任一样就不再写：内容（图片字节或规范化后的歌词文本），
与外部编号（哪个源的哪一张图、哪一条歌词记录）。只按内容挡不住同一张图的另一档缩略图（B2 说明）。
外部封面与外部歌词的撤销就是去掉这一份：它们只在没有时写入，没有“之前的值”可恢复。歌词的自动修改记在曲目当时所在的发行上（B2 说明）。

## 6. 程序层的判定

程序层按缺口工作：还没处理过的、输入变了的、匹配规则升级了的才处理；扫描进行时让路。

匹配依据按可靠程度排列，前面的命中就不再用后面的：

1. 标签里的外部 ID。
2. 条码；厂牌加编号。
3. 曲目里的 ISRC 集合。
4. 由曲目数与时长推出的光盘目录。子任务 B1 已核实可行：整轨抓取的 CD 可以由各轨时长重建目录并算出 disc ID 做精确查询；
   没有精确命中时退为按时长的模糊结果，它只能缩小到同一专辑的若干 CD 版本，两者的可靠程度要分开对待。
5. 声学指纹（AcoustID）。
6. 标题、艺人、曲目数与时长的查询：只产生候选，从不直接判定。

“把握足够”才由程序直接定：必须是唯一候选，并且至少有一项独立的佐证（如曲目数一致、各曲时长在容差内）；
有任何相反的证据就降为拿不准。宁可多交给模型，不可错判。具体规则由子任务 C 逐条定义并用测试固定（见[自动整理合同](../../../.trellis/spec/backend/curation-contracts.md)第 15 节）。
匹配的输入只取人工修正与扫描值：自动层是匹配的产出，不能拿来证明自己（C 说明）。

- 把握足够：保存外部对应，把空缺的字段补到自动层，本地没有封面或歌词时取外部的，符合第 7 节条件的结构操作直接做。
- 拿不准或没匹配上：形成待定项，带上候选、本地证据与冲突点，交给模型层。没配置模型时停在那里。
- 匹配不上的记为已尝试，文件变了或规则升级之后才再试（U12）。

## 7. 结构操作的自动使用

| 操作 | 自动使用的条件 |
| --- | --- |
| 问题核对、默认版本、认领 | 模型提出，审查通过 |
| 专辑归组（归入、移出） | 只在强证据下：两个发行的外部对应指向同一个外部专辑（release group）。程序层可以直接做（只做归入）；模型提出时证据里必须有这条对应。发行最近一次归组是人做的，不再自动归组（C 说明） |
| 艺人合并、改名 | 先做成可撤销。程序层：两个本地艺人的外部对应指向同一个外部艺人时合并；其余由模型提出并审查 |
| 忽略艺人候选 | 先做成可撤销，之后可以自动 |
| 艺人拆分 | 不自动提出；它是纠正错误合并的手段，由撤销合并覆盖 |
| 发行的合并与拆分 | 只在强证据下：外部对应表明这些曲目属于同一个外部发行（合并）或不同的外部发行（拆分）。一律由模型提出并审查，程序层不直接做 |

**强证据**是后端的硬规则，不由模型自述：证据必须是已经保存、状态为生效的外部对应。
模型在方案里声称有依据而库里没有对应记录时，后端转人工。

这是对 [ADR 0002](0002-metadata-overlays.md) 第六节“强证据路径”的批准：获批的共同分组标识是上面这一种，
并且只来自第 8 节批准的外部源。标题、艺人、年份、目录相似，或多个模型一致，仍然只能产生候选。

## 8. 外部源

### 形态（U4）

- 每个源是编进程序的适配器，放在与管家无关的位置；不建第三方插件宿主、能力注册表或独立进程的插件协议。
  以后出现第三方来写源的需求时，再把已经稳定的接口升级为宿主，条件见架构决策摘要的“扩展边界的两步走”。
- 每个源有一份声明：标识与显示名、提供的能力、启用条件、限速、需要的配置项。设置页按声明列出各源的开关。
- 能力是几个窄接口，源按自己的情况实现其中几个：发行查找、录音查找、艺人查找、指纹识别、封面、歌词。
  调用方（程序层的匹配、管家的工具）只面向能力，不直接依赖某个源。
- 管家现有的两个音乐资料工具改为走同一个 MusicBrainz 适配器，工具的名字与输出不变。
  它们是 MusicBrainz 专用的工具（自由查询串与 include 列表），直接用适配器的实体级读取与查询；“只面向能力”约束的是程序层（B1 说明）。

### 首批的源（U8）

| 源 | 能力 | 默认 | 启用条件 |
| --- | --- | --- | --- |
| MusicBrainz | 发行、录音、艺人查找 | 开 | 总开关打开 |
| Cover Art Archive | 封面 | 开 | 总开关打开 |
| LRCLIB | 歌词 | 开 | 总开关打开 |
| AcoustID | 指纹识别 | 开（B3 修订：原为关） | 管理员填入自己的用户密钥，并且镜像里有 Chromaprint（B3：静态 `fpcalc`）。B3 补充修订：发布镜像内置 ROOMusic 注册的应用密钥（原为“管理员填入自己注册的应用密钥，仓库不内置共用密钥”） |

- 扫描解析并保存标签里的 MusicBrainz 各类 ID、ISRC 与 AcoustID。
- 生产镜像增加 Chromaprint 用来计算声学指纹。没有它或没填密钥时，AcoustID 显示为未启用，其余功能不受影响。
- 没有官方开放接口的平台（网易云、QQ 音乐等）不内置。艺人图片与简介、Discogs、华语覆盖更好的封面与歌词源不在首批。

### 共用的规则

- 出站：管家与外部源共用同一个出站客户端（现有的客户端迁到平台层），地址规则沿用 [ADR 0005](0005-steward-data-and-egress.md) 第 5 节。
  地址由程序固定的源，允许它官方的重定向目标（Cover Art Archive 的图片实际由 archive.org 提供）。
- 限速：每个源一个全实例的限速器。MusicBrainz 与 Cover Art Archive 的清单请求共用每秒 1 次；
  用户在对话里的查询与后台匹配共用同一个限速器，对话优先。Cover Art Archive 的图片下载另设每秒 1 次：它的第一跳也经过 MetaBrainz 的网关，
  所以对这个网关合计每秒 2 次（Cover Art Archive 的文档写明目前没有限速规则；B2 说明）。
- 缓存：按请求内容缓存响应；有结果的缓存时间长，空结果与失败的缓存时间短。
- 重试：服务不可用与限流按源的要求退避重试，有上限；超过上限记为稍后再试，不算匹配失败。
- 配置：各源的开关与 AcoustID 密钥是实例级的，由管理员设置；密钥用现有的密钥库加密，绑定实例与用途。
- 存放（默认 7）：外部下载的封面、指纹与查询缓存放在数据目录，属于可以重新获取的数据，不进备份。
  （B3 修订：声学指纹按需计算、量小，缓存放在数据库并随曲目删除，见决策记录“B3 说明”。）
  自动层、外部对应、待定项与批次在数据库里，随数据库备份。恢复备份后外部封面的记录还在而图片文件不在：之后的整理把它当作缺口重新获取，
  新的写入替换旧记录（B2 说明）。
- 下载的图片沿用现有封面的校验（大小、格式）与内容寻址存储。

### 发给外部源的数据

| 源 | 发出的内容 |
| --- | --- |
| MusicBrainz | 外部 ID、条码、ISRC、厂牌与编号、标题与艺人的查询词、由曲目时长推出的光盘目录 |
| Cover Art Archive | 外部 ID |
| LRCLIB | 曲目标题、艺人、专辑名、时长 |
| AcoustID | 声学指纹与时长，以及应用密钥（B3 补充：发布镜像里是 ROOMusic 内置的）与管理员填入的用户密钥 |

- 不发送音频、文件路径与实例标识。
- 声学指纹是由音频算出的摘要，不能还原音频；它是音频派生的数据，只发给 AcoustID。
- 外部源返回的内容一律是不可信文本，进入模型之前按 ADR 0005 第 4 节加来源标记。

## 9. 模型层：后台运行

### 身份（U5）

- 后台整理归开启它的管理员：用他自己配置的端点与密钥，可以单独选一个“整理用的模型”，不选就用对话模型。
- 管理员开启的自动整理视为该管理员本人的请求：发给模型的数据范围、密钥的使用都按他本人使用管家时的规则。
- 不引入实例级共享的模型密钥，不新造系统用户。

### 运行（默认 4、默认 6）

- 复用管家的运行、工具、方案与审查。每批待定项是一个归该管理员所有、标为自动整理的会话；
  它不混在他自己的对话列表里，从整理记录进入。可以点开看模型查了什么、为什么这么判断，也可以接着对话纠正。
- 运行由后台调度启动，第一条消息由程序生成。模式固定为 `steward`：必须经过审查，不能直接执行。
- 自动整理的运行里，字段类的写工具写自动层；工具对模型的名字与参数不变，由运行的来源决定写到哪一层。
- 全实例同一时刻只跑一个后台的模型运行，不占用户自己的并发名额。

### 审查策略第 2 版

| 规则 | 第 1 版 | 第 2 版 |
| --- | --- | --- |
| 不可撤销项 | 转人工 | 不变 |
| 方案超过 20 项 | 整份转人工 | 后台按批组织待定项，一批的项数由调度控制在上限内，超出的拆到下一批 |
| 批准但高风险 | 转人工 | 不变 |
| 审查证据 | 只有本地摘要与前后值 | 增加程序保存的外部对应与候选摘要；它们来自数据库，不来自模型的参数，并带来源标记 |
| 强证据类操作（归组、发行合并拆分） | 无 | 证据里没有生效的外部对应时，后端直接转人工 |
| 审查不可用 | 不执行 | 不变；后台按退避间隔重试有限次数，仍不可用则待定项停在等模型 |

- 审查模型仍然不自己查资料，也不使用另一个端点。
- 用户在对话里的 `steward` 模式也改用第 2 版；对话里的行为变化只有“证据里多了外部对应”这一点。
- 审查模型与整理用的模型相同时照常自动执行，设置里提示另选一个审查模型（U11）。

### 例外（默认 5）

- 审查转人工或没通过的项，记在对应的待定项上（提出的修改、前后值、审查的理由），等管理员处理。它不随方案的 24 小时有效期过期。
- 管理员采纳时，后端按当时的状态重新校验后执行，记为人工确认的操作，字段类的写入人工修正。
- 管理员不采纳时，写“不再提出”的标记。
- 不做站外通知；例外在应用里看。

### 用量（U10）

- 后台整理的 token 设每日上限，默认每天 1000 万，可以修改，也可以设为不限。审查调用计入。
- 当天达到上限后不再启动新的运行，正在跑的运行跑完当前这一步后结束；次日继续。
- 只统计后台整理。用户自己在对话里使用管家不受这个上限限制，M6 的单次运行上限照旧。
- 当天用量与排队的项数在设置里可见。

## 10. 开关与停止（U12）

- 自动整理默认关，由管理员打开。打开意味着向外部服务发送第 8 节列出的内容，并在配置了模型时使用他的密钥，
  这一步由人来做；之后不再逐项询问。
- 一个总开关，加各源的分开关。模型层只在该管理员配置了模型时运行；没配就只做程序层能确定的部分。
- 后台可以暂停：暂停只停后台的工作，不影响已写入的内容与撤销；重新打开总开关时自动解除。暂停与扫描进行中在每次出站之前生效（C 说明）。
- 不设定时。后台按缺口持续处理，扫描进行时让路。打开开关时存量曲库一次全部进入队列，
  受各源限速与每日上限约束；进度可见，可以暂停。
- 下列任一情况出现后，不再发起新的外部请求与模型调用：总开关关闭；该管理员被停用或不再是管理员；
  他的端点或密钥被清除（只停模型层）；某个源被关闭（只停这个源）。
- 总开关关闭时，后端不向任何外部源发请求。已经写入的自动层保留，可以按来源整体撤销。
- 本节的开关管的是后台自动整理。管家对话里的音乐资料工具是 M6 已有的功能，属于用户本人发起的请求，不受总开关与各源开关影响；
  否则默认关闭的开关会把它关掉，与第 13 节“没有开启自动整理的实例行为不变”相反（B1 说明）。

## 12. 已接受的剩余风险

| 风险 | 为什么接受 | 约束后果的手段 |
| --- | --- | --- |
| 自动修改可能是错的，并且在有人发现之前一直生效 | 产品定位是减少人的确认（U1） | 每条有记录、来源与依据，可以单条、按批、按来源撤销；人工修正不会被盖；撤销过的不再应用；不可撤销的操作不自动执行 |
| 外部源本身的数据有错，会被当作把握足够的依据写进曲库 | 没有更权威的开放数据源 | 只写自动层；把握规则要求独立佐证，有相反证据就交给模型；可以按来源整体撤销 |
| 审查模型与整理用的模型相同时，两者可能被同一段外部文字误导，而后台没有人在场（U11） | 强制两个模型会让只有一个模型的用户用不上 | 审查是全新上下文的独立调用，只看后端生成的证据与前后值；强证据是后端的硬规则；自动修改全部可撤销；设置里提示 |
| 外部源的返回内容进入模型，可能带有写给模型看的指令 | 目前没有可靠的技术手段 | 来源标记；模式固定为 `steward`，写入必须经过审查；模型不能自己声明依据 |
| 外部服务能看到查询词（专辑、曲目、艺人的名字，条码，声学指纹）与实例的出口地址 | 这是使用外部数据源的前提 | 默认关；打开前说明会发出什么；每个源可以单独关；不发路径、音频与实例标识 |
| 无人值守时花的是管理员自己的密钥 | 不引入共享密钥（U5） | 每日上限默认开；用量可见；关掉开关即停 |
| 外部源对华语与冷门录音的覆盖可能不足，这部分主要靠模型判断，消耗更多 | 首批只接有官方开放接口的源 | 每日上限；匹配比例在真实试用时记录；接口统一后可以再加源 |
| 存量曲库的首次整理受 MusicBrainz 每秒 1 次的限制，几千张专辑需要数小时到数天 | 必须遵守外部源的使用要求 | 进度可见，可以暂停；缓存避免重复请求 |

## 14. 未采纳的方案

| 方案 | 不采纳的原因 |
| --- | --- |
| 外部产出与模型判断一律作为候选，等人确认 | 太严，实际操作不顺；与产品定位相反（U1、U2） |
| 自动产出写进现有的修正表，加一列作者 | 一个字段只有一行，自动与人工会互相覆盖，优先顺序要靠运行时判断 |
| 自动修改沿用现有的撤销规则（核对版本号） | 用户改一次就让整批撤不了 |
| 后台运行用系统用户加实例级共享的模型密钥 | 推翻“密钥按用户配置”，多一套密钥管理 |
| 模型层另写一条“一次调用出结论”的流水线 | 省 token，但过程不可见、不能接着对话纠正，审查与工具要重做一遍。子任务 D 实测消耗后可以再评估 |
| 例外沿用会话里的待确认方案 | 24 小时过期，用户发新消息即作废 |
| 用外部封面或歌词替换本地已有的 | 要定“哪一个更好”的规则，容易引起争议；首版只补空缺 |
| 建第三方插件宿主（独立进程、通信协议、插件分发） | 目前没有非要第三方来写的源；整理体验取决于写入与模型判断，不取决于宿主（U4） |
| 审查必须使用与整理不同的模型 | 只有一个模型的用户用不上（U11） |
| 定时整理（每天固定时间跑一次） | 按缺口持续处理更及时，也不需要用户设置时间（U12） |
| 仓库内置共用的 AcoustID 密钥 | 密钥的限额与使用条款按应用计，各实例应自己注册（U8）。B3 补充起改为内置：AcoustID 推荐应用内置自己的应用密钥、按用户密钥区分使用者；密钥不进仓库，只进发布镜像 |
| 不接 AcoustID，只靠标签里的标识 | 流媒体下载的单曲与标签差的文件没有条码和编号，只能靠 ISRC 或声学指纹（U7、U8） |

## 15. 验收场景（各子任务实现时写成测试）

用合成曲库验收，曲库覆盖第 2 节列出的各种形态；外部源在自动化测试里用受控的本地服务代替，不请求真实服务。

- 总开关关闭时，后端不向任何外部源发请求，也不发起后台的模型调用。
- 打开开关、不配置模型：扫描后不需要任何人工操作，能匹配上的发行补上了封面、歌词与空的字段，建立了外部对应；
  每一项在整理记录里有来源与依据。
- 人工修正过的字段，自动整理给出不同的值时，显示的仍是人工的值；清除人工修正后显示自动层的值；再清除自动层后显示扫描值。
- 按批撤销后，这一批改过的字段、封面、歌词回到这一批之前的状态；这一批之后有过人工修改的发行同样能撤。
- 撤销过的自动修改在之后的整理里不再出现；重扫不清除自动层、外部封面、外部歌词与外部对应。
- 配置模型后：程序拿不准的项由模型提出修改，审查通过的自动执行；审查转人工或没通过的出现在例外里，
  采纳后执行，不采纳后不再提出。
- 审查不可用时什么都不执行；当天用量达到上限后不再发起模型调用，次日继续；管理员被停用、清除密钥或关掉开关后后台停止。
- MusicBrainz（含封面清单）的请求全实例不超过每秒 1 次；某个源关闭后不再向它发请求。
- 自动的专辑归组、艺人合并、发行合并只在有强证据时发生，每一项都能撤销并回到操作前原样。
- 曲目标题与曲目艺人：人工可改、自动可写、人工优先、可撤销；流媒体下载的单曲能靠 ISRC 或声学指纹匹配并补全。
- 音乐目录以只读方式挂载时全部功能可用，源文件的内容与修改时间不变。
- 真实环境试用一次：真实的四个外部源与一个真实的模型端点，对合成曲库跑完一轮，记录匹配比例、token 消耗与发现的问题。
