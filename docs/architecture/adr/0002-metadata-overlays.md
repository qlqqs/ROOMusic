## 二、要解决的问题

若人工直接修改现有扫描列，下次扫描会覆盖结果；若禁止扫描更新这些列，又会失去新来源
事实。仅在浏览器覆盖显示则无法让详情、检索和其他用户得到一致结果。另一个问题是来源
匹配与业务身份目前紧密相连：保住一条 Track 的 UUID，不一定保住它所属的 Release；
保住一个目录锚点，也不能证明该目录里的内容仍是同一个版本。

因此需要同时回答“观察到什么”“用户要求展示什么”“为什么这样展示”和“这个修正仍然
属于谁”，不能只增加一个优先级更高的字符串。

## 三、推荐候选：分离事实、修正意图与有效读值

### 责任与边界数据流

当前 scanner 会直接写图；下表是未来写路径必须形成的职责，不宣称已有独立模块。

| 责任 | 推荐归属 | 不得承担的责任 |
| --- | --- | --- |
| 读取文件、解析标签/CUE、生成观察及扫描终态 | library/scanner 与纯 organizer 规则 | 覆盖人工修正；以相似文件名迁移用户意图；把缺失误判成删除授权 |
| 图身份、来源绑定、字段规则、关系变更和有效值投影 | catalog 应用/领域边界 | 从 UI 展示值反推来源事实；允许 scanner 绕过已确认的关系约束 |
| 修正操作的授权、审批、revision、幂等、记录和逆操作协调 | operations 合同与 catalog 类型化用例协作 | 任意表/任意字段修改器；自行决定音乐领域归组规则 |
| 解码、展示、编辑预览和冲突提示 | REST 边界与前端 | 在客户端决定最终有效值或权限；把草案审批当成已提交 |

```text
只读音乐源 → 扫描观察 + 当前规则决策 ───────────┐
                                             │
人工修正提案 → 后端授权/必要审批 → catalog 修正意图 ├→ catalog 有效投影
                                  └→ 操作记录  │    → REST → 页面/检索
经确认的来源映射与版本关系 ────────────────────┘
```

扫描观察流不经过逐字段 Change Set；修正、迁移修正和人工结构变更才进入受治理写路径。
未来 Steward 只能提交同一种提案，不能成为独立的字段权威。

### 覆盖语义

推荐首先针对批准的少量描述字段实施，不预设所有扫描列都可编辑。路径、来源身份、编解码
事实、CUE 时间边界及图关系不能伪装成普通文本覆盖。

| 修正意图 | 有效值 | 后续重扫行为 |
| --- | --- | --- |
| 无覆盖／清除覆盖 | 采用**当前**扫描基值，而非创建修正时的旧值 | 随扫描基值更新 |
| 设置明确值 | 采用经过字段校验的人工值 | 更新基值与证据，不抹掉人工值 |
| 显式设空 | 对允许空值的字段，显示明确空值，抑制扫描回填 | 扫描有值也不自动恢复 |

- “清除覆盖”是撤销人工优先权；“设空”本身是一项持续生效的修正。不能用空字符串、
  一个无语义区分的 `null` 或简单空值回退把二者混为一谈。
- 必填字段能否设空由领域合同决定；不允许设空时应拒绝，而非自动换成“未知”并报告成功。
  集合字段的空集合与没有覆盖也要区分；署名的集合编辑粒度在实施前确定。
- 编辑请求未涉及某字段，表示不修改该字段，不隐含清除覆盖。
- 推荐按实体和字段保存共享资料库修正；用户自己的收藏/歌单不是元数据覆盖，不从这里
  获得共享治理权限。
- 投影应能解释：扫描基值、修正意图、有效值及选中原因。检索、排序、分页、列表和详情
  必须使用同一有效语义，不能只在前端把卡片文字替换。
- 人工修正不是新的 tag 证据，也不自动消除所有扫描不确定性；“已人工处理”与原始规则
  仍有疑问应分别表达，具体问题状态属于后续设计。

## 四、身份稳定性的实际边界

以下仅保证已核对代码中的匹配机制，不保证音频内容相同或任意路径演进稳定。

| 身份依据 | 当前构成与可复用条件 | 不保证的场景 |
| --- | --- | --- |
| 物理 `source_identity` | root ID、`physical:v1` 与规范化相对路径；同 root、同路径重扫匹配原 Track | 文件重命名、移动、换 root；同路径被其他内容替换仍可能复用，当前并非内容指纹身份 |
| CUE `source_identity` | root ID、`cue:v1`、sheet 相对路径、父音频相对路径、轨号、`INDEX 01` 帧 | sheet/父文件改名或移动、轨号/起始帧变化；旧身份兼容只是升级路径，不是通用映射保证 |
| 普通、多碟、Box 叶候选 `candidate_anchor` | root、`v2`、候选种类、规范化范围，分区为空 | 目录范围变化、普通/多碟/拆分种类变化；标题修改若影响分桶，也可能间接改变锚点 |
| 散落文件、同目录拆分候选 `candidate_anchor` | 还使用候选内排序最小的相对来源路径作分区；无来源才退到分组分区 | 最小成员移除/改名、新增更小成员、分桶集合变化；不保证增减文件后 Release ID 不变 |
| 现有图 UUID | 命中锚点保留 Release/Group；命中来源保留 Track，Medium 按所属 Release 与碟序定位 | Track 复用不保证所属 Release/Medium 不变；新锚点不会自动继承旧 Release 的人工意图 |

定位：[identity.go](../../../backend/internal/catalog/identity.go) 与 [persist.go](../../../backend/internal/catalog/persist.go) 的身份与持久化函数、
[organizer.go](../../../backend/internal/catalog/organizer.go) 的 `stableAnchorPartition` 和
`CandidateIdentity`；反例见[来源身份测试](../../../backend/internal/library/scan_rules_test.go)
`TestTrackSourceIdentityIsStableOnlyForSameRootAndPath` 及
[整理测试](../../../backend/internal/catalog/organizer_test.go)
`TestOrganizeRootUnknownAndCueIdentityAreExplicit`。

[0011 迁移](../../../backend/migrations/0011_scan_staging_and_identity.sql)只在无冲突时升级旧
Release 锚点；会收敛到同一锚点的旧记录保留旧标记，交给后续扫描匹配 Track。这不是人工
版本合并决策，更不能作为覆盖层自动迁移的充分证据。

### 推荐的修正绑定及演进规则

修正应引用 catalog 管理的实体身份与明确的适用范围，而不是把 `candidate_anchor` 或
`source_identity` 字符串直接当永久修正主键。仍须校验该实体的来源绑定和关系版本；仅换成
UUID 外键无法解决内容被替换、Track 被重新挂接或旧 Release 已无可见 Track 的问题。

| 场景 | 行为（尚待实现；标“已批准”的行由阶段 I 实施） |
| --- | --- |
| 同来源、同结构重扫 | 保留实体绑定和修正，只更新观察；相关基值变化可标示待复核，但不得静默删改既有修正 |
| 仅路径书写被规范化 | 沿用现有安全路径规范化，不把越界、跨 root 或真实改名当成等价路径 |
| 物理文件或目录重命名、移动（同一 root） | **已批准（2026-09-28）**：只在完整成功扫描中，把本轮新出现且没有身份匹配的观察，与本轮将被置为缺失的旧曲目按音频指纹配对；唯一 1:1 完全相同才重绑定到原 UUID，修正与人工关系随之保留。多对多、指纹不同或扫描不完整时不重绑定，按原规则把旧来源置为缺失，并留待人工认领。仍不按标题相似搬移修正 |
| 跨 root 移动、重新注册导致 root 身份变化 | 不推定身份连续；若要转移修正，必须有单独审阅的绑定映射、双方 revision、影响预览和逆操作 |
| 分桶、最小来源或 CUE 分轨结构变化 | **已批准（2026-09-28）**：Release 按所含曲目的成员关系匹配——复用包含候选多数曲目、且没有被重叠更高的候选占用的既有 Release，锚点降为定位信息；因此增删文件或最小来源变化不再换 Release ID。无法证明成员关系连续时保留原修正，隔离待认领的新观察/提案，不静默重挂到新目标 |
| Track 来源相同，但扫描拟改变其所属版本 | 字段修正与关系修正分别判断。已确认的关系不能被当前 `medium_id` 重写逻辑绕过；必须先形成 catalog 冲突处理路径 |
| 合并、拆分或重新归组 | 先明确每个修正的目标映射和冲突决议；不能把 Release 修正复制给全部拆分结果，或按最后写入覆盖合并双方修正 |
| 完整扫描确认缺失 | 保留实体、修正和证据，不清理人工历史；普通浏览仍遵守 present-only，未来管理入口才负责解释悬挂修正 |
| 来源重新出现 | 原身份与绑定可确认时继续使用原修正；新身份不自动继承。同路径复用无法证明内容相同：阶段 I 保存音频指纹后，同路径但指纹不同的内容不静默沿用原身份 |
| 扫描失败、取消或不完整 | 已提交观察可以保留，但不得负向 missing 对账、删除覆盖或宣称整库回滚；对应来源绑定冲突仍单独可见 |

此处的“隔离”是保留证据、停止有歧义的修正转移或人工关系变更，不是新增文件隔离工具，
也不是丢弃新扫描事实。M3 开启编辑前，必须选择并测试与当前扫描写图路径相容的最小方案。
不能先开放修正，再把扫描冲突推迟到 M4。

## 五、revision、provenance 与有效投影

### 并发与授权

- 当前没有 catalog 编辑 revision。推荐区分修正状态版本、结构/来源绑定版本和相关扫描
  基值版本；具体粒度由实施子任务决定，但提案所依赖的全部状态必须可检验。
- 保存、清除覆盖、设空及转移都要携带预期版本，在后端授权后进行比较。冲突应返回当前
  安全摘要供重新预览，不使用最后写入获胜，不自动扩大覆盖范围。
- 以扫描证据为依据的待审批提案必须绑定该证据版本或摘要。相关基值、归属或来源可用性
  变化后重新评审；仅时间戳刷新、语义相同的重扫不应被当作新的人工修改。
- 修正、对应记录、最小恢复信息及幂等结果需同一事务提交。扫描对相关身份/关系的更新
  也必须参与同一并发约束，不能依赖“编辑请求之间有锁”来防扫描覆盖。
- 幂等请求包含目标、字段、操作语义及预期版本；“设空”与“清除覆盖”不能得到相同指纹。
  具体执行与重试合同见 [ADR 0003](0003-governed-operations.md)。

### 来源可解释性

推荐保留三个不同的记录视角：

1. **当前观察/规则证据**：沿用 tag、CUE、推断、规则、扫描 ID 和观察时间；继续标明
   `inferred`、候选与置信度，不把人工选择伪装为高置信 tag。
2. **持久修正来源**：记录实际 actor、目标及字段、设置/设空/清除的意图、理由、相关
   观察摘要、操作引用和版本；未来有 Agent 时另记提案者及审阅者，不取代实际授权主体。
3. **有效值解释**：指出本次展示采用扫描还是修正，以及底层值是否已变化。普通读者只
   获得批准的安全投影；完整证据的权限不能因新投影被绕过，不披露绝对路径或私有素材。

当前观察行会替换，修正审计不能只引用一个下一次重扫就消失的证据行。需要保留支持解释及
恢复的最小、安全、版本化证据摘要；它不是音频副本或完整数据库快照。

撤销修正应恢复**前一个修正意图**，包括“无覆盖”和“显式空”的区别，而不是把旧有效值写回
扫描列。例如清除覆盖后底层值已经变化，恢复无覆盖应读当前基值；若预览/批准依赖的相关
证据已变化，则先报冲突重新确认，不能声称整库退回历史时刻。

## 六、ReleaseGroup 实体化与覆盖层的关系

已有 `release_groups` 表只证明存在关系占位，不证明已支持作品/版本族的语义治理。Release
保留为不同版本的实体。2026-09-28 批准的安排：阶段 I 提供按组只读接口（此前每个 Release 各占
一组，接口自然退化为一组一个版本）；组成员调整作为 M3 的试点受治理操作；默认版本、版本对比
与 Release 合并/拆分在 M4 及之后。

- **强证据路径**：只有经批准、可追溯且语义层级明确的共同分组标识或明确关系，才可进入
  确定性分组规则；必须核对它描述的是版本族而非单个发行、录音或曲目，并排除相反证据。
  当前仓库没有这样的跨版本自动归组写路径；本 ADR 不批准任何外部提供方或标签字段，
  Core 1 也不引入强证据自动归组。
- **人工确认路径（已批准为 Core 1 的唯一归组方式，2026-09-28）**：由获授权的人确认具体
  成员、版本差异、理由、影响范围和预期 revision，再进入受治理操作。
- 标题、艺人、年份、目录相似，或未经语义核验的条码/目录号，只能产生候选；多个模型
  一致、人工把标题改成相同值，也不能升级成自动合并证据。
- 严格多碟和 CUE 父子规则说明的是一个 Release 的来源结构，不是不同版本必属同一
  ReleaseGroup 的证据。
- Group 成员调整不是删除/折叠 Release；Release 合并、拆分和 Track 重挂必须分别定义
  类型化操作、修正分配、版本冲突和逆操作。它们不能藏在一次字段编辑里。
- Group、Release、Track 的覆盖作用域必须独立。未来 Group 展示字段不得反写所有版本
  的观察；继承和默认版本策略另行确认，不能让某个版本的“设空”意外清空整组。
- 已批准的分组关系应与自动归组观察分开；重扫出现新候选或反证时产生待复核状态，而非
  无记录地覆盖人工归组。弱证据或映射歧义一律保持版本独立。

## 七、替代方案与取舍

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 独立修正意图 + catalog 有效投影（推荐候选） | 重扫与人工意图可共存，清除与逆操作可解释 | 必须补身份演进、revision、查询一致性及审计；不能只加一个覆盖表就开放编辑 |
| 直接覆写 Release/Track 扫描列 | 初次实现少、现有读取无需适配 | 重扫覆盖、观察与人工来源混淆，无法可靠撤销；不推荐 |
| 人工编辑后冻结扫描列 | 看似能保住人工结果 | 丢失最新来源事实和缺失/冲突证据；不推荐 |
| 写回源文件标签后再扫描 | 其他软件可能读到标签 | 违反当前源文件只读边界，还需独立文件安全、备份与恢复能力；本路线不启用 |
| 仅前端或本地浏览器覆盖 | 不改后端即可演示 | 多用户、检索、审计与恢复不一致；不能作为真实修正交付 |
| 所有观察与编辑都做完整事件溯源 | 理论上可重放完整历史 | 当前观察历史不完整，迁移和存储成本扩大；没有本阶段必要性，不推荐 |

## 八、阶段、迁移与失败恢复

- **M0**：只交付此草案及仓库事实；不改 schema、路由或权限。
- **B0**：纯拆包，不借拆包改变身份和重扫语义；catalog 先拆，为阶段 I 提供修改落点。
- **阶段 I（已批准）**：新增音频指纹迁移，实施成员关系匹配与同 root 保守重绑定，用合成 fixture
  的集成测试证明 ID 稳定；提供 ReleaseGroup 只读接口。不开放任何修正写入。
- **M1a/M1b**：M1a 使用现有读取与管理 API；M1b 使用阶段 I 的按组只读接口。
- **M3 候选**：批准有限字段、有效投影和受治理写路径后，才能开放修正；首批试点为字段修正与
  ReleaseGroup 成员调整。`editor`、新的审批政策和 Agent 能力均不能因覆盖层存在而自动启用。
- **M4 候选**：在 M3 的写路径、映射和恢复验证通过后，实现默认版本、版本对比与 Release 合并/拆分。
- **M6 候选**：复用相同后端用例，不直接操作覆盖存储，不由本 ADR 预先纳入范围。

实施时只通过新的已审阅迁移演进，不修改既有迁移。旧扫描值作为观察基线，不猜测其中
哪些是历史人工修改；历史缺失证据不补造。先建立只读有效投影，在“没有覆盖”时与现有
REST 行为对比，再启用写入；来源映射歧义须能阻断受影响操作并保留原数据。

事务失败时回滚本次修正及成功记录；不影响先前已提交扫描观察。无法确认提交结果时按
同一幂等上下文查询，不创建另一条修正赌重试。投影无法解释修正或绑定冲突时，暴露安全的
冲突状态，不静默退回基值假装修正已生效。

回退优先关闭新写入口，保留修正、审计和已确认关系的兼容读取。不能简单部署不认识覆盖
的旧 scanner/读模型，让它覆盖人工关系或隐藏修正；须评估兼容性，必要时停止相关写入，
选择前向修复或经批准的备份恢复。删除覆盖数据、伪造 down migration、写回音乐文件均不是
回退方案。

## 九、验收矩阵（未来实施门禁，不是本轮已通过测试）

全部使用合成 fixture 与隔离数据库；不依赖或扫描仓库 `music/`。

| 场景 | 必须断言 |
| --- | --- |
| 相同来源重扫且修正存在 | 基值/当前证据更新；人工值、目标和审计不丢失；没有逐扫描字段管理变更集 |
| 无覆盖、设置、设空、清除 | 四种状态转换正确；必填字段设空被拒；清除读最新扫描基值，未提交字段不变 |
| 并发修正、扫描相关基值/关系变化 | 预期版本过期时拒绝或重新预览；无部分更新、静默重挂或最后写入覆盖 |
| 同 root 内重命名、移动（阶段 I） | 完整成功扫描中唯一 1:1 音频完全相同时保留原 UUID 与修正；多对多、指纹不同或扫描不完整时不重绑定，只有完整成功扫描可置旧来源 missing；没有相似度迁移修正 |
| 换 root | 新旧身份分离；转移修正只能通过单独审阅的映射操作 |
| 最小成员增减、同目录冲突、多碟结构变化（阶段 I） | Release 按成员关系匹配，增删文件与最小来源变化不换 ID；成员关系无法证明连续时，修正不会被复制、丢弃或偷偷继承，旧绑定可追踪 |
| CUE sheet/父来源/轨号/起始帧改变与旧库升级 | 覆盖身份演进与兼容反例；不把旧身份回退当任意跨版本复用 |
| 同路径替换音频或缺失后恢复 | 阶段 I 保存指纹后，同路径但指纹不同的内容不静默沿用原身份；不声称路径相同证明内容相同 |
| 失败、取消或不完整扫描 | 保留已提交正向观察和既有覆盖；无负向 missing、覆盖清理或虚假恢复点 |
| 弱证据分组、强证据冲突、人工确认 | 弱证据只提候选；无批准规则则不自动归组；Group 成员变化保留不同 Release |
| 合并/拆分/重新归组带相斥修正 | 先给出完整映射与冲突决议；失败不改变任何相关实体；逆操作恢复修正意图而非源标签 |
| 投影与 provenance | 列表、详情、检索/排序/分页一致；观察与修正可区分；详细证据授权和路径脱敏不退化 |
| 越权、重复请求、记录写入失败 | 越权无副作用；同键同义只执行一次、不同语义冲突；业务和成功记录共同提交或回滚 |
| 撤销前发生后续编辑/扫描依赖变化 | 不覆盖后续修正；必要时重新评审；恢复无覆盖不把历史基值伪写回扫描列 |
| 关闭写入与兼容回退 | 修正/关系仍可解释、不可被旧扫描器破坏；无覆盖时读模型与旧合同一致 |
