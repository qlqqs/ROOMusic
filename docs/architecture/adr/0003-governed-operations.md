### 当前可恢复性与缺口

- 目录恢复只支持：当前为 disabled，revision 匹配，且能找到对应当前 revision 的成功
  disable 记录，其前态为 active、版本恰好相邻。恢复产生**新 revision**，不是回退计数器。
- 注册已存在路径会返回其实际状态和 revision，不隐式重新启用，不保证每次注册都增加
  revision。create 记录的空前态不是删除根目录、移除已有资料库或通用撤销注册的充分依据。
- 恢复目录配置不恢复音乐文件、已扫描元数据或被外部程序删除的内容，也不等于恢复某次
  扫描。当前停用/恢复不应被 UI 命名为整库“检查点回滚”。
- 表允许 `failed` 状态，但当前写入点只插入成功操作；校验拒绝和事务失败通常返回错误，
  不会生成完整的失败 Journal。不能因为列存在就宣称所有尝试已经持久审计。
- **已发现的目标绑定缺口**：停用指纹只有状态与预期 revision，恢复指纹只有预期 revision，
  均没有路由中的 root ID；重放查询又只按 actor/类型/键定位。从代码可推导：同一 actor
  将同键同 body 用于另一个 root 时，可能拿到前一 root 的已存响应，而不是目标冲突。
  这是静态核对发现，未在本轮运行复现；修复须另立行为变更与定向测试，不混入 M0 或
  行为保持的 B0。
- 重放查询位于修改事务之前；现有测试证明的是串行重试路径，不足以承诺并发同键请求
  都返回相同结果。通用合同实施前必须补齐并发收敛验证，不能直接复制该流程并声称完备。

## 二、治理对象、角色与风险分类草案

### 不同操作流不得混用

| 操作流 | 应有的权威与记录 | 不应套用的概念 |
| --- | --- | --- |
| 共享资料库人工管理/修正 | 后端授权、类型化变更、版本与幂等、持久操作记录；按批准政策决定是否审批 | 前端按钮可见即有权限；管理员天然能恢复任何历史状态 |
| 用户本人的收藏、歌单等个人数据（未来能力） | session 与归属校验、资源可见性、输入限制及必要的并发/重试合同；可有自己的审计/撤销 | **不进入共享资料库治理审批**；也不能借免审批修改他人数据或共享元数据 |
| 确定性扫描观察 | 管理员启动/取消的现有授权、扫描运行记录、当前来源证据及 complete-only missing | 不按每个发现字段创建人工变更集，不把扫描记录展示成可撤销检查点 |
| 运行日志 | 安全诊断与 request/scan/operation 关联 | 不作为恢复所需业务状态的唯一来源 |

当前只存在 `admin`、`user`；`editor` 是角色扩展候选，不能从原型文案或以下分级推导其权限。
`admin`/`user` 是身份角色，`assistant`/`steward`/`operator` 是未来执行模式，二者不可互换。
现有人类管理员直接调用目录端点，也不代表后端已记录 `operator` 模式或通用审批。

### 拟议风险类别（供讨论，不是已批准权限表）

| 类别 | 示例 | 推荐讨论方向与限制 |
| --- | --- | --- |
| 只读 | 浏览、证据查询、预览 | 不走变更审批，仍按后端权限过滤；详细证据当前为管理员专属 |
| 个人范围写入 | 自己的收藏/歌单 | 普通用户自己的行为不走共享治理审批；跨用户共享/代办另行授权 |
| 有限共享数据库修正 | 单个可解释字段覆盖、清除覆盖 | 可采用人工明确提交的轻量路径；是否另需审批取决于批准后的角色/范围政策 |
| 结构性或批量共享变更 | 版本重新归组、合并拆分、修正迁移、多资源批量操作 | 完整影响预览、范围上限、相关 revision 和可执行逆操作；审批强度待确认 |
| 不可逆或外部副作用 | 永久删除、源标签写回、移动/删除源文件 | **当前拒绝且不注册能力**；未来必须独立批准安全、恢复及明确不可逆政策 |

不能仅因操作名为“设置字段”就归为低风险；目标数量、是否改变共享关系、来源绑定、可恢复性
与受影响用户都要进入判断。模型给出的风险值只是证据输入，后端自行判定。

现有目录和成员管理在 M1 仍可按当前合同使用；不能把此草案的治理建议倒灌成“所有管理
操作必须等通用审批后才能开放”，也不能反过来把未实现的收藏/歌单当成已有能力。

## 三、推荐候选：最小共同合同与类型化执行器

### 概念与责任

| 概念 | 推荐职责 | 明确不等于 |
| --- | --- | --- |
| Change Set | 一次操作的明确意图、完整目标范围、依赖版本、变更与逆操作计划 | 原始 HTTP body、任意字段补丁或一轮完整扫描 |
| Approval | 对特定提案及上下文作出的有期限授权输入 | 已执行、已成功，或永久授予调用者某种权限 |
| Operation Journal | 追加式生命周期记录，关联 actor、mode、业务结果及安全审计线索 | 可任意改写的状态摘要、运行日志或完整事件溯源 |
| Checkpoint | 支持本操作逆向执行的最小前态、版本、关系清单或必要摘要 | 整库/全文件系统备份、每次扫描自动创建的快照 |
| 类型化逆执行器 | 在当前授权和前置条件成立时执行已注册的逆动作 | 自然语言“撤销一下”、恢复旧 SQL 或任意 shell |

操作域拥有批准绑定、生命周期、幂等及恢复协调；目录和 catalog 用例仍拥有各自业务规则，
身份域负责当前主体授权。通过应用合同/窄端口协作，不让“通用操作”包直接读写各业务私有表。
M3 推荐先支持明确、有限的数据库事务操作；不为了未来文件副作用预建通用分布式执行平台。
文件读取、模型审查和人工等待在执行事务外完成；事务内只核验已有依据与批准是否仍有效。

### 边界数据流

```text
人类明确意图 / 未来 Agent 提案
  → 后端解码与当前主体授权 → 业务用例形成有界预览 / Change Set
  → 政策要求的人工批准或独立审查（与执行分开持久标识）
  → 后端重验 actor、mode、policy、工具、目标、版本、证据与批准有效性
  → 幂等执行入口 → 类型化业务用例 → 同一受控事务
       └→ 资源变化 + 最小恢复信息 + 成功 Journal + 幂等结果
  → 安全结果投影 → 页面显示审批、执行、可恢复性各自状态
```

同源/会话检查属于入口防护；业务授权与物理边界仍由后端重验。提案、预览、已批准、已执行
及可恢复是不同事实；已批准不代表提交成功，有操作记录也不代表存在逆操作。

### 批准与 actor/mode/policy 绑定

推荐批准至少绑定：实际发起主体及代办关系、提案身份/版本、规范化参数、类型化目标集合、
范围摘要、相关 revision、证据摘要、操作定义/政策版本、允许模式、批准者及有效期限。
这些是概念要求，不是本轮确定的数据库列或 wire schema。

- actor 来自有效会话或未来批准的委托身份；不能信任请求中自填的用户、角色或模式。
  记录提案者、审阅者与执行所代表的人，但不保存会话 token、密码、原始提示词或私有路径。
- 修改目标、参数、依据、模式或政策要求时，原批准不得自动套用；需要重新预览/审查。
  权限被撤销、用户被禁用、证据过期或目标改变后，即使曾批准也不能执行。
- 批准与执行分离，执行入口只接受后端可验证的批准记录/依据；不能由调用者在自己的
  proposal 中写 `approved` 就取得权威。
- 执行时再次授权、核对受影响范围及版本；使用有约束的后端工具，不允许任意 SQL、shell、
  主机路径或 Agent 直接访问私有存储。
- 人类普通管理 UI 的一次明确提交可作为已批准政策中的轻量路径，但“是否需要独立审批”
  必须由政策规定；不能在记录缺失时补造一次人类批准。

### 未来 Music Steward 的继承合同

此表来自[操作规范](../../../.trellis/spec/backend/agent-and-operation-guidelines.md)的长期
约束，不表示 M3 已有运行时，也不替代尚待确认的工具/风险权限矩阵。

| 模式 | 批准路径 | 执行边界 |
| --- | --- | --- |
| `assistant` | 危险提案须当前用户明确批准 | 不得自批；仍校验当前身份、工具、范围、版本和幂等 |
| `steward` | 独立 Review Subagent 对有界提案给出结构化结果，且政策允许 | 主 Agent 不可自审；审阅输出只是输入，后端最终裁决 |
| `operator` | 显式管理员选择的直接执行，不需用户确认或 AI 审查步骤 | 只跳过批准步骤，不跳过授权、工具白名单、版本、幂等、日志与恢复分类 |

独立审查的 `approved`、`rejected`、`needs_human_confirmation` 不能混同。审阅者不可用、
失败、拒绝或要求人工时，Steward 不执行；需要人工时进入明确人工路径，不静默降为
Operator。审查证据必须有界且脱敏，不提供数据库连接、媒体字节或无限制文件系统访问。
即使审阅通过，后端也可以且必须拒绝越权、过期或不安全操作。

## 四、revision、幂等与执行结果

### 推荐的并发与幂等合同

1. 业务用例列出完整受影响资源及关联前置条件。除字段本身，还包括来源绑定、Group/Release
   成员关系等；不能只检查用户打开的那一行。revision 粒度与
   [覆盖层 ADR](0002-metadata-overlays.md) 一起确定。
2. 幂等键有明确的 actor/类型化操作作用域；规范化指纹必须包含目标身份和完整操作语义、
   预期版本及批准上下文引用，不能遗漏路由目标。相同键不同目标、设空与清除、不同范围
   均应冲突，而非重放无关结果。
3. 同键同义的已完成请求，在当前授权允许读取该结果后返回已存结果，不重新执行，也不因
   首次执行已提升 revision 而再用旧版本执行一次。权限撤销后不能借重放读取受限数据。
4. 同键并发请求须收敛为一个执行者和可查询结果；执行中、成功、失败或结果暂未知必须可
   区分。不能让客户端遇到断线后换新键重试，也不能把重复执行风险伪装为成功。
5. 真正执行前，在能覆盖并发写者的锁/条件更新边界内重验授权相关状态、资源版本和批准。
   stale revision 交由用户重新预览，不无条件重试为覆盖写。
6. 资源、修正意图、相关关系、最小恢复信息、成功 Journal 与幂等结果在同一事务提交。
   必需 Journal 或恢复信息写入失败不得留下“业务成功但记录缺失”的半成品；普通运行
   日志不替代这些业务记录。

长期合同中的失败、进行中、部分失败等状态不意味着每种工具都允许部分成功。推荐 M3
数据库内操作以全成全败为默认；超出大小/时限上限应拆成用户明确批准的独立操作，而不是
先提交半批后再把它称为原子批次。文件/外部副作用的分阶段执行合同不属于本次启用范围。

### 失败与持久记录

- 可记录的已接受提案应有可追踪执行身份；授权拒绝用安全拒绝信息记录，避免给攻击者
  泄露目标存在性或放大无界审计写入。
- 业务事务回滚后，失败生命周期记录可通过独立、受控的记录流程写入，明确没有业务提交；
  不可为了保留失败事件而提交半个业务事务。
- 数据库故障时不能保证立即写下失败事件。提交结果不明须呈现待核实、按原幂等身份对账，
  不能把“未收到响应”当成已回滚，也不能伪造持久审计成功。
- 需要 Journal 追加事件来记录状态变化，不覆盖历史成功事实来“消除”错误。面向 UI 的
  当前状态摘要可以是派生结果，不成为另一写权威。

## 五、检查点与逆操作

### 单次逆操作

- 可恢复性由已注册业务执行器与实际前态证据决定；不是每条记录都显示“撤销”。清除覆盖、
  设空、Group 成员调整等必须有不同且类型化的逆语义。
- 逆操作是一次新的、受授权/必要审批保护的管理操作，关联原操作并提升 revision；不删除
  原 Journal，不把版本号倒退，不重放已失效的原批准。
- 必须确认当前状态仍符合原操作后态及依赖关系。若已有他人修正、扫描身份/关系变化或
  后续操作依赖该结果，则报冲突并要求重新形成方案，不覆盖新状态。
- 恢复覆盖时恢复之前的**修正意图**；无覆盖不是历史扫描值快照。依赖当前扫描证据的恢复
  预览需重验这些证据；不能把撤销解释成全库时间旅行。
- 证据缺失、逆执行器版本不受支持、目标不可确认或操作不可逆时，拒绝逆操作并说明边界；
  不要求 Agent 根据自然语言日志补猜旧值。

### 逆序链：全部预检后原子执行

“恢复到某点”只有对明确支持的、范围有界的管理操作链才可成立，不能泛指扫描结束时间。
推荐首版若实现链式恢复，限定为同一数据库事务可覆盖的资源；否则只提供单次逆操作。

1. 从当前头部确定待撤销的操作集合与依赖闭包，按依赖的逆序形成计划。时间排序本身
   不足以确定依赖；不能跳过作用于同一目标或依赖其关系的后续操作。
2. 在有界范围内读取所有相关记录、前后态、逆执行器与当前目标；以一致锁顺序保护完整
   资源集。检查每一步的当前权限/政策、批准、可逆性、范围、证据及目标版本。
3. 在写入前，按“最新操作先撤销”模拟**整条链**，验证后一步的逻辑结果能满足前一步的
   逆向前置条件；任何一环不可逆、证据缺失、版本冲突或闭包超限，整条链拒绝。
4. 区分历史逻辑前后态与新 revision：撤销后状态可以等价于较早状态，但版本仍单调增长。
   用操作关联和已验证的模拟结果衔接步骤，不把历史 revision 原样写回或逐步当成当前值。
5. 全部通过后，在同一事务执行整链及对应记录、恢复信息和幂等结果；提交前的约束失败、
   Journal 写入失败或取消均整体回滚。提交结果不明按同一执行身份对账。

不能先撤销一部分再检测剩余链，也不能逐项提交后称为“全部恢复成功”。涉及外部副作用、
源文件、不可逆节点或旧日志无充分前态的链，首版直接拒绝；未来若提供分阶段补偿，必须
单独批准并诚实呈现部分失败，不沿用本节的原子性承诺。

### 不可逆边界

当前源目录只读。永久删除、移动、标签写回等能力均不因 Operator 模式或风险分类草案而
获得授权。未来经独立任务批准的不可逆工具，仍须显式标注无逆操作、拒绝跨越该节点的恢复；
已有长期规范对永久清理的 Operator-only 约束也不是启用该工具的许可。

## 六、替代方案与取舍

| 方案 | 收益 | 代价与结论 |
| --- | --- | --- |
| 最小共同操作合同 + 各能力类型化执行器（推荐候选） | 目录、覆盖和未来结构操作共享授权/幂等/审计语义，保留业务所有权 | 需补批准绑定、恢复证据及跨资源并发合同；先做已批准操作，不做通用任意写引擎 |
| 轻量替代：目录与少量修正各保留专用操作记录/单次逆操作 | 更小实施面，不必立即建设统一审批队列或链式恢复 | 仍需同等身份、revision、目标幂等和恢复保证；统一查询可后续适配，不能宣传为完整通用治理。若 M3 范围很小，可优先选此方案 |
| 所有操作完整事件溯源、分支和全库快照 | 统一历史重放的表达能力强 | 当前历史不足且扫描具有部分提交；复杂度与存储/恢复承诺超出需求，不推荐 |
| 直接扩展目录表的类型字符串与任意 JSON 执行 | 表面复用快 | 把不同资源规则、权限和逆语义藏进无类型数据；容易遗漏目标/版本，不推荐 |
| 运行日志或模型描述驱动撤销 | 几乎不增加业务记录 | 无充分前态、版本和原子性，不可作为恢复机制 |

选择轻量替代不等于降低安全门槛：可以暂不提供审批队列、批量/链式恢复，但不能只实现
可点击 UI，或把不支持的恢复用自然语言指令替代。

## 七、适用阶段与迁移/回退

| 阶段 | 建议边界（除现状外均待批准） |
| --- | --- |
| M0 | 记录本草案与代码缺口，不更改当前目录合同或权限 |
| M1 | 使用现有目录/成员管理与扫描 API；只展示有实际依据的目录操作摘要，隐藏通用审批及扫描恢复点 |
| B0 | 行为保持拆包；目标幂等修复、通用操作、权限和新增错误语义须独立审阅，不混入纯重构 |
| M3 | 明确选择最小共同合同或轻量替代；先覆盖批准的目录与元数据修正写路径；成员管理是否纳入需另列范围，不声称已全部治理 |
| M4 | 依赖 M3，逐类批准 Group/版本关系操作、修正迁移及逆操作，不直接开放任意合并/拆分 |
| M5 | 个人收藏/歌单继续走归属与资源授权，不强塞共享治理审批 |
| M6 | Agent 身份委托、工具注册、独立审查与模式选择经单独批准并验证后，才复用同一执行权威 |

### 渐进迁移

1. 通过新迁移演进，不改已共享迁移。先补现有窄合同的测试及经批准的缺口修复，再扩展
   新能力；旧 root 结果的重放不得被新指纹规则无意破坏，兼容窗口需专项设计。
2. 历史目录记录可经只读适配展示为“旧目录操作”，保留原 ID、actor、revision、响应与
   原语义；不能补造 `change_set_id` 对应的历史意图、批准、mode、policy 或未记录的失败。
   若迁移建立新关联 ID，必须标明是迁移关联而非当时已存在的事实。
3. 历史 restore 仅保留原来明确支持的恢复依据；不得从空前态推导 create 可逆，更不能
   把旧扫描记录导入检查点或承诺跨全部历史的链式撤销。
4. 一次操作只有一个执行权威；若过渡期写入新旧记录，必须同事务且有明确幂等归属，
   不允许两个入口各执行一次。读取先验证等价，写入按能力分阶段切换。
5. 审计保留时长、检查点清理及证据安全必须先有规则；清理恢复信息前，明确改变对应
   操作的可恢复性，不保留一个已经失效的“撤销”按钮。

### 回退与故障恢复

关闭新提案/写入入口时，保留历史读取、已提交记录及恢复依据；进行中的操作必须先对账，
不能仅回滚前端就重放。旧程序不认识新状态/覆盖/图关系时，不应重新获得这些资源的写权威；
选择兼容只读、前向修复或经审阅的备份恢复。不得删 Journal、删检查点或倒退 revision 来
制造“像没执行过”的假象。源文件仍完全不动，不引入破坏性的假 down migration。

## 八、测试与验收场景（未来实施门禁）

下表是必须新增或延续的验证场景，不是本轮已实现或运行通过的断言。用小型合成 fixture
及隔离数据库，不使用真实 `music/` 或私有路径。

| 场景 | 必须断言 |
| --- | --- |
| 当前目录注册/停用/恢复及成员管理 | 沿用现有权限、同源、状态、最后管理员与 session 约束；重复注册不重新启用目录 |
| 现有停用/恢复同键用于不同 root | 指纹绑定目标；跨目标明确冲突且无副作用，不返回另一 root 的结果；旧结果兼容可验证 |
| 同键同义串行/并发、同键不同参数/模式/目标 | 一个执行结果，不重复副作用；不一致请求冲突；权限失效后重放不泄露结果 |
| 操作超时、断线、提交结果不明 | 保留稳定执行身份并可对账；不换新键猜测重试，不伪称失败已回滚 |
| user 越权共享写入、未知 editor、伪造 actor/mode | 默认拒绝；没有数据库变化或权限提升；不得把缺少角色解释成 admin |
| 自己的收藏/歌单与他人资源（能力实现时） | 本人合法写入不触发共享治理审批；跨用户/不可见目标拒绝；仍有输入及并发保护 |
| 批准后更换目标、参数、revision、证据或政策 | 批准失效，重新预览/审批；不调用业务执行器 |
| 批准与执行之间用户禁用/权限撤销 | 执行重新授权并拒绝；既有批准不授予永久能力 |
| Assistant 未获必要人工批准 | 不执行危险提案，不能用自填批准绕过 |
| Steward 自审、审阅不可用/拒绝/需人工 | 不执行、不降级 Operator；独立批准也不能越过后端能力拒绝 |
| Operator 非管理员或未知/越界工具 | 拒绝；管理员也必须通过参数、范围、版本、幂等和恢复分类校验 |
| 单事务中资源、恢复信息或 Journal 写入失败 | 业务及成功记录共同回滚；可记录的失败与未确定提交结果明确区分 |
| 单次撤销前发生后续编辑、来源映射变化 | revision/依赖冲突，不覆盖新值；原 Journal 不被删除，新逆操作 revision 递增 |
| 清除覆盖和设空的逆操作 | 恢复正确修正意图；不把历史扫描值写回基值；相关证据变化触发重新确认 |
| 两步及以上逆序链、共享资源交叉依赖 | 全链模拟与全部预检；逆序正确、版本单调增长、依赖闭包完整 |
| 链中途的不可逆、缺失证据、越权、超限或冲突 | 预检整链拒绝；所有资源和成功 Journal 无变化，不先撤销前半段 |
| 全链执行末步故障、记录失败或提交前取消 | 整体回滚；不出现半条恢复链或虚假成功 |
| 扫描失败/取消/不完整及正常重扫 | 已提交正向观察可保留；只有成功完整扫描作 missing；无逐字段治理变更或扫描恢复点 |
| 历史迁移、兼容读取、关闭新写入 | 不伪造审批/mode/失败历史，不扩大旧恢复能力，不让旧入口重新执行新操作 |
| 记录与证据安全 | 仅批准的角色/归属可读，范围及分页有界；无 token、密码、完整主机路径、SQL、私有媒体和原始模型内容 |

## 九、实施前待批准事项

1. M3 选择共同合同还是轻量替代；首批治理哪些操作，是否实现审批队列/单次逆操作/链式
   恢复，成员管理的持久审计何时补齐。不能以“通用”二字扩大首批范围。
2. 风险分类及具体权限矩阵：哪些人类共享操作需要独立审批；是否引入 `editor` 以及其
   提案、执行、批准权限。当前 admin/user 合同在批准前保持不变。
3. actor/委托、mode、政策版本、批准期限和失效策略；是否要求人类复核不同于提案者；
   Steward 独立审查不替代后端权威这一不变量不可放宽。
4. 资源 revision、证据依赖、幂等作用域、并发执行和断线对账方案；目录目标绑定缺口
   的独立修复范围及旧记录重放兼容策略。
5. 检查点最小内容、保留与清理政策、逆执行器兼容版本、恢复链范围/大小/时限和原子性；
   没有验证的恢复类型应明确不支持，而不是以风险提示代替实现。
6. 审计失败/数据库不可用的呈现与恢复责任，历史记录迁移及新旧写入口切换/回退方案。
7. M4 结构操作与 M6 Agent 的单独批准边界；源标签/文件变更继续范围外，不因模式存在
   自动解禁。

本 ADR 获批时须记录选择者、日期与明确范围；M0 文档验收只证明提案和证据齐备，不证明
通用治理能力已经可用。
